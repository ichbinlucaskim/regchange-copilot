# 17. 조정 가능한 지점 — 노브 목록과 그 근거

ML 에는 조정 지점의 이름이 정리돼 있다 — 학습률, 배치 크기, 스케줄러. 누구나 "학습률을
올리면 수렴이 빨라지고 불안정해진다"를 안다. **에이전트 쪽은 그 어휘가 아직 정리돼
있지 않다.** 이 문서는 이 저장소가 실제로 조정한 지점을 한 곳에 모은 것이다.

**노브 총 69개** — 측정 **15** / 추론 **17** / 관행 **13** / 설계 **24**.

측정으로 정한 것이 15개다. 나머지 54개는 근거가 있되 **재보지 않았거나**(추론),
**표준값을 그대로 쓰거나**(관행), **값이 하나뿐인 결정**(설계)이다. 이 비율 자체가
이 시스템의 현재 상태다 — 조정 지점의 5분의 1만 실측으로 정해져 있다.

---

## 1. 노브인가 설계인가

```
값을 바꾸는 것    →  노브  →  이 문서
구조를 바꾸는 것  →  설계  →  ADR
```

경계가 애매한 것을 먼저 처리한다.

| 항목 | 판단 | 근거 |
|---|---|---|
| **`GroundingMode`** (anchored / de-anchored) | **노브** | 값처럼 보이지만 검증기 **구조**를 바꾼다(1단계 블라인드 호출이 생긴다). 그럼에도 노브로 두는 이유는 **같은 자리에 같은 서명으로 갈아끼울 수 있고 골든셋으로 대조 가능**하기 때문이다 — ADR-016 이 `VECTOR`/`LEXICAL` 경로를 남긴 것과 같다. 채택 결정 자체는 ADR-013 에 있고, 이 문서는 **현재 값이 무엇이고 바꾸면 무엇이 움직이는가**만 다룬다 |
| **청킹 단위** (조) | **노브이자 설계** | 값은 하나지만 바꾸면 **인용 경로·골든셋 채점 단위·DB 스키마**가 함께 움직인다. 되돌리기 비용이 「스키마」인 유일한 노브이며, 그래서 아래 표에 넣되 **바꾸려면 ADR 이 먼저** 라고 적는다 |
| **`MAX_REVISIONS`** | **노브** | 0/1/2 는 값이다. 다만 0 으로 정한 **결정**은 ADR-013 의 정정 이력에 있다 |
| 킬 스위치 저장 위치 | **설계 (ADR-019)** | DB 냐 환경변수냐는 값이 아니라 구조다. 노브는 그 위의 `CACHE_TTL_SECONDS` |
| gate 2단을 코드로 하는 것 | **설계 (원칙 2)** | 노브가 아니다 |
| 승인 게이트를 그래프에 두는 것 | **설계 (ADR-018, 원칙 4)** | 노브가 아니다 |

## 2. 근거를 세 종류로 구별한다

| 종류 | 의미 | 개수 |
|---|---|---|
| **측정** | 대조 실험으로 정했다. 수치와 출처가 있다 | **15** |
| **추론** | 근거는 있으나 재보지 않았다 | **17** |
| **관행** | 일반적으로 쓰는 값. 우리 데이터로 고르지 않았다 | **13** |
| **설계** | 값이 하나뿐이며 그것이 결정 자체다 (fail-closed 등) | **24** |

**측정과 나머지를 섞지 않는 것이 이 문서의 요지다.** 「추론」 항목 중 측정할 가치가
있는 것에는 ⚑ 를 붙였다.

## 4. ML 과 다른 점

### 4-1. 결정론이 없다

`temperature` 와 `seed` 를 **쓸 수 없다** — Sonnet 5·Opus 5 가 거부한다
(`docs/incidents/llm-api-schema-drift.md`). 그래서 **노브를 바꿔 재면 그 차이가 노브
때문인지 변동성 때문인지 가려야 한다.**

3회 반복으로 그 크기를 쟀다 (`docs/15-variability-results.md`):

| 경로 | 편차 |
|---|---|
| 검색 (임베딩·BM25·RRF) | **0** — 15케이스 × 3모드 완전 일치 |
| 생성·판정 | 집계값 0~2, **케이스 단위 10/15 불안정** |

→ **집계값으로 노브를 비교하는 것은 유효하고, 케이스 단위로 비교하는 것은 유효하지 않다.**
→ **검색 층 노브는 1회 측정으로 충분하다.** 그 경로에 샘플링이 없기 때문이다.

### 4-2. 노브가 서로 얽힌다

ML 의 하이퍼파라미터보다 결합이 강하다.

```
임베딩 교체 → 검색 결과 → gate 2단 대조 집합 → 폐기율
청킹 단위   → 인용 경로 → 골든셋 채점 단위와 어긋남 → 지표 자체가 무의미
k 증가      → 후보 증가 → 프롬프트 길이 → 비용 + max_tokens 압박
max_tokens  → 잘림 → SCHEMA_INVALID → 거짓 INSUFFICIENT_EVIDENCE  (실제로 일어났다)
```

**한 번에 하나씩 바꾼다.** 임베딩 2종 × 검색 3종을 곱하지 않고 임베딩을 먼저 확정한 뒤
결합을 잰 것이 그 원칙의 적용이다 — 곱하면 2×3=6 이 아니라 2+3=5 회로 같은 결론에
도달하고, 15건 규모에서는 교호작용을 검출할 검정력이 없다 (규약 §1).

### 4-3. 되돌리기 비용이 계층적이다

ML 에서는 대부분 "재학습"이지만 여기서는 층마다 다르다.

| 비용 | 무엇이 필요한가 | 해당 노브 |
|---|---|---|
| **즉시** | 값만 바꾼다 | 임계값, TTL, `MAX_REVISIONS`, `GroundingMode`, 프롬프트 |
| **재실행** | 인덱스는 그대로, 검색만 다시 | `k`, 결합 방식, 어휘 토큰 |
| **재인덱싱** | 152개 조 전부 다시 임베딩 | 임베딩 모델 |
| **재적재** | 원문부터 다시 파싱 | 정규화 규칙 버전, 결합자 |
| **스키마** | 마이그레이션 + 골든셋 채점 단위 변경 | **청킹 단위** |

아래로 갈수록 **되돌리기가 아니라 다시 만들기**에 가까워진다. 청킹 단위를 바꾸면
기존 측정 전부와 비교가 끊긴다 — 그래서 ADR 이 먼저다.

### 4-4. 측정에 돈이 든다

**골든셋 15건 1회가 $2.07** (`docs/15` §6). 노브 하나를 재려면 최소 그만큼 들고,
변동성까지 보려면 3배다.

그래서 "일단 바꿔보고 재본다"가 ML 보다 비싸다. **바꾸기 전에 예상 방향을 적고,
예상과 다르면 그것이 발견이다.** 이 저장소에서 실제로 그렇게 된 것이 셋이다.

| 예상 | 실제 |
|---|---|
| 모순 필터가 싸고 확실하게 걸러낼 것이다 | 12/21 발화 중 10건만 정답 — **기각** |
| de-anchored 가 case-013 을 잡을 것이다 | 여전히 놓쳤고 **정답 3건을 깨뜨렸다** |
| 재작성이 근거를 더 찾을 것이다 | **새 근거 0/15** |
| 캐시되는 것은 시스템 지침이다 | **응답 스키마가 접두부에 얹힌다** — `citation-grounding` 이 1,005 → 1,261 이 되어 최소값을 넘겼다 (§5-1) |

### 5-1. 프롬프트 캐싱 — 도입 (2026-08-24)

| | |
|---|---|
| **이전 판단** | "system 지침이 고정이라 캐시 이득이 있을 자리지만 **비용이 병목이 아니었다**" |
| **갱신 사유** | API 누적 지출 $10.85, 남은 예산 $3.3. **병목이 되었다** |
| **현재 판단** | **도입.** 프롬프트 본문은 한 글자도 바꾸지 않았다 |

**무엇을 했나.** `system` 을 문자열에서 같은 내용의 text 블록 하나로 감싸고 거기에
`cache_control: {"type": "ephemeral"}` 를 걸었다 (`adapters/llm/claude.py`).
**순서를 바꿀 것이 없었다** — 접두부는 `tools → system → messages` 순인데 우리는 도구를
쓰지 않고, 동적인 것(개정 조문·검색 문단)은 처음부터 전부 `messages` 에 있었다.
프롬프트가 이미 캐싱이 요구하는 모양이었다.

**최상위 `cache_control`(자동 캐싱)을 쓰지 않았다.** 그것은 *마지막* 캐시 가능 블록에
브레이크포인트를 놓는데, 우리 요청에서 마지막 블록은 케이스마다 달라지는 사용자
메시지다. 매 호출이 쓰기(1.25배)가 되고 읽기는 한 번도 일어나지 않아 **비용이 늘어난다.**

**실측 — 캐시되는 접두부는 시스템 지침보다 크다.** 예상과 달랐던 곳이다.

| 프롬프트 | 시스템 지침 (`count_tokens`) | **실제 캐시된 접두부** | 차이 |
|---|---|---|---|
| `obligation-extraction` | 1,326 | **2,052** | +726 |
| `impact-assessment` | 1,963 | **3,044** | +1,081 |
| `citation-grounding` | 1,005 | **1,261** | +256 |

차이는 응답 스키마(`output_config.format`)다. 스키마가 큰 프롬프트일수록 접두부가 크다.
**이것이 판단을 뒤집었다** — 시스템 지침만 세면 `citation-grounding`(1,005)이 Sonnet 5 의
최소 캐시 길이 1,024 에 19 토큰 모자라 "호출이 가장 많은 프롬프트는 캐시가 안 된다"가
결론이었을 것이다. 실제로는 스키마가 얹혀 1,261 이 되어 캐시된다. **모델별 최소값이
다르다**(Opus 5 는 512, Sonnet 5 는 1,024) — 대조 모델로 돌리면 조건이 달라진다.

**실측 — 출력이 바뀌는가.** 공식 문서는 "Prompt caching has no effect on output token
generation. The response you receive is identical to what you would get if prompt caching
were not used" 라고 적는다. 그 위에 같은 날 같은 3케이스(003·009·011)를 캐싱 없이 1회,
캐싱으로 1회 돌려 §1b 의 3회 실행과 나란히 놓았다.

- `hit`(정답 문단 적중)과 `cited` 는 5회 전부 같은 방향이다 — case-009 는 5/5 동일.
- 흔들린 것은 `impact_status` 와 `departments` 이며, **§1b 가 R-27 로 이미 등재한 바로 그
  두 필드다.** case-003 의 세 가지 status 는 캐싱을 켜기 전 3회 실행에서 이미 전부 나왔다.
- **캐싱 실행의 모든 값에 캐싱 없는 선례가 있다.** 오히려 이력에서 가장 벗어난 것은
  오늘의 **캐싱 없는** 실행이었다(case-011 이 3/3 이관 → 이관 아님).

→ **(a) 판정.** 캐싱이 출력을 바꾼다는 증거가 없고, 관측된 차이는 이미 문서화된 변동성
범위 안이다. n=1 대조로 "같음"을 증명한 것은 아니다 — **증명한 것은 "변동성과 구별되는
차이가 관측되지 않았다"이며**, 프롬프트 바이트가 그대로라는 사실과 공식 문서의 보장이
판단의 주된 근거다.

**실측 — 얼마나 줄었나.** 같은 토큰 볼륨 기준 **입력 비용 −26.5%** (3케이스 대조:
$0.0914 → $0.0672), 캐시 히트율 0.3333. 15건 실행 구조(2026-08-22 v3)에 적용하면
입력 289,353 토큰 중 **129,402(44.7%)가 접두부**이고 입력 비용 $0.5787 → $0.3604(−37.7%),
실행 전체는 $2.013 → $1.795(**−10.8%**). 출력 토큰이 비용의 71%라 총액 절감은 여기서 막힌다.

**TTL 은 기본값(5분)이다.** 1시간(쓰기 2배)을 사지 않은 근거: 같은 프롬프트의 연속 호출
간격이 실측 최대 **208초**였다(15건 실행). 케이스당 간격이 5분을 넘기 시작하면 재검토한다.

| 노브 | 값 | 근거 | 바꾸면 |
|---|---|---|---|
| 캐시 브레이크포인트 위치 | `system` 1개 | 설계 — 정적/동적 경계가 거기 하나뿐 | 자동 캐싱은 **비용이 는다** |
| 캐시 TTL | 5분(기본) | **측정** — 호출 간격 최대 208초 | 1h 는 쓰기가 2배 |
| `MIN_CACHEABLE_PROMPT_TOKENS` | 1024 (Sonnet 5) | **문서 + 실측** | 미달은 오류가 아니라 **조용한 무효과** |

**미달이 조용하다는 것이 이 노브의 함정이다.** 공식 문서가 "No error is returned" 라고
적는다. 그래서 비용 집계가 `cache_read_input_tokens` 를 **반드시** 읽어야 한다 —
캐시 도입 후 `input_tokens` 는 브레이크포인트 이후 토큰만 담으므로, 그 값만 더하면
**비용이 조용히 작게 나온다.** `impact_eval` 의 비용식을 네 단가(입력·출력·캐시읽기·
캐시쓰기) 전부 쓰도록 고쳤고, `billed_input_tokens` 와 `cache_hit_ratio` 를 요약에 넣었다.

### 5-2. Batch API — 미도입

| | |
|---|---|
| **할인** | 입력·출력 **50%** (Sonnet 5 $1/$5 per MTok). 캐싱과 **스택된다** |
| **이유 (미도입)** | 반복 측정 구간에서 지연이 순환 속도를 해친다. 대부분 1시간 내, **24시간 내 미완료는 만료** |
| **구조적 이유** | **우리 파이프라인은 케이스 단위 의존 사슬이다** — 의무추출 → 영향평가 → 인용검증이 앞 단계의 출력을 입력으로 받는다. 배치로 옮기려면 단계별로 3개의 배치를 순차 실행해야 하고, 이는 플래그가 아니라 러너 재작성이다 |
| **도입 조건** | **없다. 조건이 사라졌다** (2026-08-24 갱신) |

**도입 조건이 사라진 경위를 그대로 남긴다.** 이 표를 처음 쓸 때 조건은 "7단계 배포 후
운영 — 매일 아침 폴링으로 나온 개정을 배치로 돌리면 지연이 문제가 되지 않는다"였다.
**7단계(AWS 배포)가 범위에서 빠지면서 그 자리가 없어졌다.**

새 조건을 지어내지 않는다. 배치가 값을 하는 조건은 "지연을 감수할 수 있는 대량 처리"인데,
그런 처리 경로가 이 저장소에 남아 있지 않다. 조건이 다시 생기면(예: 일일 운영이 하루치를
모아 도는 형태가 되면) 그때 이 칸을 채운다 — **빈 칸을 "조건 미정"으로 채우는 것과
"조건이 사라졌다"고 적는 것은 다른 사실이다.**

도입하게 되면 지켜야 할 것은 기록해 둔다: 결과 순서가 보장되지 않으므로 **`custom_id`
로만 대조한다.** 배치가 5분을 넘길 수 있어 캐싱은 **1시간 TTL** 로 바꾼다(공식 문서 권고).
배치 안에서 `max_tokens: 0` 캐시 예열은 지원되지 않는다.

## 6. 이 문서를 살아 있게 하는 규칙

새 상수나 임계값을 도입할 때 이 문서에 등재한다. 근거를 **측정/추론/관행**으로 구별해
적는다. **근거가 없으면 상수를 만들지 않는다.**

마지막 줄이 이 저장소가 계속 지켜 온 것이다 — `UNSUPPORTED` 임계를 만들지 않은 것,
발화하지 않는 정합성 규칙 7개를 `ENFORCED` 로 올리지 않은 것, 이동 점수 가중치를
동결한 것이 전부 같은 규칙의 적용이다.
