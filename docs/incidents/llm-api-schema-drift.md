# 미수 3 — 설계한 스키마가 외부 API 사실과 어긋나 있었다

**3단계 5절(LLM 첫 등장) 착수 직전, `llm_invocation` 테이블을 만들기 전에 발견했다.**

값이 틀린 적이 없다. **아직 저지르지 않았기 때문이다.** 그래서 미수이며 사건 번호를
받지 않는다.

---

## 무엇이 일어났을 것인가

`llm_invocation` 스키마 설계가 **`temperature` 와 `seed` 컬럼**을 재현 근거로 상정하고
있었다. 그대로 만들었다면:

- 두 컬럼은 **모든 행에서 NULL** 이었을 것이다.
- 그 NULL 을 나중에 읽는 사람은 "기록이 누락됐다" 또는 "기본값을 썼다"로 읽는다.
  **"애초에 존재하지 않는 값"이라는 세 번째 가능성은 스키마 어디에도 적혀 있지 않다.**
- 그리고 그 위에 세운 replay 설계가 성립하지 않는 채로 남았을 것이다.

### 사실

대상 모델인 `claude-sonnet-5` 와 `claude-opus-5` 는 **샘플링 파라미터를 거부한다.**
`temperature` / `top_p` / `top_k` 를 보내면 **HTTP 400** 이고, `seed` 는 API 표면에
존재하지 않는다. 확장 사고(thinking)가 항상 관여하는 모델 계열에서 샘플링 제어가
제거됐고, 대신 `output_config.effort` 로 깊이를 조절한다.

즉 **"온도 0 + 시드 고정으로 같은 답을 재현한다"는 방식이 이 API 표면에는 없다.**

---

## 어떻게 발견되었는가

**구현 직전에 API 레퍼런스를 읽었기 때문이다.** 어댑터를 쓰기 전에 모델 ID·구조화 출력
계약·토큰 사용량 필드·단가를 확인하러 갔고, 그 문서의 "API 변경" 표에 샘플링 파라미터
제거가 적혀 있었다.

**탐지 장치가 잡은 것이 아니다.** 이번에도 문서가 잡았지만, 미수 2 와 달리 **우리 문서가
아니라 외부 문서**였다. 우리 쪽에는 이것을 잡을 장치가 없었다.

만약 어댑터를 먼저 쓰고 나중에 읽었다면, 첫 호출이 400 으로 실패했을 것이고 그때
스키마를 고쳤을 것이다. **즉 이번에는 "실패가 시끄러웠을" 가능성이 높다.** 그 점에서
조용한 누락 계열보다는 덜 위험하다 — 그러나 그것은 운이지 설계가 아니다. 400 이 나지
않고 조용히 무시되는 파라미터였다면 NULL 컬럼과 틀린 replay 설계가 그대로 남았다.

---

## 미수 1·2 와의 대조

| | 미수 1 | 미수 2 | **미수 3** |
|---|---|---|---|
| 시점 | 이미 저질렀다 | 아직 저지르지 않았다 | **아직 저지르지 않았다** |
| 결과 | 우연히 맞았다 | 틀렸을 것이다 | **틀렸을 것이다** |
| 대상 | 코드가 쓴 결과 | 문서가 쓴 지시 | **문서가 그린 스키마** |
| 무엇이 틀렸나 | 표본이 잘려 있었다 | **우리 판단**이 틀렸다 | **외부 시스템의 사실을 확인하지 않았다** |
| 잡은 것 | 다른 방식의 재계산 | 우리 문서가 요구한 검증 | **외부 문서** |

**미수 2 와 형태는 같다** — 문서화된 방향을 따랐다면 잘못됐을 것이다.
**성질은 다르다.** 미수 2 는 우리가 가진 데이터를 잘못 해석한 것이고, 이번은 **확인할 수
있었던 외부 사실을 확인하지 않은 것**이다.

---

## 대비되는 사례 — 법제처는 팠고 Anthropic 은 안 팠다

0.7단계에서 법제처 API 는 **실측했다.** `docs/api-exploration/law-api-spec.md`,
`edge-cases.md`, `diff-measurements.md` 가 그 기록이다. 응답 유형을 분류했고,
`efYd` 소급 조회가 실패한다는 것도 6건을 실제로 던져 보고 알았다(골든셋 README §5).
`<개정 …>` 마커 556건, `<54>` 578건 같은 숫자가 문서에 있는 이유가 그것이다.

**같은 저장소에서 LLM API 는 실측 없이 스키마를 그렸다.** 파라미터 이름을 기억으로 적었고,
그 기억이 이전 세대 모델의 것이었다.

### 교훈 — 실측하는 습관은 외부 시스템마다 따로 필요하다

한 외부 시스템을 판 경험이 다른 외부 시스템으로 자동으로 옮겨 가지 않는다.
법제처 API 는 "낯설다"고 느껴 팠고, LLM API 는 "안다"고 느껴 안 팠다.
**익숙함이 검증을 건너뛰게 만든다.** 그리고 이 도메인에서 익숙한 것일수록 세대가 바뀌며
조용히 달라져 있다.

CLAUDE.md §5.1 은 "확인하지 않은 규제 내용을 쓰지 않는다"를 규정한다. 이번 건은 그
규칙의 적용 범위가 **규제 원문에만 걸려 있었다**는 사실을 드러낸다. 외부 API 계약도 같은
성질의 사실이다.

## 파급 — replay 의 성격이 바뀐다

이것이 이 미수의 실질적 결과다.

| | 전제했던 replay | **실제로 가능한 replay** |
|---|---|---|
| 무엇을 확인하나 | 같은 입력에 **같은 답**이 나오는가 | 같은 입력으로 **지금 돌리면 무엇이 나오는가** |
| 근거 | `temperature=0` + `seed` 고정 | 없음 (파라미터가 존재하지 않는다) |
| 쓸모 | 결정론 검증 | **모델·프롬프트 교체 시 회귀 검증** |

**모델 교체 시 회귀 검증에는 여전히 쓸 수 있다.** 다만 의미가 다르다.

**이 사실을 문서에 적지 않으면 나중에 "replay 가 다른 답을 내는데 버그 아닌가"가 된다.**
그것이 이 문서를 쓰는 가장 실용적인 이유다.

### 그래서 재현 가능성을 무엇으로 확보하는가

같은 답을 보장할 수 없으므로, **그때 무엇을 보냈고 무엇을 받았는지를 완전히 남기는**
쪽으로 옮긴다. `010_llm_invocation.sql` 이 그 형태다:

- `prompt_template_sha256` — 프롬프트 원본 고정
- `request_params_json` — 실제로 보낸 파라미터 전부
- `api_version` — 같은 모델 ID 라도 버전이 바뀌면 기본값이 바뀔 수 있다
- `input_document_versions_json`, `retrieved_chunk_ids[]` — 입력 고정
- `raw_output_sha256`, `s3_key_raw_output` — 받은 것 고정

**"재현"이 "같은 답"에서 "같은 상황의 완전한 기록"으로 바뀐 것이다.** 감사 질문이
"그 시점에 담당자가 알 수 있었던 정보는 무엇이었는가"(원칙 6)라면, 후자로도 답할 수 있다.
답할 수 없게 되는 것은 "지금 다시 돌려도 같은가"이며, 그 질문은 원칙 6 의 질문이 아니다.

## 재발 방지

| 장치 | 무엇을 막나 |
|---|---|
| **외부 시스템 의존 스키마는 실측 기록 없이 확정하지 않는다** | 기억으로 그린 컬럼. 법제처에 적용한 기준을 다른 외부 시스템에도 적용한다 |
| **항상 NULL 인 컬럼을 만들지 않는다** | "누락"과 "존재하지 않음"이 같은 NULL 로 표현되는 것 |
| **`request_params_json` 같은 열린 자리를 둔다** | 파라미터가 하나 생길 때마다 같은 미수가 반복되는 것. `변경사유` 를 닫힌 enum 으로 두지 않기로 한 것과 같은 논리 |

**아직 장치가 없는 것**: 외부 API 계약이 우리 스키마와 어긋났는지를 **주기적으로** 확인하는
방법이 없다. 이번에는 착수 직전에 읽어서 잡았지만, 이미 돌고 있는 코드의 전제가 조용히
낡아 가는 것은 잡지 못한다. 모델·API 버전을 `llm_invocation` 에 기록해 두는 것이 그
탐지의 최소 재료이며, 실제 탐지 장치는 아직 없다.
