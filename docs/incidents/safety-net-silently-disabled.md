# 안전망이 조용히 무력화되어 있었다 — 연속 0건 알람

**발견일**: 2026-08-26 (로컬 cron 7일차 운영 점검, `docs/24-operations-record.md` §5-3)
**고친 날**: 2026-08-26
**성격**: **여섯 번째 사건이며 앞의 다섯과 계열이 다르다.**

---

## 0. 한 줄

**9회 연속 0건인데 카운터가 0 이었다.** 안전망은 만들어져 있었고 테스트도 있었으며,
**다른 상태 하나에 걸려 돌지 않았다.** 그 사실은 알람이 울리지 않는 것으로만 드러난다.

---

## 1. 무엇이 틀렸나

| | 값 |
|---|---|
| 실제 이력 | `SUCCEEDED_ZERO` **9회 연속** (2026-08-20 ~ 08-25 UTC) |
| 그 앞의 실행 | `SKIPPED_CANARY_FAILED` 1회 (2026-08-26 UTC, 카나리아 DNS 실패) |
| `consecutive_zero()` | **`(0, 0)`** |
| 알람 | 없음 |

`src/regchange/ops/history.py` 의 `consecutive_zero()` 가 가장 최근 실행부터 거슬러
올라가며 이렇게 셌다.

```python
for run in runs:
    if OpsRunStatus(run["status"]) is not OpsRunStatus.SUCCEEDED_ZERO:
        break  # ← SKIPPED_CANARY_FAILED 도 여기서 끊었다
    streak += 1
```

가장 최근 실행이 카나리아 실패였으므로 **첫 바퀴에서 끊겼다.** 그 뒤의 9회는 보지도
않았다.

---

## 2. 왜 무거운가 — 이 알람은 다른 방어가 없는 자리를 지킨다

`src/regchange/ops/daily.py` 의 `extract_detected()` 가 스스로 이 알람을 안전망으로
지목한다.

> 법령ID나 MST가 빈 항목은 조용히 건너뛴다. … **spec 경로가 통째로 틀렸다면 교집합이
> 0이 되어 `SUCCEEDED_ZERO`가 연속되고, 연속 0건 알람이 그것을 잡는다.**

즉 **코퍼스 설정이나 요청 경로가 조용히 깨졌을 때 그것을 잡는 유일한 장치**다.
카나리아는 잡지 못한다 — 카나리아는 「법제처 API 가 응답하는가」를 보고, 이 알람은
「우리가 보는 대상이 여전히 우리 대상인가」를 본다.

**카나리아가 임계(60일)보다 자주 실패하면 이 알람은 영원히 울리지 않는다.**
7일 운영에서 이미 한 번 실패했으므로 이것은 가정이 아니라 **관측된 조건**이다.

---

## 3. 원인 — 「그 외는 끊는다」

상태는 다섯인데 코드가 판정한 것은 **하나**였다(`SUCCEEDED_ZERO` 인가 아닌가).
나머지 넷이 전부 「끊는다」로 접혔고, 그 접힘 안에 **성질이 정반대인 둘**이 함께 있었다.

| 상태 | 접힌 판정 | 실제로 무엇인가 |
|---|---|---|
| `SUCCEEDED` | 끊는다 | ✅ 맞다. 포착이 있었다 |
| `PARTIAL` | 끊는다 | ❓ 교집합이 있었을 수도, 없었을 수도 |
| `FAILED` | 끊는다 | ❌ **관측이 없었다.** 포착의 증거가 아니다 |
| `SKIPPED_CANARY_FAILED` | 끊는다 | ❌ **수집을 하지 않았다.** 포착의 증거가 아니다 |

이 카운터가 묻는 것은 **「마지막 포착 이후 며칠인가」**다. 그 질문에 대해
`SKIPPED_CANARY_FAILED` 는 **포착의 증거도 부재의 증거도 아니다.** 끊을 것이 아니라
건너뛰어야 한다.

**그렇다고 세어서도 안 된다.** 관측하지 못한 날을 0건으로 세면 수집 실패가 「개정 없음」
으로 위장하며, 그것이 **R-11 이 정의한 최상위 위험**이다. 끊지도 세지도 않는 **세 번째
값**이 필요했고, 코드에는 그 자리가 없었다.

## 4. 앞의 다섯과 무엇이 다른가

| # | 사건 | 무엇이 틀렸나 |
|---|---|---|
| 1 | 조용한 누락 3건 | **측정 코드**가 적게 셌다 |
| 2 | 테스트가 운영 이력을 지웠다 | **개발 행위**가 운영 데이터를 파괴했다 |
| 3 | LLM API 스키마 드리프트 (미수) | **외부 계약**에 대한 우리 기억이 낡았다 |
| 4 | 측정 러너가 전량 실패를 만점으로 보고 | **측정 코드**가 실패를 성공으로 바꿔치기했다 |
| 5 | 경계를 넘은 전제 2건 | **우리가 정한 근거**가 다음 단계에서 무효가 됐다 |
| **6** | **연속 0건 알람 무력화** | **안전망 자체가 돌지 않았다** |

1·4는 측정 코드, 2는 개발 행위, 3·5는 전제였다. **6번은 방어 장치 그 자체다.**

**차이가 중요한 이유는 드러나는 방식이다.**

```
측정 코드가 틀리면   →  숫자가 이상하다        →  다시 세면 드러난다
안전망이 안 돌면     →  아무 일도 일어나지 않는다  →  드러나지 않는다
```

**안전망의 실패는 「아무 알람도 없음」과 구별되지 않는다.** 그리고 그 상태는
「정상」과 **바이트 단위로 같다** — R-11 이 외부 API 에 대해 적은 문장과 같은 구조다.

> 이 API는 성공 응답에도 `resultCode`·`page`·`numOfRows`가 없어 **정상 0건과 요청
> 실패가 바이트 단위로 동일하다.** — `docs/04-risk-register.md` R-11

**R-11 은 외부 API 의 조용한 실패이고, 이 사건은 그 R-11 을 막으려고 만든 방어의
조용한 실패다.** 방어가 한 겹 안쪽에서 같은 병에 걸렸다.

## 5. 어떻게 발견되었나 — **알람이 아니라 조회로**

**알람은 아무것도 말하지 않았다.** 7일차에 `ops` 조회 결과를 하나씩 손으로 읽다가,
「0건이 6일인데 연속 0건 카운터가 0」이라는 **두 수치의 모순**에서 나왔다.

```
ops summary   0건 성공 6일
ops alerts    연속 0건: 0회 / 0일
```

**같은 사실을 두 경로로 본 것이 발견의 전부다.** 한쪽만 봤으면 드러나지 않는다.
이것은 이 저장소가 반복해서 쓴 방법이며(카나리아 = 수집의 두 번째 관측, 재계산 =
집계의 두 번째 관측), 이번에는 **사람이 그 역할을 했다.**

**자동으로 잡을 수 있었나 — 아니다.** 단위 테스트는 `SUCCEEDED_ZERO` 만 이어진 이력과
`SUCCEEDED` 가 끊는 이력을 검사했고 **둘 다 통과했다.** 없던 것은 「그 사이에 다른
상태가 낀 이력」이었다. 테스트가 검사한 것은 코드가 다루기로 한 경우들이고, 결함은
**다루기로 하지 않은 경우**에 있었다.

## 6. 고친 것

**판정을 세 값으로 나누고 다섯 상태를 전부 열거했다.**
`src/regchange/ops/models.py` 의 `zero_streak_verdict()`.

| 상태 | 판정 | 근거 |
|---|---|---|
| `SUCCEEDED` | `BREAK` | 처리한 법령이 있다. 정의상 교집합이 있었다 |
| `SUCCEEDED_ZERO` | `COUNT` | 폴링이 정상이고 교집합이 0 이었다 |
| `PARTIAL` | `laws_detected > 0` 이면 `BREAK`, 아니면 `COUNT` | **상태로 가르지 않고 관측값으로 가른다.** 일부 실패했어도 교집합이 있었으면 spec 경로는 살아 있다 |
| `FAILED` | `SKIP` | 폴링한 날짜가 **전부** 실패했다. 0 을 관측한 것이 아니다 |
| `SKIPPED_CANARY_FAILED` | `SKIP` | 수집 자체를 하지 않았다 |

**세 가지를 함께 넣었다.**

1. **기본 분기를 두지 않는다.** `match` 의 마지막이 `assert_never(status)` 이므로
   상태가 하나 늘면 **mypy 가 `make lint` 에서 막는다.** 「그 외는 끊는다」가 이번
   결함의 원인이었으므로 그 표현이 코드에 다시 생길 수 없게 했다.
   (검증: 분기 하나를 지우면 `error: Argument 1 to "assert_never" has incompatible
   type "Literal[OpsRunStatus.FAILED]"; expected "Never"`)
2. **달력 일수를 계수한 실행 기준으로 잰다.** 건너뛴 실행을 기점으로 삼으면
   관측하지 못한 구간이 0건 구간에 포함된다.
3. **`LIMIT` 을 걸지 않는다.** 건너뛰는 상태가 창 앞을 채우면 구간이 조용히 잘리고,
   그 절단은 **알람을 덜 울리는 방향**이다 — 이 함수에서 가장 피해야 하는 실패다.

### 발화까지 확인했다

카운터가 이어지는 것만으로는 안전망이 산다고 할 수 없다. `fetch_alerts()` 가 실제로
`CONSECUTIVE_ZERO` 를 내는지까지 고정했다
(`tests/integration/test_ops_history.py::test_the_alert_fires_across_a_canary_failure`).

**고치기 전 코드로 되돌리면 그 테스트를 포함해 3건이 실패한다.** 확인했다.

### 지금 데이터로 재현

```
고치기 전:  연속 0건 0회 / 0일
고친 뒤:    연속 0건 9회 / 6일   (임계 60일 → 알람은 여전히 없음. 6일은 정상이다)
```

**알람이 울리지 않는 결과는 같지만 이유가 다르다.** 전에는 셀 줄 몰라서였고 지금은
6일이 60일 미만이어서다.

## 7. 남는 것

- **`FAILED` 가 연속되는 것을 이 알람은 잡지 않는다.** 의도한 것이다 — 그 사실은
  `ops_run` 에 행으로 남고 `ops summary` 의 실패일수와 `ops history` 가 보여준다.
  한 알람에 두 실패를 묶으면 하나를 고치고 "해결됐다"가 된다 (R-28/R-29 를 나눠
  등재한 것과 같은 판단). **다만 「실패가 며칠 연속인가」를 보는 장치는 아직 없다.**
- **`SKIP` 이 오래 이어지는 것도 잡지 않는다.** 카나리아가 계속 실패하면 그 자체가
  `CANARY_FAILED` 알람으로 매번 뜨므로 별도 장치를 만들지 않았다. **그 알람을 아무도
  보지 않으면 같은 자리에 같은 병이 생긴다** — 미확인으로 남긴다.
- **이 사건은 알람을 보낼 곳이 없다는 사실과 겹쳐 있다.** 지금 알람은 `ops alerts`
  조회 명령이 전부다. 사람이 조회하지 않으면 울려도 들리지 않는다.

## 8. 이 사건이 남기는 규칙

> **안전망은 「돌았는가」를 확인해야 하고, 그 확인은 「울리지 않았다」로 대신할 수 없다.**

안전망을 만들 때 함께 만든다: **발화 테스트**(그 이력에서 실제로 알람이 나오는가) 와
**열거 강제**(상태가 늘 때 조용히 기본 분기로 떨어지지 않는가).
