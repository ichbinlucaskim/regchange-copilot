# 테스트가 운영 이력을 지웠다

**2026-08-20. 운영 시작 첫날. 실제 손실이 발생했다.**

`make check` 안의 `TRUNCATE` 가 운영 데이터베이스를 비웠다. 그날의 첫 운영 실행
기록(`ops_run` 1행)이 소실됐다. 복구하지 않았다 — 복구할 수 없다.

| | |
|---|---|
| **잃은 것** | `ops_run` 1행 (2026-08-20 첫 실행, `SUCCEEDED_ZERO`, 7일 창 폴링) |
| **원인** | 테스트와 cron 이 같은 데이터베이스(`regchange`)를 썼다 |
| **발견** | 사고 직후. `regchange ops summary` 가 "운영 기록이 없다"를 출력했다 |
| **대응** | 테스트 DB 분리(`regchange_test`) + 파괴 대상 DB 가드 |

---

## 이 사건이 기존 기록과 다른 점

이 디렉터리의 기존 기록(`silent-undercounting.md`)은 전부 **"계산이 틀렸다"** 였다.
조용한 누락 3건, 미수 2건, 원인 진단 정정 3건 — 값이 틀리거나 판단이 틀렸다. 데이터는
그대로 있었고 다시 세면 맞는 값이 나왔다.

**이번은 개발 행위가 운영 데이터를 파괴한 것이다.** 다시 셀 대상이 없다.

그리고 **미수가 아니다.** 미수는 "같은 기전이 재발했으나 결론이 틀리지 않은 경우"이며,
값이 맞았다는 이유로 지우지 않으려고 남기는 것이다. 여기서는 값이 맞고 틀리고가 아니라
행이 사라졌다. 사건 번호를 받는다.

---

## 무엇이 일어났나

`ops` 패키지를 만들면서 `tests/conftest.py` 의 `TRUNCATED_TABLES` 에 `ops_run` 과
`ops_law_outcome` 을 추가했다. 테스트가 서로 간섭하지 않으려면 필요한 조치였고,
그 판단 자체는 옳다.

문제는 **그 `TRUNCATE` 가 향하는 데이터베이스**였다. `conftest` 는 `owner_dsn()` 으로
접속했고, 그 값은 `regchange` — cron 이 방금 첫 실행 기록을 쓴 바로 그 DB 다.

```
07:00 KST   cron 이 아닌 수동 첫 실행 → ops_run 1행 기록 (성공)
    ↓
   make check → pytest → conftest → TRUNCATE ops_run, ops_law_outcome, ... CASCADE
    ↓
   regchange ops summary → "운영 기록이 없다"
```

**이 노출은 새로 생긴 것이 아니다.** `load_run` 과 `regulation_document` 는 처음부터
같은 목록에 있었고 같은 DB 를 지우고 있었다. 달라진 것은 **지워서 아까운 것이 생겼다**는
사실뿐이다. 적재 데이터는 다시 수집하면 되지만 "그날 돌았다"는 다시 만들 수 없다.

---

## 어떻게 발견되었나

**운이 좋았다.** 세 가지가 겹쳤다.

1. `ops summary` 를 그날 만들었고, 만들자마자 눈으로 확인하려고 실행했다
2. 실행 기록이 1건뿐이라 "0건"이 즉시 이상해 보였다
3. 직전에 `make check` 를 돌렸다는 사실이 기억에 남아 있었다

**셋 중 하나만 어긋났어도 몇 주 뒤에 발견했을 것이다.** 조회 명령이 없었다면 아무도
`ops_run` 을 보지 않았을 것이고, 실행이 수십 건 쌓인 뒤였다면 몇 행이 빠진 것을
알아채지 못했을 것이다. 이력의 중간이 비면 그것이 "노트북이 꺼져 있던 날"인지
"지워진 날"인지 **구별할 방법이 없다.**

> 이 저장소의 사건 기록에서 반복되는 발견 경위: **다른 방식으로 다시 세어 봤을 때.**
> 이번에는 "다른 방식으로 세는 도구"(`ops summary`)를 만든 직후였다.

## 왜 조용한가

| 신호 | 실제 |
|---|---|
| `make check` | **성공한다.** 662 passed |
| DB | 비어 있다. 오류 없음 |
| 로그 | `TRUNCATE` 는 정상 SQL 이다. 경고가 없다 |
| 무엇을 잃었는가 | **아무도 모른다.** 지워진 행의 목록은 남지 않는다 |

**테스트가 실패했다면 즉시 알았을 것이다.** 성공했기 때문에 늦었다. 이것이
이 저장소가 반복해서 마주친 형태다 — 실패는 시끄럽고 조용한 것은 성공처럼 보인다.

`TRUNCATE` 는 심지어 불변성 트리거도 우회한다. `regulation_*` 테이블에는 행 단위
`BEFORE UPDATE OR DELETE` 트리거가 걸려 있어 과거를 지울 수 없지만(원칙 6),
`TRUNCATE` 에는 그 트리거가 발화하지 않는다. **원칙 6을 지키는 장치가 이 경로에는
없었다.**

---

## 왜 위험한가

운영 실적은 **시간이 만드는 자산**이고 복구할 수 없다. 코드는 나중에 밤새워 다시 쓸 수
있지만 "N개월간 매일 돌았다"는 못 만든다 (ADR-014).

몇 달 뒤 "N일간 운영, M건 포착, 실패 K일"을 말하려는데 이력 중간이 끊겨 있으면
그때는 되돌릴 방법이 없다. 더 나쁜 것은 **끊겼다는 사실조차 증명할 수 없다**는 점이다 —
미실행일과 삭제된 날이 똑같이 "행이 없음"으로 보인다.

**이 사고가 3개월 뒤에 발견됐다면 3개월치가 날아갔을 것이다.** 운영 시작 첫날에
발견된 것이 유일한 다행이다. 잃은 것이 1행이라 이 기록을 쓸 수 있었다.

## 대응

### 1. 데이터베이스 분리 (설정)

테스트는 `regchange_test` 에서 돈다. 세션 시작 시 없으면 만들고, 스키마와 권한은
**마이그레이션이** 적용한다.

**권한을 conftest 가 흉내 내지 않는 것이 중요하다.** 마이그레이션 003 은
`GRANT CONNECT ON DATABASE %I` 에 `current_database()` 를 쓰므로 어느 DB 에서든
같은 SQL 이 같은 경계를 만든다. conftest 가 GRANT 를 직접 썼다면 security 테스트가
검사하는 대상이 **커밋된 SQL 이 아니라 테스트 코드**가 되고, 그 순간
"테스트를 통과시키려고 테스트를 고치는" 경로가 열린다.

### 2. 파괴 대상 DB 가드 (구조)

**분리만으로는 부족하다.** 분리는 설정이고, 설정은 `.env` 한 줄이나 환경변수 하나로
되돌아온다. 그래서 규칙을 이름에 걸었다 — `regchange.store.dsn`:

```python
DISPOSABLE_DATABASE_SUFFIX = "_test"


def assert_disposable_database(database: str) -> str:
    if not database.endswith(DISPOSABLE_DATABASE_SUFFIX):
        raise ProductionDatabaseError(...)
```

**의도가 아니라 접속 결과를 검사한다.** `TRUNCATE` 직전에 `SELECT current_database()`
로 서버에 물어 확인한다. DSN 문자열은 우리 의도이고 서버 응답은 사실이며,
**이 사고의 원인이 바로 그 둘의 어긋남**이었다 — 우리는 테스트 DB 를 쓴다고 믿었다.

가드는 마이그레이션보다도 먼저 돈다. 마이그레이션도 되돌릴 수 없는 작업이다.

### 3. 발화 확인

**장치를 만들고 발화시켜 보지 않으면 작동하는지 모른다** (R-21 탐지 장치와 같은 규칙).

- `tests/unit/test_store_dsn.py` — 운영 DB 이름이 거부되는가, 그리고 **운영 DB 의
  실제 이름이 우연히 규칙을 통과하지는 않는가**
- `tests/integration/test_test_database_guard.py` — 픽스처가 건네는 커넥션이 정말
  `_test` 를 보고 있는가, 운영 DB 에 붙으면 가드가 발화하는가
- 수동 확인(2026-08-20): `TEST_DATABASE` 를 `regchange` 로 바꾸고 이름 검사를
  우회한 상태로 DB 테스트를 실행 → `ProductionDatabaseError` 로 **중단**됐고,
  운영 DB 의 `ops_run` 2행은 그대로였다

## 교훈

> **개발 환경과 운영 환경의 경계는 코드가 아니라 인프라로 그어야 한다.**
> DB 이름이 같으면 어떤 코드 규율도 그 경계를 지키지 못한다.

`TRUNCATED_TABLES` 목록을 아무리 신중히 관리해도 이 사고는 막히지 않았다. 목록은
"무엇을 지울까"의 문제였고 사고는 "어디서 지울까"에서 났다. 코드 리뷰가 볼 수 있는
것은 앞의 질문뿐이다.

**그리고 이 경계는 로컬에서 더 흐리다.** AWS 라면 계정이나 VPC 가 갈라서 같은 실수를
하기 어렵다 — 운영 DB 에 붙으려면 다른 자격증명, 다른 엔드포인트, 대개 다른 네트워크가
필요하다. 로컬은 같은 Postgres 인스턴스에 DB 이름만 다르고, 자격증명도 호스트도 같다.
**경계를 넘는 데 필요한 것이 문자열 하나뿐인 환경**에서는 그 문자열을 검사하는 장치가
있어야 한다.

부수적으로: `TRUNCATE` 가 불변성 트리거를 우회한다는 것을 알고 있었고
(`conftest` 모듈 docstring 에 적혀 있다), "app_* role 에 TRUNCATE 권한이 없으므로
안전하다"고 결론지었다. 그 결론은 **애플리케이션 role 에 대해서만** 맞았다.
테스트는 소유자 권한으로 붙는다. 방어의 적용 범위를 좁게 확인하고 넓게 안심했다.

## 원칙과의 연결

### "0과 실패를 같은 값으로 두지 않는다"의 같은 형태

이 저장소는 수집에서 그 구별을 집요하게 지켰다 — 정상 0건과 요청 실패를 같은
`0` 으로 기록하지 않으려고 카나리아와 0건 재요청을 만들었다(ADR-005, R-11).

**같은 구별이 운영 이력에서는 없었다.**

| 수집 | 운영 이력 |
|---|---|
| "그날 개정이 없었다" | "그날 실행하지 않았다" (노트북 꺼짐) |
| "요청이 실패했다" | "그날 기록이 지워졌다" |
| 응답만으로 구별 불가 → 카나리아 | 행 부재만으로 구별 불가 → **장치 없었음** |

`ops_run` 은 "실패한 날"과 "실행하지 않은 날"을 구별하려고 만든 테이블인데,
정작 **"지워진 날"** 은 그 설계에 없었다. 지금도 없다 — 가드는 지워지는 것을 막을
뿐이고, 이미 지워진 것을 사후에 알아내지는 못한다. 그것이 이 사건의 잔여 리스크다.

### R-11 계열이지만 방향이 반대다

| | R-11 (외부 API) | silent-undercounting (우리 코드) | **이 사건** |
|---|---|---|---|
| 성질 | 조용한 실패 | 조용한 누락 | **조용한 파괴** |
| 방향 | 안 들어옴 | 적게 셈 | **있던 것이 사라짐** |
| 복구 | 재수집 가능 | 재계산 가능 | **불가능** |

앞의 둘은 원본이 남아 있어 되돌릴 수 있다. 이 사건만 되돌릴 수 없으며,
그래서 **탐지가 아니라 예방**이 유일한 대응이다.

## 남은 것

- **삭제 탐지는 없다.** 누군가 소유자 권한으로 `TRUNCATE` 하면 지금도 지워지고,
  지워진 사실은 남지 않는다. 가드는 테스트 경로에만 걸려 있다. `ops_run` 에
  연속성 검사(예: `run_id` 의 시각 순서에 구멍이 있는가)를 넣을 수 있으나,
  미실행일과 구별되지 않으므로 **탐지가 되지 못한다** — 현재 설계로는 불가능하다.
- **백업이 없다.** 로컬 Postgres 볼륨이 유일한 사본이다. 배포 전까지 이 상태다.
  이 항목은 `docs/08-deployment-considerations.md` 로 넘긴다.
