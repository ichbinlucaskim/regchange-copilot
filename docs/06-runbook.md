# 06. 운영 런북

## 이 문서의 목적

시스템이 이상 동작할 때 **당직자가 새벽에 읽는 문서**다. 설명이 아니라 절차를 쓴다.
배경 지식을 전제하지 않고, 명령어와 판단 기준을 그대로 적는다.

## 1. 킬 스위치

**스위치는 `.env` 가 아니라 DB 에 있다** (ADR-019). `.env` 에 `LLM_ENABLED=true` 를 적어도
아무 효과가 없다.

### 1.1 지금 상태를 본다

```bash
regchange switch list       # 현재 값 + 마지막 변경 사유
regchange switch history    # 누가 언제 왜 바꿨는가 (감사 질문의 답)
```

### 1.2 끈다

```bash
regchange switch off LLM_ENABLED --by <사람> --reason "<왜 끄는가>"
```

`--by` 와 `--reason` 은 **필수다.** 껐다는 사실만 남으면 다음 사람이 왜 껐는지 모른다.

### 1.3 무엇이 멈추는가

| 스위치 | 멈추는 것 | 멈추지 않는 것 |
|---|---|---|
| `RETRIEVAL_ENABLED` | 사내 규정 검색 전부(위임 승격의 재검색 포함) | 수집·파싱·차분(`ops daily`) |
| `LLM_ENABLED` | 모델 호출 전부 — 추출·초안·검증 | 검색, 승인 기록, 검토 UI 조회 |
| `DISPATCH_ENABLED` | 승인된 건의 **외부 발송** | 승인 자체. `action_outbox` 행은 계속 쌓인다 |

### 1.4 반영까지 걸리는 시간 — **최대 60초**

보장이 아니라 **상한**이다. 프로세스마다 최대 60초짜리 캐시가 있다.

즉시 반영이 필요하면 **프로세스를 재시작한다.** 캐시를 비우는 명령은 일부러 만들지
않았다 — 60초가 실제로 문제가 되는지 아직 관측된 적이 없다.

### 1.5 끄면 안전한가 — 진행 중이던 작업

| 상황 | 어떻게 되는가 |
|---|---|
| **이미 나간 모델 호출** | 끝까지 간다. 중간에 끊지 않는다 — 끊으면 `llm_invocation` 행이 남지 않는 호출이 생긴다 |
| **다음 노드로 넘어가려는 그래프** | 그 노드 진입에서 멈춘다. 예외가 나며 체크포인트는 직전 노드까지 남는다 |
| **승인 대기 중인 그래프** | `LLM_ENABLED` 를 꺼도 **재개된다.** 승인 이후 노드는 모델을 부르지 않는다 — 스위치는 모델을 멈추는 장치이지 사람의 판단을 멈추는 장치가 아니다 |
| **승인은 됐는데 발송이 꺼짐** | `action_outbox` 에 쌓인다. 켜면 나간다 |

### 1.6 멈춘 이유를 구별한다

로그와 예외 메시지에 셋 중 하나가 찍힌다. **조치가 다르다.**

| 종류 | 뜻 | 무엇을 하는가 |
|---|---|---|
| `OFF` | 누가 껐다 | `regchange switch history` 로 이유를 보고 그 사람에게 묻는다 |
| `NEVER_SET` | 켠 적이 없다 | `regchange switch on` 으로 켠다. **기본값은 꺼짐이다** |
| `UNAVAILABLE` | 상태를 못 읽었다 | **스위치 문제가 아니다.** DB 장애 대응이 먼저다 |

### 1.7 다시 켤 때 확인할 것

1. 껐던 이유가 해소됐는가 — `regchange switch history` 로 그때의 `reason` 을 읽는다
2. 켠 뒤 `regchange switch list` 로 값이 실제로 바뀌었는지 확인한다
3. `DISPATCH_ENABLED` 를 켤 때는 **쌓여 있던 `action_outbox` 가 한꺼번에 나간다.** 켜기
   전에 그 수를 확인한다
4. 켜는 것도 기록이다. `--reason` 에 "무엇이 해소돼서 켠다"를 적는다

### 1.8 기본값이 꺼짐인 이유

설정 누락이나 신규 환경 기동이 기능 활성으로 이어지면 **아무도 그 상태를 눈치채지
못한다.** 행이 없으면 꺼진 것으로 읽으며, 켜는 것은 사람의 명시적 행위여야 한다
(CLAUDE.md §6, fail-closed).

## 5-1. 일일 작업 (로컬 운영) — ADR-014

이 절만 절차가 채워져 있다. 실제로 도는 유일한 자동 작업이기 때문이다.

### 무엇이 도는가

```
매일 07:00 KST  launchd(com.regchange.daily)
  → scripts/ops/daily_ingest.sh
    → regchange ops daily --days 7
      카나리아 → regDt 폴링(어제부터 7일) → 코퍼스 필터
      → 본문 수집·적재 → 직전 MST 확보 → diff → ops_run 기록
```

로그: `data/ops-logs/daily-YYYYMM.log` (월 단위). **1차 기록은 `ops_run` 테이블**이고
이 파일은 프로세스가 죽어 행조차 못 남긴 경우의 흔적이다.

### 어떻게 알아차리는가

```bash
make ops-summary          # 운영 일수 / 성공·실패·미실행 일수 / 총 포착
make ops-history          # 최근 30일, 실패한 법령과 사유까지
make ops-alerts           # MISMATCH · 변경규모 초과 · 연속 0건 · 카나리아 실패
```

### 상태별 판단 기준

| 상태 | 뜻 | 조치 |
|---|---|---|
| `SUCCEEDED` | 새로 포착한 개정이 있고 실패 없음 | 없음 |
| `SUCCEEDED_ZERO` | 코퍼스 대상 개정 0건 | **정상이다.** 12개월 실측에서 코퍼스 개정일은 365일 중 14일이다 |
| `PARTIAL` | 일부 날짜/법령 실패 | `ops history` 로 사유 확인. **다음 실행이 자동 재시도한다** |
| `FAILED` | 폴링한 날짜가 전부 실패 | API 상태 확인. 지속되면 `docs/incidents/` 기록 |
| `SKIPPED_CANARY_FAILED` | 카나리아 실패로 **수집하지 않음** | 우리 실패가 아니다. 그날 데이터가 없는 이유가 기록돼 있다 |

### 실패했을 때

1. **재시도를 늘리지 않는다.** 기록이 우선이다. 실패한 법령은 다음 실행이 다시 시도한다.
2. 특정 날짜만 다시 돌리려면: `uv run regchange ops daily --date 20260819`
3. 원인이 새로운 것이면 `docs/incidents/` 에 추가한다.

### 며칠 비었을 때

노트북이 꺼져 있었으면 실행 기록이 없다. 7일 이내면 다음 실행이 자동 회수한다.
그보다 길면 창을 명시적으로 넓힌다:

```bash
uv run regchange ops daily --days 21
```

`ops summary` 의 **미실행일**이 그 공백을 계속 보고한다. 숨기지 않는다.

### launchd 등록·해제·확인

```bash
make ops-install                                        # 등록 (07:00 KST → 로컬 시각 환산)
launchctl print gui/$(id -u)/com.regchange.daily | grep 'last exit code'
launchctl kickstart -k gui/$(id -u)/com.regchange.daily # 지금 한 번 돌리기
make ops-uninstall                                      # 해제
```

### 첫날 실패의 두 원인

1. **macOS 보호 디렉터리 (exit 126, `Operation not permitted`).**
   저장소가 `~/Documents` · `~/Desktop` · `~/Downloads` 아래에 있으면 launchd 가 띄운
   프로세스는 그 안의 스크립트를 **실행하지 못한다**(TCC). 파일 읽기는 되는데 실행만
   막히므로 원인이 보이지 않는다. 해소는 둘 중 하나다 —
   - 시스템 설정 > 개인정보 보호 및 보안 > **전체 디스크 접근 권한**에 `/bin/bash` 추가
     (`+` > `Cmd+Shift+G` > `/bin/bash`)
   - 저장소를 보호 디렉터리 밖으로 옮긴다 (예: `~/dev/`)

   `make ops-install` 이 이 조건을 감지해 경고한다.

2. **환경 미상속.** launchd 는 셸 환경을 상속하지 않는다. `.env` 는 파이썬이 직접
   읽으므로(`regchange.config.settings`) 셸에서 export 할 필요가 없고, `PATH` 와 작업
   디렉터리는 래퍼 스크립트가 고정한다. **수동 실행이 되는데 launchd 만 실패하면
   1번을 먼저 의심한다.**

### 타임존 — 세 개의 시계를 구별한다

| 무엇 | 어느 시계 | 이유 |
|---|---|---|
| 기록 (`ops_run`, `run_id`, `fetched_at`) | **UTC** | 어디서 돌려도 같아야 정렬이 단조롭다 |
| 법령 날짜 (`regDt`, 공포일자, 시행일자) | **원본 8자리** | 법제처가 준 값이다. 변환하지 않는다 |
| 표시·일수 집계 (`ops summary` 의 실행일) | **KST** | 운영자가 검증할 수 있는 달력은 자기가 사는 달력이다 |
| 스케줄 (`StartCalendarInterval`) | **기계 로컬** | launchd 에 타임존 옵션이 **없다** |

**이 기계는 `America/Los_Angeles` 다.** 그래서 `make ops-install` 은 07:00 KST 를
로컬 시각으로 환산해(현재 15:00 PDT) plist 에 넣는다.

주의할 것:

- **타임존이 바뀌면 재설치한다.** `make ops-install` 을 다시 돌리면 된다.
- **DST 전환 시 한 시간 어긋난다.** PDT→PST 전환에서 07:00 KST 가 14:00 이 되지만
  plist 에는 15:00 이 남는다. 재설치 전까지 한 시간 늦게 돈다.

**둘 다 데이터를 틀리게 하지 않는다. 그것은 우연이 아니라 설계의 결과다.**

폴링 창은 실행 시각이 아니라 **KST 달력**에서 계산되고(`OPS_CALENDAR_OFFSET`),
어제부터 **7일을 재확인**한다. 실행이 한 시간 늦거나 심지어 하루 밀려도 그날의 창이
전날들을 다시 덮으므로 포착 대상이 빠지지 않는다. 환산 오차가 영향을 주는 것은
**"얼마나 빨리 알아채는가"** 뿐이다.

바꿔 말하면 **재확인 창이 스케줄 정확도에 대한 의존을 흡수한다.** 창을 1일로 줄이면
이 성질이 사라지고, 그때는 환산 오차가 곧 누락이 된다 — `--days` 기본값을 낮출 때
이 문장을 먼저 읽는다.

## 5-2. 검토 큐 (4단계) — ADR-018

### 무엇이 도는가

개정 조문 하나가 그래프를 타면 `human_review` 에서 **멈춘다.** 그래프는 그 상태로
`graph_checkpoint` 스키마에 남고, 프로세스가 죽어도 살아남는다. 사람이 결정을 내려야
다음 노드가 실행된다 — **승인 없이 발송 대상이 만들어지는 경로는 존재하지 않는다.**

```bash
make review-ui            # http://127.0.0.1:8000
uv run regchange ops alerts   # 기한 초과 / 기한 미상 건수
```

### 화면이 반드시 보여주는 것

넷 다 **"결론만 보고 승인"을 어렵게 만들기 위한 것**이다 (F-7).

1. `NEEDS_REVIEW` 경고 — 뒷받침되지 않아 제거된 주장이 있었다는 사실
2. gate 3단 판정 분포와 **각 판정의 이유**
3. 부서 배정의 근거 조항·표현과 **간접 도출 여부**
4. gate 가 폐기한 것들

### 기한 — 우리가 정한 값이 아니다

`due_at` 은 **개정 조문의 시행일**이다. 그 날까지 사내 규정이 정비되어 있어야 한다.
시행일을 확보하지 못한 건은 `due_at` 이 NULL 이고, `ops alerts` 가 **기한 초과와 따로**
센다.

| 알림 | 무엇을 뜻하는가 | 조치 |
|---|---|---|
| `REVIEW_OVERDUE` | 시행일을 넘긴 대기 건이 있다 | 담당자를 재촉한다 |
| `REVIEW_DUE_UNKNOWN` | 시행일을 확보하지 못한 대기 건이 있다 | **수집 경로**를 확인한다 |

둘을 한 숫자로 합치지 않는다. 조치가 다르면 지표도 달라야 한다.

### 결정이 반영되지 않는 경우

API 가 409 를 돌려주면 **그 결정은 반영되지 않았다.** 두 가지 원인이 있다.

| 응답 | 원인 | 확인 |
|---|---|---|
| `이미 … 상태다` | 누군가 이미 결정했다 | `review_decision` 에서 결정자와 시각 |
| `그래프가 재개되지 않았거나 승인 노드에 닿지 않았다` | 체크포인트에 그 스레드의 중단 상태가 없다 | `graph_checkpoint` 와 `impact_assessment.thread_id` |

**조용히 200 을 돌려주지 않는다.** 화면이 승인됐다고 표시하는데 실제로는 아무 일도 없는
상태를 만들지 않기 위해서다.

### 승인이 형식화되고 있는지 확인한다 (F-7)

```bash
curl -s localhost:8000/api/metrics | python3 -m json.tool
```

**반려율이 0 에 수렴하고 검토 소요가 짧아지면** 게이트가 통과 의식이 된 것이다.
둘을 함께 보지 않으면 "빠르게 잘 처리되고 있다"와 구별할 수 없다.
`OTHER` 반려가 쌓이면 사유 코드 집합이 업무를 담지 못하는 것이므로 코드를 늘린다.

### 이관된 건(`INSUFFICIENT_EVIDENCE`)은 큐에 없다

행은 남지만 `queued_at` 이 NULL 이라 대기 목록에 나오지 않는다. **볼 것이 없다는 사실
자체가 결과**이며, 상세 화면에서는 열어 볼 수 있다. 이관 비율이 매우 낮으면 gate 가
통과시키기만 하는 것이므로 원칙 2가 실제로 작동하는지 의심한다 (ADR-013 신호 4번).
