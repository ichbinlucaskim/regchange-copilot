# 24. 운영 실적 — 로컬 cron 7일차

이 문서는 축 3(운영)의 근거다. 8단계 README 의 "N일간 운영, M건 포착, 실패 K일"이 여기서
나온다. **수치를 좋게 보이려고 고르지 않는다.** 실패와 미수행을 그대로 적는다.

조회 일시: 2026-08-26 22:51Z. 이 문서의 모든 수치는 `regchange ops` 조회 결과이며
**LLM 호출은 없었다. 비용 $0.**

---

## 1. 날짜 라벨을 먼저 정한다

세 시간대가 섞여 있어 "7일차"의 기준일이 셋이다. 혼동을 막기 위해 먼저 고정한다.

| 축 | 값 |
|---|---|
| 기계 로컬 | PDT (UTC-7). 조회 시각 2026-08-26 15:51 PDT |
| 기록 | **UTC**. `run_id`, `ops_run.started_at`, 매니페스트 `fetched_at` 전부 |
| 보고 라벨 | **KST**. `ops summary` · `ops history` 의 「날짜」 열 |

cron 은 **07:00 KST = 22:00 UTC(전일)** 에 돈다. 그래서 같은 실행이
`20260825T220006Z`(UTC 8-25)이면서 보고서에는 8-26(KST)으로 뜬다.

**이 문서는 KST 로 센다.** 대상이 한국 법령이고 07:00 KST 가 하루 경계이기 때문이다.
따라서 운영 구간은 **2026-08-21 ~ 2026-08-27 (KST 7일)**이다. UTC 로 세면 8-20 ~ 8-26 이며
같은 7일이다. 어느 쪽으로 세도 7일이고, 라벨만 다르다.

## 2. 집계

```
운영 기간    2026-08-21 ~ 2026-08-27 (7일)
실행일       7일 (실행 10회)
  성공       0일
  0건 성공   6일
  부분 실패  0일
  실패       0일
  미수행     1일 (카나리아 실패)
미실행일     0일

포착         법령 0건 / change_set 0건 / 변경 0조문
```

**요약: 7일 중 6일 정상 수집(포착 0건), 1일 미수행(카나리아 실패), 미실행 0일.**

실행이 10회인데 실행일이 7일인 것은 첫날(8-21 KST)에 4회 돌았기 때문이다. 셋은 설치
당일의 손수 실행(`16:37Z`, `16:40Z`, `20:49Z`)이고 넷째가 첫 정규 cron(`22:00Z`)이다.
이후로는 하루 1회다.

## 3. 포착 0건은 「포착 없음」이지 「수집 실패」가 아니다

**0건 자체는 예상 범위 안이다.** 12개월 실측에서 코퍼스 개정일은 365일 중 14일이었다
(`docs/domain-selection/amendment-frequency.md`). 7일에 0건일 확률이 높다.

문제는 "정말 개정이 없었나"와 "수집이 죽어서 0인가"를 가르는 것이다. **로그가 가른다.**

성공한 6일 전부에서 이렇게 찍혔다 (8-25 UTC 실행 예):

```
canary.passed  date=20250401 total_count=83
폴링 대상   7일 ['20260819' ... '20260825']
  20260819  정상  전체  4 / 코퍼스 0
  20260820  정상  전체  2 / 코퍼스 0
  20260821  정상  전체  4 / 코퍼스 0
  20260822  정상  전체  0 / 코퍼스 0
  20260823  정상  전체  0 / 코퍼스 0
  20260824  정상  전체  3 / 코퍼스 0
  20260825  정상  전체 22 / 코퍼스 0
```

가르는 근거가 셋이다.

1. **카나리아 통과.** 고정 날짜(20250401)에 대해 매번 `total_count=83` 이 돌아왔다.
   API 와 파싱 경로가 살아 있다는 뜻이다.
2. **전체 개정은 잡힌다.** 폴링한 7일 중 여러 날에 전체 개정이 2~22건 잡혔다. 응답이
   비어 있는 것이 아니다.
3. **코퍼스 교집합만 0.** 잡힌 개정이 우리 9개 법령·4개 행정규칙에 해당하지 않았다.

**따라서 "포착 없음"이다.** 수집은 7일 중 6일 정상이었다.

0건 재요청(`zero_recheck`)은 각 실행에서 2회 발생했고 **결과가 달랐던 날은 없다**
(`zero_recheck.confirmed count=0`).

## 4. 실패와 재시도

### 카나리아 실패 1회 — 2026-08-27 07:05 KST

```
[CANARY_FAILED] 2026-08-26 22:05Z  20260826T220526Z-d664  (SKIPPED_CANARY_FAILED)
  카나리아 실패(20250401): TRANSPORT — jo_history_by_date: 전송 오류가 3회 시도에도
  계속됐다 (ConnectError: [Errno 8] nodename nor servname provided, or not known).
  본 수집을 시작하지 않는다. 0으로 기록하는 것보다 '수집 안 함'이 안전하다
```

`[Errno 8] nodename nor servname provided` 는 **DNS 해석 실패**다. 3회 재시도가 전부
같은 오류로 끝났다. 시작 시각이 평소 `22:00:0x` 가 아니라 `22:05:23` 인 것으로 보아
절전에서 깨어난 직후 네트워크가 아직 붙지 않은 상태로 판단한다.

**이것은 설계대로 동작한 것이다.** 수집을 시작하지 않고 `SKIPPED_CANARY_FAILED` 로
기록했다. 0 을 기록했다면 "그날 개정이 없었다"와 구별되지 않는다. 상태를 나눠 둔 것이
여기서 값을 했다.

**미실행(노트북 꺼짐/launchd 미기동)은 0일이다.** launchd 는 7일 모두 깼다.
미수행 1일은 깼지만 네트워크가 없어 스스로 멈춘 것이며, 둘은 다른 사건이다.

### 재시도

| 항목 | 값 |
|---|---|
| 본 수집 재시도 (`ops_run.retries`) | 7일 전부 0 |
| 카나리아 재시도 | 8-27 실행에서 3회 시도(2회 재시도) 후 실패 |

**API·네트워크 열화의 신호는 없다.** 성공한 6일에서 재시도가 한 번도 없었다. 8-27 의
재시도는 원격이 아니라 로컬 DNS 문제다.

## 5. 조용한 실패 점검

### 5-1. 매니페스트 없는 스냅샷 — 없음

```
리프 디렉터리 90개
  정상(매니페스트+페이지)  90
  매니페스트 없음          0
  페이지 없음              0
```

run 디렉터리 8개(`20260819T190817Z-5b64` ~ `20260824T182350Z-5837`) 전부에서
`manifest.json` 수와 `page-*.xml` 수가 일치한다. **중간에 죽은 실행은 없다.**

> 점검할 때 깊이를 틀리지 말 것. 매니페스트는 run 디렉터리 바로 아래가 아니라
> `<run>/<endpoint>/<MST-…>/manifest.json` 에 있다. 한 단계 위에서 찾으면 90개가 전부
> "매니페스트 없음"으로 나온다.

**이 함정도 계열이 있다.** 일회성 조사 코드가 운영이 쓰는 구조를 직접 들여다보다
잘못 안 것이며, CLAUDE.md §4 의 「**운영 결과를 확인할 때는 운영이 쓰는 함수를 부른다**」
가 막으려는 그 형태다. 이번에는 「없음 90건」이라는 **없는 발견**을 만들 뻔했고,
`assemble_body()` 대신 `조문내용` 을 직접 읽어 「본문이 오지 않는다」를 만든 사례와
같다 (`docs/incidents/measurement-reported-failure-as-success.md` §5-1).
**리뷰도 테스트도 거치지 않는 조사 코드가 더 위험하다** — 우회하기 쉽고 틀려도
드러나지 않는다.

### 5-2. `find_orphan_documents()` — 0건, 다만 무의미하다

```
find_orphan_documents() -> 0건
load_run                   0
regulation_document        0
```

**0건이지만 이것을 "고아 문서가 없다"의 근거로 쓸 수 없다.** 문서가 아예 0건이라
공허하게 참이다. 0.5단계의 `CREATE TABLE` 단언과 같은 형태 — 통과했지만 아무것도
증명하지 않았다.

**그 질의가 실제로 고아를 잡는지는 통합 테스트를 열어 확인했다 (2026-08-26).**
`tests/integration/test_store_loader.py::test_orphan_document_is_findable_when_run_never_completes`
가 **실제로 고아를 만든다** — 특금법 픽스처를 수집 경로에 태워 스냅샷을 쓰고,
`load_run_id=uuid4()` 로 문서를 적재한 뒤 그 run 을 끝내 기록하지 않는다. 그리고
`find_orphan_documents()` 가 **정확히 그 문서 id 하나**를 돌려주는지 본다
(`assert orphans == (result.document_id,)`).

```
0건 조회       공허하다      (문서가 0건이라 자동으로 0)
통합 테스트    공허하지 않다  (고아를 만들고, 그것만 잡는지 본다)
```

**보완할 것 없음.** 다만 두 사실을 섞지 않는다 — 운영 DB 의 0건은 여전히 아무것도
증명하지 않으며, 증명하는 것은 테스트다.

**함께 드러난 사실: 디스크의 스냅샷 90건이 DB 에 적재되어 있지 않다.** 스냅샷은 8-19 ~
8-24 의 분석·평가 작업이 남긴 것이고, 일일 운영은 포착 0건이라 적재할 것이 없었다.
운영 경로의 결함은 아니지만, **적재 경로는 이 7일 동안 한 번도 실행되지 않았다.**
즉 이 운영 실적은 "폴링과 판정"까지만 증명하며 "적재와 diff"는 증명하지 않는다.

### 5-3. ★ 연속 0건 알람이 카나리아 실패 한 번에 리셋됐다 — **고침**

**이번 점검에서 나온 유일한 결함이며, 여섯 번째 사건으로 등재했다**
(`docs/incidents/safety-net-silently-disabled.md`).

```
연속 0건: 실행 0회 / 달력 0일  (임계 60일) -> 알람 없음
```

실제로는 `SUCCEEDED_ZERO` 가 9회 연속이었는데 카운터가 0 이다. 원인은
`src/regchange/ops/history.py:343` `consecutive_zero()` 다. 가장 최근 실행부터 거슬러
올라가며 `SUCCEEDED_ZERO` 가 아니면 **끊는다.** `SKIPPED_CANARY_FAILED` 도 끊는다.

왜 문제인가. `extract_detected()` 의 주석이 이 알람을 안전망으로 지목한다.

> spec 경로가 통째로 틀렸다면 교집합이 0이 되어 `SUCCEEDED_ZERO`가 연속되고,
> 연속 0건 알람이 그것을 잡는다. — `src/regchange/ops/daily.py:104`

그런데 **카나리아가 60일에 한 번보다 자주 실패하면 이 알람은 영원히 울리지 않는다.**
7일차에 벌써 한 번 실패했으므로 가정이 아니라 관측된 조건이다. 코퍼스 설정이나 요청
파라미터가 조용히 깨져도 안전망이 발화하지 않는다.

**의미상으로도 틀렸다.** 이 카운터가 묻는 것은 "마지막으로 무언가 포착한 지 며칠인가"다.
`SKIPPED_CANARY_FAILED` 는 **코퍼스를 보지 않은 날**이며 포착의 증거도 부재의 증거도
아니다. 끊을 것이 아니라 건너뛰어야 한다.

### 고쳤다 (2026-08-26)

**판정을 세 값으로 나누고 다섯 상태를 전부 열거했다** —
`src/regchange/ops/models.py` 의 `zero_streak_verdict()`.

| 상태 | 판정 | 근거 |
|---|---|---|
| `SUCCEEDED` | `BREAK` | 처리한 법령이 있다. 정의상 교집합이 있었다 |
| `SUCCEEDED_ZERO` | `COUNT` | 폴링이 정상이고 교집합이 0 이었다 |
| `PARTIAL` | `laws_detected > 0` 이면 `BREAK`, 아니면 `COUNT` | **상태로 가르지 않고 관측값으로 가른다** |
| `FAILED` | `SKIP` | 폴링한 날짜가 **전부** 실패했다. 0 을 관측한 것이 아니다 |
| `SKIPPED_CANARY_FAILED` | `SKIP` | 수집 자체를 하지 않았다 |

**`FAILED` 를 세지 않는 이유가 끊지 않는 이유와 다르다.** 세면 수집 실패가
「개정 없음」으로 위장하고(R-11), 끊으면 안전망이 무력화된다. **끊지도 세지도 않는
세 번째 값이 필요했고 코드에 그 자리가 없었다** — 이번 결함의 본체가 그것이다.

**기본 분기를 두지 않는다.** `match` 의 마지막이 `assert_never(status)` 이므로 상태가
하나 늘면 mypy 가 `make lint` 에서 막는다. 분기 하나를 지워 확인했다:

```
error: Argument 1 to "assert_never" has incompatible type
       "Literal[OpsRunStatus.FAILED]"; expected "Never"
```

### 지금 데이터로 재현

```
고치기 전:  연속 0건 0회 / 0일
고친 뒤:    연속 0건 9회 / 6일    (임계 60일)
```

**알람은 여전히 울리지 않는다. 그러나 이유가 다르다** — 전에는 셀 줄 몰라서였고
지금은 6일이 60일 미만이어서다.

### 발화까지 확인했다

카운터가 이어지는 것만으로는 안전망이 산다고 할 수 없다. `fetch_alerts()` 가 실제로
`CONSECUTIVE_ZERO` 를 내는지까지 고정했다.

| 테스트 | 무엇을 고정하나 |
|---|---|
| `test_a_canary_failure_does_not_break_the_zero_streak` | 낀 카나리아 실패에서 구간이 이어진다 (4회 / 5일) |
| **`test_the_alert_fires_across_a_canary_failure`** | **그 이력에서 알람이 실제로 나온다** |
| `test_a_fully_failed_run_is_also_skipped` | `FAILED` 도 건너뛴다 |
| `test_a_partial_run_that_saw_the_corpus_breaks_the_streak` | 교집합이 있었던 `PARTIAL` 은 끊는다 |
| `test_a_partial_run_without_an_intersection_is_counted` | 교집합 0 인 `PARTIAL` 은 센다 |
| `test_the_span_is_measured_from_the_oldest_counted_run` | 일수를 건너뛴 실행 기준으로 재지 않는다 |
| `test_every_status_has_a_verdict` (단위) | 다섯 상태가 전부 판정을 갖는다 |

**고치기 전 동작으로 되돌리면 3건이 실패한다.** 확인했다 — 회귀 테스트로 성립한다.

경위와 계열은 `docs/incidents/safety-net-silently-disabled.md` 에 여섯 번째 사건으로
남겼다. **앞의 다섯과 다르다** — 1·4는 측정 코드, 2는 개발 행위, 3·5는 전제였고
이번은 **안전망 그 자체**다.

| `SNAPSHOT_ROOT` 설정 | **미설정 → 고침 (2026-08-26)** | `.env` 에 키가 통째로 없었다. 절대 경로를 넣었고 `.env.example` 도 갱신했다 |
| 매니페스트 `directory` 상대 경로 | 유효 | `20260819T190817Z-5b64/law/MST-282481-7af929`. 90건 전부 상대. `/Users` 가 박힌 매니페스트 0건 |
| 시각 UTC 기록 | 유효 | `ops_run.started_at` tz=`Etc/UTC`, 매니페스트 `fetched_at` `+00:00`, `run_id` 접미 `Z` |

**어긋난 것 하나: `SNAPSHOT_ROOT` 가 설정되어 있지 않았다.**

`settings.py:167` 이 스스로 적어 둔 위험 그대로다.

> 상대 경로를 주면 그대로 돌려준다. `LocalDocumentStore` 가 절대 경로로 정규화하며,
> 그 정규화는 프로세스 작업 디렉터리 기준이다 — cron 은 작업 디렉터리가 다르므로
> **운영에서는 절대 경로를 준다.**

**문서는 맞았고 실행이 따르지 않았다.** edge-case #10 과 같은 형태다 — 경고가 적혀
있는데 지켜지지 않았다. 경고를 적는 것과 그것이 설정에 반영되는 것은 다른 사실이며,
**적어 둔 쪽만 보면 지켜진 것처럼 읽힌다.**

### 노출 범위를 정확히 적는다 — **두 겹이 막고 있었다**

처음 진단은 "launchd 의 `WorkingDirectory` 한 줄에 기대고 있다"였는데, 확인해 보니
**막는 것이 둘**이다.

| 겹 | 무엇 |
|---|---|
| launchd | `<key>WorkingDirectory</key><string>/Users/lucasmac/dev/regchange-copilot</string>` |
| 래퍼 | `daily_ingest.sh` 의 `REPO_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/../.." && pwd)"` → `cd "$REPO_ROOT"` |

**래퍼 쪽이 더 강하다** — 자기 파일 위치에서 저장소 루트를 구하므로 plist 가 바뀌어도
성립한다. 따라서 「plist 한 줄이 빠지면 조용히 다른 경로에 쓴다」는 **정확하지 않다.**

**실제로 물리는 자리는 래퍼를 거치지 않는 호출**이다 — 다른 디렉터리에서
`uv run regchange ops daily` 를 직접 부르거나, 컨테이너·다른 배포 형태에서 이 셸
스크립트가 없을 때. 위험은 실재하되 방아쇠가 처음 생각과 다르다.

### 고쳤다 (2026-08-26)

```
.env          SNAPSHOT_ROOT=/Users/lucasmac/dev/regchange-copilot/data/snapshots
.env.example  키는 원래 있었다. 비워 두지 말라는 근거와 예시 한 줄을 더했다
```

`.env.example` 에는 값을 넣지 않는다(기계마다 다르다). 대신 **왜 비워 두면 안 되는지**
와 예시 경로를 적었다 — 다음 사람이 같은 자리에서 빠지지 않게 하려면 키의 존재가
아니라 **그 근거**가 있어야 한다.

## 7. 스모크 행 제외 확인

4단계에서 "지우지 않고 세지 않는다"로 처리한 행이 통계에서 빠지는지 확인했다.

DB 에 남아 있는 스모크 흔적은 **3개 테이블에 4행**이다(`docs/12-impact-assessment-results.md` §11).

|---|---|---|
| `review_decision` | 1행 (`decided_by='smoke-test'`) | 제외됨 |
| `impact_assessment` | 2행 | 제외됨 |
| `action_outbox` | 1행 | 통계 대상 아님 |

```
summarize_reviews()     -> total=0, reject_rate=None, excluded_reviewers=['smoke-test']
summarize_assessments() -> total=0, transfer_rate=None, excluded_assessments=2
```

**`ops summary` 는 이 행들을 세지 않는다.** `src/regchange/ops/history.py` 는 `ops_run`

`review/queue.py` 의 `SMOKE_REVIEWERS`·`SMOKE_ASSESSMENT_IDS` 가 담당하며 둘 다 동작한다.

**고칠 것 없음.**

## 9. 이 실적이 증명하는 범위 — **「7일간 운영」이 아니다**

**한 줄로 뭉뚱그리면 틀린 주장이 된다.** 무엇이 돌았고 무엇이 돌지 않았는지를 먼저
가른다.

| | 항목 | 근거 |
|---|---|---|
| **증명됐다** | 폴링 (`lsJoHstInf` 일자별 이력, 7일 창) | 실행 10회, 응답 전체 개정 2~22건 |
| | 응답 형태 분류 (정상 0건 / 요청 실패) | 0건 위장이 구별됐다 (§3) |
| | 카나리아 (매 실행, 실패 시 수집 미시작) | 6일 통과(`total_count=83`), 1일 실패 후 **수집하지 않음** |
| | 0건 재요청 확인 | 재시도 성공한 6일 전부 0 |
| | 실행 이력 기록 (`ops_run`) | 미수행 1일이 **행으로** 남았다 |
| **증명 안 됐다** | **적재** (`load_document` / `load_run`) | 7일간 **0회 실행**. 포착 0건이라 적재할 것이 없었다 |
| | **diff** (`change_set` 생성) | 위와 같음. `change_set` 0행 |
| | 그 이후 (검색·영향평가·승인) | 운영 경로에서 돈 적 없다. 골든셋 위의 값이다 |

```
DB 현황   regulation_document 0 / load_run 0 / regulation_article 0 / change_set 0
디스크    스냅샷 90건 — 전부 8-19 ~ 8-24 의 분석·평가 작업이 남긴 것
```

**결함이 아니다.** 포착이 0건이면 적재할 것이 없는 것이 정상 동작이다. 다만 그 정상
동작이 **적재 경로가 살아 있다는 증거는 아니다.**

### README 에 넣을 문장

> 로컬 cron 으로 **7일간(2026-08-21 ~ 08-27 KST) 매일 폴링**했다. **6일 정상 수집,
> 1일 미수행**(카나리아 DNS 실패로 수집을 시작하지 않음), **미실행 0일**. 코퍼스 개정
> **포착 0건** — 12개월 실측 개정일이 365일 중 14일이므로 예상 범위이며, 카나리아 통과와
> 일자별 전체 개정 건수(2~22건)로 "수집 실패"가 아닌 "포착 없음"임을 로그에서 구별했다.
> **이 7일이 증명하는 것은 폴링과 판정까지이며, 적재·diff 경로는 실행될 일이 없어
> 증명되지 않았다.**

**"7일간 운영"이라고 쓰지 않는다. "7일간 폴링, 포착 0건"이다.** 앞의 표현은 파이프라인
전체가 7일 돌았다는 뜻으로 읽히고, 그것은 사실이 아니다.

**"완벽하게"도 쓰지 않는다.** 7일 중 하루는 돌지 못했고, 그 7일 동안 **연속 0건
알람이 무력화된 채였다**(§5-3). 알람이 조용했던 것은 정상이어서가 아니었다.
