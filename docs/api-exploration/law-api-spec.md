## 1. 엔드포인트와 공통 파라미터

### 1.1 Base URL

```
https://www.law.go.kr/DRF/lawSearch.do    # 목록 조회
https://www.law.go.kr/DRF/lawService.do   # 본문 조회
```

`https://law.go.kr/DRF/...`(www 없음)도 동일하게 동작한다. `https://law.go.kr/OpenApiService/...`
는 **404**다 — 이 프로젝트의 `.env`에 처음 설정되어 있던 값이며 0.7단계에서 정정했다.

### 1.2 공통 파라미터

| 파라미터 | 필수 | 값 | 근거 |
|---|---|---|---|
| `OC` | 필수 | 발급받은 사용자 식별값 | 전 픽스처 |
| `target` | 필수 | 아래 target 표 참조 | 전 픽스처 |
| `type` | 필수 | `XML` / `JSON` / `HTML` | XML만 실측(`law_009244_mst252787.xml` 등). JSON은 **미확인** |
| `display` | 선택 | 목록 조회 반환 건수 | `search_law_teukgeum.xml` |
| `page` | 선택 | 목록 페이지 (1부터) | 실측 확인, §6.1 |

**`OC`는 응답 본문에 그대로 되돌아온다.** `법령상세링크`, `조문링크`,
`조문변경이력상세링크` 필드가 요청 URL을 통째로 담는다 (`search_law_teukgeum.xml`,
`dayjochg_regdt20250401.xml`). 응답을 로그·픽스처·캐시에 남길 때 반드시 마스킹해야 한다.

**일자별과 조문별 조문 변경이력은 같은 target(`lsJoHstInf`)을 쓰고 엔드포인트로만
갈린다.** `lawSearch.do`면 일자별, `lawService.do`면 조문별이다. 응답 스키마도 다르다
(§5.2, §5.3).

`lsHistory`는 활용가이드에 존재하지만 이 OC로는 **미신청 상태**다. 호출하면 HTTP 200에
"미신청된 목록/본문에 대한 접근입니다" HTML 안내 페이지가 온다
(`error_target_lsHistory.html`). 필요해지면 open.law.go.kr에서 해당 API를 신청해야 한다.
현재로선 **법령 연혁 목록 없이도** 조문별 변경 이력(`lsJoHstInf`)이 각 버전의
법령일련번호를 주므로 대체 가능하다 (`jochg_009244_jo000200_full.xml`).

#### 주의: 루트 대조는 필요하지만 충분하지 않다 (2026-08-12 구현 중 발견)

**`law` 검색 · `eflaw` 검색 · `lsHstInf` · `lsJoHstInf`(일자별) 네 target이 루트
`LawSearch` + 항목 `law`로 전부 같다.** 위 표만 보면 네 행이 구별되지 않는다.

그런데 **항목 내부의 식별자 경로가 갈린다.**

| target | MST 경로 | 법령ID 경로 |
|---|---|---|
| `law` / `eflaw` 검색 | `법령일련번호` | `법령ID` |
| `lsHstInf` | `법령일련번호` | `법령ID` |
| `lsJoHstInf` (일자별) | `법령정보/법령일련번호` | `법령정보/법령ID` |
| `lsJoHstInf` (조문별) | `법령정보/법령일련번호` | **항목에 없음** (응답 루트에 1회) |

대조 없이 잘못된 경로로 읽으면 **식별자가 조용히 `None`이 된다** — 실측:
`lschg_regdt20240719.xml`(5건)을 일자별 경로로 읽으면 5건 전부 `None`이며 예외도
경고도 없다.

→ **응답이 echo하는 `<target>`을 루트 태그와 함께 대조한다.** 검색·이력 계열은 전부
`<target>`을 echo한다(본문 계열은 echo하지 않으며 루트가 `<법령>`이라 애초에 구별된다).

#### 같은 target이 엔드포인트에 따라 다른 스키마를 낸다

**`lsJoHstInf` 두 행을 반드시 다른 것으로 다룬다.** 세 곳이 다르다.

| | 일자별 (lawSearch.do) | 조문별 (lawService.do) |
|---|---|---|
| 루트 태그 | `LawSearch` | **`LawService`** |
| `<조문정보>` 내부 | **`<jo>` 반복** | **단일** (`jo` 래퍼 없음) |
| 조문 필드 | 조문번호, 변경사유, 조문링크, **조문변경이력상세링크, 조문개정일, 조문시행일** | 조문번호, 변경사유, 조문링크, **조문변경일** |

루트 태그만 보고 분기하면 조문별 응답이 일자별 파서로 들어가고, `law/조문정보/jo`가
0건이므로 **조문이 조용히 사라진다.** 실측: `jochg_009244_jo000200_full.xml`을
일자별 경로로 세면 28건이 아니라 0건이다.

#### `resultCode`의 유무가 계열로 갈린다 (R-11의 근거)

| 계열 | `totalCnt` | `page` | `numOfRows` | `resultCode` |
|---|---|---|---|---|
| 검색 (`law`/`eflaw`/`admrul` 검색) | O | O | O | **O** |
| 이력 (`lsHstInf`, `lsJoHstInf` 양쪽) | O | X | X | **X** |
| 본문 (`law`/`eflaw`/`admrul` 본문) | X | X | X | **X** |

**이력 계열에는 `resultCode`가 없다.** edge-case #10의 `resultCode` 기반 성공/실패
분류를 이력 계열에 적용할 수 없다는 뜻이며, 이것이 R-11의 구조적 원인이다
(ADR-005 R-11, `error_dayjochg_id_only_zero.xml`).

#### 수집한 페이지를 병합하지 않는다 (2026-08-12)

여러 페이지로 받은 응답을 **하나의 문서로 합치지 않고 페이지별 원본 파일 + 매니페스트로
보관한다.** 병합하면 `totalCnt`와 실제 행 수가 어긋난 문서가 생기고, **그 어긋남이
바로 위 잘림 판별의 유일한 단서**다. 우리가 그런 문서를 만들면 스스로 위조 증거를
생산하는 것이 된다.

0.8단계 `scripts/analysis/amendment_frequency.py`는 `<law>`를 첫 응답 루트에 append
했다. 탐색 목적에는 문제가 없었으나 운영 스냅샷에는 쓸 수 없다.

근거와 구현은 `src/regchange/adapters/storage/base.py`(`DocumentStore`)와
`src/regchange/ingest/snapshot.py`.

#### `totalCnt`가 세는 대상

- **이력 계열의 `totalCnt`는 `<law>` 수(법령 수)이지 조문 수가 아니다.**
  `dayjochg_regdt20250401.xml`은 `totalCnt=83`, `<law>` 83건, `law/조문정보/jo`
  **286건**이다. 조문 수로 착각하면 완주 검사가 항상 실패한다.
- **본문 응답에는 `totalCnt`가 없다.** 페이지네이션 완주 검사의 대상이 아니며,
  클라이언트는 목록 응답과 본문 응답을 구조적으로 구별해야 한다.

#### 항목 요소명은 target마다 다르다

`law` 계열은 `<law>`, 행정규칙 계열은 `<admrul>`이다. **`<law>`만 세는 점검은
`search_admrul_aml.xml`을 0건으로 오판한다** — 2026-08-11 전수 점검에서 실제로
발생했다 (`docs/incidents/silent-undercounting.md` "재계산도 틀릴 수 있다").


#### XML 속성으로만 존재하는 값 — 전수 목록 (2026-08-17)

**파서는 태그 텍스트를 읽는다. 속성은 구조적으로 놓치기 쉽고 실제로 반복해서 놓쳤다.**
`scripts/analysis/scan_xml_attributes.py` 로 픽스처 33개(파싱 가능 32개) 전수를 훑었다.

계열별 요약:

| 계열 | 파일 | 요소 | 속성 종류 | 속성 총계 |
|---|---|---|---|---|
| DOCUMENT (본문 law/eflaw) | 13 | 57,055 | **7** | 2,616 |
| HISTORY (일자별 `lsJoHstInf`) | 8 | 47,708 | 2 | 5,882 |
| HISTORY (조문별 `lsJoHstInf`) | 3 | 855 | 1 | 56 |
| HISTORY (일자별 `lsHstInf`) | 1 | 73 | 1 | 5 |
| SEARCH (`law` / `eflaw` / `admrul`) | 4 | 270 | 각 1 | 15 |
| DOCUMENT (행정규칙 본문) | 1 | 253 | **0** | 0 |
| 에러 응답 (`<Law>` 루트) | 2 | 2 | **0** | 0 |

0건 둘은 재확인했다. 행정규칙 본문은 §6.1 의 기존 측정("XML 속성 0개")이 재현된 것이고
(`조문내용` 203개), `<Law>` 루트 둘은 텍스트 한 줄짜리 에러 응답이다. **0을 그대로
받아들이지 않고 먼저 의심했다** — `search_admrul_aml.xml` 을 0건으로 오판한 전례가 있다.

아니라 **"응답에 있는데 파서가 추출하지 않아서"**다. 그래서 태그 대조를 함께 한다.

##### `조문시행일자문자열` — 네 번째 누락

본문 픽스처 13개 중 **8개가 이 태그를 갖고 8개 전부 값이 있다.**

```
law_010199_mst280277.xml   문서시행일 20261217   "20251216:제42조제3항,제42조의2제1항"
law_010513_mst283193.xml   문서시행일 20260203   "20260804:제50조제1항 단서\n20270204:제166조"
law_001638_mst281875.xml   문서시행일 20260701   "20251230:제2조제35호, 제45조\n20260402:…"
```

같은 문서의 조문 단위 `<조문시행일자>` 태그는 **전부 문서 시행일자로 평탄화**되어 있다.
즉 **조문별 시행일 분기 정보가 본문 API 에 있으나 조문 단위 필드에는 없다.**
edge-case #8 의 "본문에서는 관측되지 않는다"가 부정확했다.

**원문만 보관하고 파싱하지 않는다** (`reference_raw` 와 같은 지위). 입도가 조문 단위보다
잘고(`제42조제3항`, `제10조의12제3항제8호`, `제50조제1항 단서`) 자유 텍스트라 파싱하면
ADR-007 의 `PARSED` 등급이 되는데, 그 등급의 값을 `valid_from` 에 넣을 수는 없다.

파싱하지 않아도 하나는 얻는다 — **"이 문서에 조문별 시행일 분기가 있는가"**. 이력 API 를
결합할 때 이 플래그가 켜진 문서에서 이력이 분기를 주지 않으면 그 자체가 조사 신호다.

> 어디서 얻을지는 아직 정해지지 않았다 — §8 참조.

### 4.3 항/호/목의 실제 구조

관측된 규칙 (`law_009244_mst252787.xml`, 4개 법령 전부 일관):

1. **항이 없고 호도 없는 조문**: `<항>` 태그 자체가 없고, `조문내용`에 조문 전문이 들어간다.
   예: 제1조(목적), 제8조, 제18조, 제19조. 4개 법령 합계 245건.
2. **항 번호가 붙는 조문**: `<항>`이 여러 개, 각각 `항번호`(`①`…)와 `항내용`을 갖는다.
   이때 `조문내용`은 **제목만** 담는다 — 예: `제4조의2(금융회사등의 고액 현금거래 보고)`.
3. **항 구분 없이 호만 있는 조문**: **`항번호`가 없고 `항내용`이 빈 문자열인 껍데기
   `<항>`이 하나 삽입**되고 그 아래 `<호>`가 달린다. 특금법 제2조·제16조가 이 경우.
   4개 법령 합계 51건.
4. **목은 `<호>`의 자식이 아니라 `<항>`의 자식이다.** 문서 순서상 직전 `<호>`에 귀속되며,
   XML에 귀속을 나타내는 필드는 **없다**.
   - 4개 법령 전부에서 "선행 `<호>` 없이 등장한 `<목>`" **0건** — 문서 순서로 귀속 판별이
     성립한다는 근거다. 순서를 보존하지 않는 파서(dict 변환 등)를 쓰면 귀속이 소실된다.

### 4.4 `조문이동이전` / `조문이동이후` — **실제 이동을 반영하지 않는다**

- 값은 두 가지뿐이다: 빈 문자열, 또는 `000000`.
- **`조문변경여부`와 완전히 연동한다**: `Y` ⇔ `000000`, `N` ⇔ 빈 문자열. 4개 법령
  1,189개 조문 전부 이 규칙을 벗어나지 않는다.
- 조사 범위(본문/연혁/eflaw 픽스처 13개 문서 · 고유 법령ID 8개 · 합계 **1,957개 조문단위**)에서 **`000000`이 아닌
  값 0건**.
- 그런데 조문 이동은 **실제로 일어난다**: 특금법 2011판과 2020판을 대조하면 12개 조문이
  이동했다 (`law_009244_mst113262_v20110519.xml` ↔ `law_009244_mst215971_v20200324.xml`).

  | 이동 전 | 이동 후 | 조문제목 |
  |---|---|---|
  | 0006001 | 0009001 | 외국환거래자료 등의 통보 |
  | 0007001 | 0010001 | 수사기관 등에 대한 정보 제공 |
  | 0008001 | 0011001 | 외국금융정보분석기구와의 정보 교환 등 |
  | 0009001 | 0012001 | 금융거래정보의 비밀보장 등 |
  | 0010001 | 0013001 | 자료 제공의 요청 등 |
  | **0012001** | **0014001** | 다른 법률과의 관계 ← 순서 역전 |
  | **0011001** | **0015001** | 금융회사등의 감독ㆍ검사 등 ← 순서 역전 |
  | 0013001 · 0014001 | 0016001 · 0017001 | 벌칙 (**2×2 모호** — 양쪽 모두 같은 제목 2건) |
  | 0015001 | 0018001 | 징역과 벌금의 병과 |
  | 0016001 | 0019001 | 양벌규정 |
  | 0017001 | 0020001 | 과태료 |

  고유 출발 조문키 12개 → 고유 도착 12개. 제목 기준 매칭은 벌칙 때문에 **14행**으로
  전개되며 4행이 모호하다.

  **두 버전 모두 이동 필드는 `000000`이다.** 즉 이 필드로는 이동을 알 수 없다.

### 4.5 별표·서식·이미지

- `기본정보/별표편집여부`는 항상 존재한다.
- `/법령/별표` 트리는 **법령에 따라 있고 없다**: 자본시장법에는 있고 특금법(target=law)에는
  없다.
- **같은 법령이라도 target에 따라 다르다**: 특금법은 `target=law`(`law_009244_mst252787.xml`)에
  별표 트리가 없지만 `target=eflaw`(`eflaw_009256_mst261379_ef20240326.xml`)에는 있다.
- 별표 하위 필드: `별표단위`, `별표번호`, `별표가지번호`, `별표구분`, `별표제목`,
  `별표내용`, `별표시행일자`(eflaw만), `별표이미지파일명`, `별표HWP파일명`,
  `별표PDF파일명`, `별표서식파일링크`, `별표서식PDF파일링크`, `별표서식이미지파일링크`.
- **별표 본문의 실질은 첨부파일(HWP/PDF/이미지)일 수 있다.** 텍스트 diff가 성립하지 않는
  범위가 존재한다.

### 4.6 `조문시행일자` — 조문별로 갈리지 않는다

- 본문 API(`law`, `eflaw`)의 `조문시행일자`는 **모든 조문이 문서 `시행일자`와 동일**하다.
  본문/eflaw 픽스처 13개 전부에서 종류가 1개다.
- `eflaw`도 마찬가지다: MST 261379를 efYd 20240326 / 20240627 / 20240719로 조회하면 46개
  조문이 **각각 그 efYd 하나로 평탄화**되어 나온다.
- **조문별 시행일이 실제로 갈리는 것은 일자별 조문 개정 이력 API에서만 관측된다**
  (`dayjochg_regdt20250401.xml`, §5.2).

### 4.7 조문키는 유일 식별자가 아니다

`조문여부=전문`(편장절관 제목행)은 **뒤따르는 조문의 키를 공유**한다. 한 조문 앞에 여러
계층 제목이 붙으면 같은 키가 중복된다.

- 자본시장법: `0011000`이 **3회** — "제2편 금융투자업", "제1장 금융투자업의 인가 및 등록",
  "제1절 인가요건 및 절차" (`law_010513_mst283193.xml`)
- 소득세법: `0012000`이 2회, `0014000`이 2회 (`law_001565_mst280405.xml`)

또한 **편/장/절/관의 계층은 XML 구조로 표현되지 않는다.** 모든 제목행이 `조문단위`로
평면 나열되고, 계층은 `조문내용` 텍스트(`제2편 …`, `제1장 …`, `제1절 …`, `제1관 …`)를
파싱해야만 알 수 있다.

### 5.1 `lsHstInf` — 법령 변경이력 목록

근거: `lschg_regdt20240719.xml` (regDt=20240719 → totalCnt 71)

> **표본 주의 (2026-08-11 추가).** 이 픽스처는 **totalCnt=71 중 5건만** 담긴 잘린
> 응답이며, 그 사실이 2026-08-11까지 어디에도 기록돼 있지 않았다. 아래 필드 목록은
> 그 5건에서 얻은 것이다.
>
> 필드 목록 자체는 사후 교차 검증으로 유효함을 확인했다 — 목록 응답 픽스처 5종
> (최대 581행, `dayjochg_regdt20210105.xml`)에서 **행마다 필드 집합이 달라지는 사례가
> 0건**이므로, 이 계열 API는 target별로 고정된 필드 집합을 낸다. 5건 표본이라도
> 필드 목록은 전수와 같다.
>
> 다만 **분포·어휘·집계는 이 파일로 결론짓지 않는다.** 5건은 법령명 가나다순 앞
> 5건(`가족관계…`~`검역공무원…`)이라 자모순으로 편향돼 있다.
> 경위는 `docs/incidents/silent-undercounting.md`의 "미수 1".

```
/LawSearch  target, totalCnt
  /law      법령일련번호, 현행연혁코드, 법령명한글, 법령ID, 공포일자, 공포번호,
            제개정구분명, 소관부처코드, 소관부처명, 법령구분명, 시행일자,
            자법타법여부, 법령상세링크
```

**조문 수준 정보가 없다.** "그날 무엇이 바뀐 법령인가"만 알려준다.

**`regDt`가 공포일자가 아님이 이 파일 하나로 재현된다.** 5건의 공포일자가
20240530 · 20211228 · 20240716 · 20240719 · 20210305로 제각각인데 요청은
`regDt=20240719`다. ADR-005 근거 3은 픽스처가 없는 실호출(`regDt=20260105`, 34건)을
인용하고 있었으나, **저장소 안에서 재현 가능한 근거가 이 파일에 이미 있었다.**

**같은 법령ID가 한 응답에 복수로 나타난다.** 5건 중 법령ID `006612`(검역공무원 복제
규칙)가 2회이며, 법령일련번호가 264383(현행, 공포 20240719)과 230047(연혁, 공포
20210305)로 다르다. **이 중복은 의미 있는 구분이므로 법령ID만으로 중복 제거하면
연혁이 사라진다.** 중복처럼 보이는 것이 세 종류이며 **셋 다 정상 데이터**다 —
구분표와 계열별 식별키는 edge-case #18에 있다. 진짜 중복은 35,681행에서 0건이다.

| | |
|---|---|

`시행예정`은 그 10건 중 단 1건에서만 나타난다.

**0.8단계 12개월 전수 캐시로는 확인할 수 없다.** 캐시는 `lsJoHstInf`(일자별) 응답이며,

### 5.4 `변경사유` 값 — 관측된 어휘는 6종

|---|---|

| `일괄개정` | 533 |
| `제정` | 484 |
| `본조신설` | 375 |

| `제정` | 484 | 3,809 |
| `본조신설` | 375 | 1,756 |
| `일괄개정` | 533 | 597 |
| `전부개정` | 34 | 536 |
| `폐지제정` | 19 | **0** |
| **어휘 종수** | **6종** | **5종** |

**두 집계는 모순이 아니라 서로 다른 모집단이다.** 픽스처 7일 중 6일이 캐시 창 밖이며,

교차 대조가 성립하는지 먼저 확인했다 — 두 모집단이 겹치는 유일한 날짜 `20260113`에서
픽스처와 캐시의 `(법령일련번호, 조문번호, 변경사유)` 목록이 **완전히 일치한다.**

**여기서 나오는 사실 두 가지가 클라이언트 설계에 직접 영향을 준다.**

1. **한 해 전체를 봐도 나타나지 않는 값이 존재한다.** `폐지제정`은 35,681 조문에
   0건이다. **`변경사유`를 코드에 닫힌 enum으로 고정하면 안 된다** — 미지의 값을
   만나면 파싱이 실패하거나, 더 나쁘게는 조용히 버려진다. 열린 문자열로 받고
   미지의 값을 **로그와 메타데이터에 남긴다.**
2. **희소성 판단은 모집단에 따라 뒤집힌다.** `전부개정`은 픽스처에서 34건으로
   `20210105` 하루에 몰린 희귀값처럼 보이지만, 전수에서는 536건으로
   `일괄개정`(597)과 같은 자릿수다. 픽스처 기준의 "드물다"를 운영 가정으로 옮기지
   않는다.

### 5.5 `조문변경여부`(본문) vs 변경이력 API — 무엇이 다른가

| | 본문의 `조문변경여부` | 변경이력 API |
|---|---|---|
| 알려주는 것 | **이번 버전에서 바뀐 조문인가** (Y/N) | 조문이 **역대 언제** 바뀌었는가 |
| 시간 범위 | 해당 MST 한 버전 | 제정부터 현재까지 전체 |
| 사유 구분 | 없음 | `제정`/`본조신설`/`조문변경`/`일괄개정` |
| 시행일 | 문서 시행일로 평탄화 | **조문별 시행일 제공**(일자별 API) |
| 변경 내용 | 없음 (바뀌었다는 사실만) | 없음 (바뀌었다는 사실만) |

**결론: 본문의 플래그만으로는 부족하다.** 이유 세 가지 —
(1) 조문별 시행일 분기는 일자별 API에만 있다,
(2) `본조신설`과 `조문변경`의 구분이 본문에는 없다,
(3) 본문 플래그는 한 버전에 대한 것이라 "언제부터 이 조문이 존재했는가"를 답하지 못한다.

**단, 둘 다 "무엇이 어떻게 바뀌었는가"는 주지 않는다.** 실제 텍스트 차분은 두 버전의 본문을
직접 비교해야 한다 — 원칙 1(결정론적 diff)이 필요한 이유가 여기서 실측으로 확인됐다.

근거: `admrul_2100000267264.xml` (자금세탁방지 및 공중협박자금조달금지에 관한 업무규정)

**법령과 조문 구조가 같지 않다. 전혀 다르다.**

| | 법령(`law`) | 행정규칙(`admrul`) |
|---|---|---|
| 루트 | `법령` | `AdmRulService` |
| 조문 컨테이너 | `조문/조문단위` | `조문내용` (평면 반복) |

| 항/호/목 | 태그로 분리 | **없음** — 텍스트 안에 `\n  ②`로 들어있다 |
| 조문시행일자 | 있음 | **없음** |
| 편장절관 | 별도 `조문단위`(조문여부=전문) | 같은 `조문내용` 태그를 공유 |

`조문형식여부 = 'Y'`인데도 조문 구조가 제공되지 않는다. 실제 값 예시:

```
[0]  '제1장 총칙\n'                                   ← 장 제목
[1]  '제1조(목적) 이 규정은 「특정금융거래정보의 …'      ← 조문
[4]  '제1편 금융회사등(카지노사업자 제외)\n'            ← 편 제목
[7]  '제4조(이사회의 역할 및 책임) ① 금융회사등은 … \n  ② …'  ← 항이 텍스트 안에
[61] '제45조 <삭 제>\n'                                ← 삭제 조문
```

**이 문서가 사내 규정 매핑의 핵심 대상이므로, 조문 단위 처리를 하려면 별도 파서가 필요하다.**
정본이 첨부파일(hwpx/pdf)일 가능성도 있다 — 이 응답의 `첨부파일` 2건이 그 예다.

### 6.1 식별자 부재 — 재확인 결과

"조문번호만 없는 것"과 "식별자가 아예 없는 것"은 난이도가 다르므로 원문 바이트로 전수
재확인했다. 결과는 **후자**다.

| 검사 | 결과 |
|---|---|
| `<조문내용 …>` 여는 태그 고유 형태 | `<조문내용>` **한 가지뿐** (202회 전부 속성 없음) |
| 문서 전체 XML 속성 개수 | **0개** (법령은 `조문단위@조문키`, `법령@법령키` 등 보유) |
| `조문번호` 태그 | **없음** |
| `조문키` 태그·속성 | **없음** |
| 조문 관련 식별자 | 문서 수준의 `행정규칙일련번호`, `행정규칙ID`뿐 |

즉 **조문 식별자를 API가 전혀 주지 않으며, 텍스트에서 복원하는 수밖에 없다.**

텍스트 패턴 커버리지는 전수 분류가 가능하다 (202개 전부):

| 패턴 | 건수 | 예시 |
|---|---|---|
| `^제(\d+)조(?:의(\d+))?\s*\(` — 제목 있는 조문 | 151 | `제5조의2(준법감시인등의 역할 및 책임) ① …` |
| `^제\d+[편장절관]\s` — 편/장/절/관 제목 | 48 | `제1장 총칙`, `제1편 금융회사등(카지노사업자 제외)` |
| 제목 없는 삭제 조문 | 3 | `제45조 <삭 제>`, `제49조 <삭 제>`, `제131조 <삭 제>` |

삭제 조문은 괄호 제목이 없어 첫 패턴에 걸리지 않는다. 별도 패턴이 필요하다.

### 6.2 행정규칙의 마커 어휘는 법령과 다르다

`admrul_2100000267264.xml`에서 관측된 본문 내 마커는 **`<삭 제>` 9건뿐**이다.
법령 본문에 흔한 `<개정 …>`·`<신설 …>`은 **0건**.

- `<삭 제>`는 **`삭`과 `제` 사이에 공백**이 있다. `<삭제>`로 매칭하면 놓친다.
- 조문 전체 삭제(`제45조 <삭 제>`)와 항 단위 삭제(`제24조(…) ① <삭 제>`)가 모두 있다.

### 7.1 페이지네이션

| 항목 | 활용가이드 | 실측 | 근거 |
|---|---|---|---|
| `display` 최대 | 100 | **상한 없음** — 500, 1000 모두 그대로 반환. 5000을 주면 totalCnt(4516)까지 반환 | 실측 |

| `totalCnt` | 전체 건수 | `numOfRows`는 요청한 display를 그대로 되돌려준다 | 실측 |

**가이드와 실제가 다르다. 실제를 신뢰하되 100 초과에 의존하지 않는 것이 안전하다** —
문서화되지 않은 동작은 예고 없이 바뀐다.

`display` 기본값 20 때문에 조용히 잘린다: `jochg_009244_jo000200.xml`은 `totalCnt=28`인데
20건만 담고 있다. 응답에 "잘렸다"는 표시가 없다.

### 7.2 에러 응답 — **HTTP 상태코드로 구분되지 않는다**

관측된 모든 응답이 **HTTP 200**이다. 실패는 본문 형태로만 구별된다.

| 상황 | 본문 | resultCode | 근거 픽스처 |
|---|---|---|---|
| 정상 (목록) | `<LawSearch>` + 키워드/section/page/numOfRows | `00` / `success` | `search_law_teukgeum.xml` |
| 정상 0건 (목록) | 위와 동일, `totalCnt=0` | `00` / `success` | `error_search_zero_result.xml` |
| 잘못된 MST (본문) | `<Law>일치하는 법령이 없습니다. …</Law>` | **없음** | `error_law_bad_mst.xml` |
| 잘못된 ID (행정규칙) | `<Law>일치하는 행정규칙이 없습니다. …</Law>` | **없음** | `error_admrul_wrong_id_param.xml` |
| 파라미터 부족 (이력) | `<LawSearch><target>…</target><totalCnt>0</totalCnt></LawSearch>` | **없음** | `error_dayjochg_id_only_zero.xml` |
| 미신청 target | **HTML 안내 페이지** | 해당 없음 | `error_target_lsHistory.html` |
| 알 수 없는 target | **본문 0바이트** | 해당 없음 | `error_unknown_target_empty.xml` |

`resultCode`는 **`lawSearch.do`의 정상 응답에만** 있다. 관측된 값은 `00`뿐이며, 다른 값은
확인하지 못했다 — **미확인**.

### 7.3 인코딩

XML 선언의 encoding 대소문자가 **API마다 다르다**. 실제 바이트는 모두 UTF-8이며 파싱에
문제는 없었다.

| 선언 | 해당 응답 |
|---|---|
| `encoding="UTF-8"` | lawSearch.do 전체, `target=law` 본문, 변경이력, admrul 본문 |
| `encoding="utf-8"` | `target=eflaw` 본문, lawService.do 실패 메시지 |

### 7.4 CDATA

`law_009244_mst252787.xml` 한 파일에 CDATA 블록 **1,126개**. 조문내용·항내용·호내용·목내용·
법령명이 모두 CDATA로 감싸여 있다. 본문 안의 `<개정 2020.3.24>` 같은 마커가 XML 태그로
오인되지 않는 것은 CDATA 덕분이다.
