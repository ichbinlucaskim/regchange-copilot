# 법제처 Open API — 발견된 함정

0.7단계 실측(2026-08-10)에서 확인한 것만 적는다. 각 항목은 근거 픽스처로 뒷받침된다.
**처리 방향만 적고 구현하지 않는다.** 구현은 1단계 이후다.

> **주의 — 이 문서의 "처리 방향"은 검증된 결정이 아니다.** 0.7단계 관측 직후에 쓴
> 가설이며, 그 중 둘이 실제로 틀렸다: #18의 중복 제거 지시(`valid_from`을 파괴했을
> 것), #10의 `resultCode` 기반 분류(모든 이력 응답을 실패로 만들었을 것). 각 항목의
> 정정 이력을 함께 읽어라. 원칙은 `docs/incidents/silent-undercounting.md`의
> "문서도 실패면이다".

<a id="1"></a>
## 1. OC가 응답 본문에 echo된다 — 보안

**무엇이 문제인가**
응답의 `법령상세링크`, `조문링크`, `조문변경이력상세링크` 필드가 요청 URL을 통째로 담으며,
거기에 `OC=<발급값>`이 그대로 들어 있다.

**관측 사례**
`search_law_teukgeum.xml`, `dayjochg_regdt20250401.xml`, `jochg_009244_jo000502.xml` —
모두 해당 필드에 `OC=***`(마스킹 후)가 남아 있다.

**처리하지 않으면 무엇이 깨지는가**
응답을 로그·캐시·픽스처·감사 레코드에 그대로 저장하면 자격증명이 그 모든 곳에 복제된다.
`audit` 패키지는 판단 근거로 원문 스냅샷을 남기므로 특히 위험하다.

**처리 방향**
수집 경계(`ingest`)에서 **저장·로깅 이전에** 마스킹한다. 마스킹 실패 시 저장을 거부한다
(`scripts/exploration/fetch.py`가 이미 그렇게 동작한다). 저장소에 OC가 남지 않는지
검사하는 테스트를 둔다.

<a id="2"></a>
## 2. 조문키가 유일 식별자가 아니다

**무엇이 문제인가**
`조문여부=전문`인 편장절관 제목행은 뒤따르는 조문의 키를 공유한다. 한 조문 앞에 여러 계층
제목이 붙으면 같은 `조문키`가 여러 행에 중복된다.

**관측 사례**
`law_010513_mst283193.xml`(자본시장법): `0011000`이 3회 — "제2편 금융투자업",
"제1장 금융투자업의 인가 및 등록", "제1절 인가요건 및 절차".
`law_001565_mst280405.xml`(소득세법): `0012000` 2회, `0014000` 2회.

**처리하지 않으면 무엇이 깨지는가**
`조문키`를 PK로 잡으면 적재가 실패하거나, upsert면 제목행이 서로를 덮어써 계층 정보가
사라진다. 인용 대상 문단 ID가 조문키에서 파생되면 **인용이 가리키는 대상이 모호해진다** —
원칙 2의 전제가 무너진다.

**처리 방향**
조문 본체(유형 자리 `1`)와 제목행(`0`)을 다른 종류의 레코드로 취급한다. 식별자는
`(법령ID, MST, 조문키, 문서 내 순번)` 조합으로 잡는 것을 검토한다. 조문키 단독을 PK로
쓰지 않는다.

<a id="3"></a>
## 3. `조문이동이전`/`조문이동이후`가 실제 이동을 반영하지 않는다

**무엇이 문제인가**
필드 이름은 조문 이동을 알려줄 것처럼 보이지만, 값은 빈 문자열 또는 `000000` 두 가지뿐이고
`조문변경여부`와 완전히 연동한다(`Y`⇔`000000`, `N`⇔`''`). 이동 정보가 아니다.

**관측 사례**
- 조사 범위 13개 문서 · 고유 법령ID 8개 · 1,957개 조문단위에서 `000000`이 아닌 값 **0건**.
- 그런데 이동은 실제로 있었다: `law_009244_mst113262_v20110519.xml`(2011판)과
  `law_009244_mst215971_v20200324.xml`(2020판)을 대조하면 12개 조문이 이동했다
  (제6조→제9조, 제7조→제10조, …). 고유 출발 조문키 12개 → 고유 도착 12개.
  **두 버전 모두 이동 필드는 `000000`이다.** 상세 표는 spec §4.4.
- 변경이력 API의 `변경사유`도 이동을 표기하지 않는다. 픽스처 전수 **4,853건**에서 어휘는
  `조문변경`/`일괄개정`/`제정`/`본조신설`/`전부개정`/`폐지제정` **6종**이며, 이동을
  가리키는 값은 없다 (spec §5.4).

**처리하지 않으면 무엇이 깨지는가**
이 필드를 믿으면 RENUMBERED를 영원히 감지하지 못한다. 이동한 조문은 "삭제 + 신설"로
보고되고, 사내 규정과의 매핑이 끊어진다. 담당자는 멀쩡한 조문이 사라졌다는 잘못된 알림을
받는다.

**정정 (1단계)**
`조문참고자료` 필드에 이동이 **텍스트로 명시**되어 있음이 확인됐다 —
`[제6조에서 이동, 종전 제9조는 제12조로 이동 <2020.3.24>]` 형태로 픽스처 7개 법령에
대괄호 92건, 구조화 시 `MoveReference` 128건. 아래 "추론해야 한다"는 서술은
**명시 표기가 없을 때의 fallback**으로 범위가 좁아졌다. 근거 변경 경위는 ADR-003의
"근거 정정 이력", 집계 오류 경위는 `docs/incidents/silent-undercounting.md`.

**처리 방향**
명시 표기가 없으면 **두 버전의 조문 집합을 직접 대조해 추론**해야 한다. 제목 일치는 출발점이지만
모호성이 있다 — 제목 `벌칙`이 **양쪽 버전 모두 2건씩** 있어 2×2 후보가 생기고,
제목 기준 매칭이 12행이 아니라 **14행**으로 전개된다. 또한 순서도 보존되지 않는다:
2011년 제11조(감독·검사)→2020년 제15조, 2011년 제12조(다른 법률과의 관계)→2020년
제14조로 **상대 순서가 역전**됐다. 판정 규칙은 ADR-003에 기록했다.

<a id="4"></a>
## 4. 목(가.나.다.)이 호(1.2.3.) 안에 중첩되지 않는다

**무엇이 문제인가**
XML 상 `<목>`은 `<호>`의 자식이 아니라 `<항>`의 자식이다. 어느 호에 속하는지를 나타내는
필드가 **없다**. 문서 순서가 유일한 단서다.

**관측 사례**
`law_009244_mst252787.xml` 제2조: `호 1.` → `목 가.`~`거.` → `호 2.` → `목 가.`~`라.` →
`호 3.` → `호 4.` → `목 가.`~`다.`
경로 통계상 `/조문단위/항/호`와 `/조문단위/항/목`이 형제다.

**보강 근거**
4개 법령 전부에서 "선행 `<호>` 없이 등장한 `<목>`" **0건**. 문서 순서 기반 귀속이
성립한다는 실측 근거다.

**처리하지 않으면 무엇이 깨지는가**
인용 경로가 뒤섞인다. "제2조제1호가목"이어야 할 인용이 "제2조가목"이 되거나 엉뚱한 호에
붙는다. 인용 검증(원칙 2)은 **문단 ID의 존재만 확인**하므로, 경로가 잘못 조립돼도
검증을 통과한다. 이 함정은 검증 장치를 우회한다.

**처리 방향**
파서는 순서를 보존하는 자료구조로 읽고, `<목>`을 직전 `<호>`에 귀속시킨다. 순서를 잃는
변환(dict 키 기반 등)을 쓰지 않는다. 선행 호 없이 목이 나오면 예외로 처리해 파서 버그를
드러낸다.

<a id="5"></a>
## 5. `조문내용`의 의미가 조건부로 달라진다

**무엇이 문제인가**
같은 태그가 두 가지 다른 것을 담는다.
- `<항>`이 없는 조문: `조문내용`에 **조문 전문**이 들어간다.
- `<항>`이 있는 조문: `조문내용`에 **제목 줄만** 들어간다.

**관측 사례**
`law_009244_mst252787.xml`
- 제1조: `'제1조(목적) 이 법은 금융거래 등을 이용한 자금세탁행위와 … 목적으로 한다. <개정 2020.3.24>'`
- 제4조의2: `'제4조의2(금융회사등의 고액 현금거래 보고)'` — 본문은 `항내용`에 있다.

항 태그 없는 조문은 4개 법령 합계 245건.

**처리하지 않으면 무엇이 깨지는가**
`조문내용`만 인덱싱하면 다항 조문의 본문이 통째로 검색에서 빠진다. 조문 전체가 제목만 남아
"영향 없음"으로 잘못 판정된다. 반대로 전문을 담은 조문은 중복 적재된다.

**처리 방향**
조문 본문 텍스트를 **`<항>` 존재 여부로 분기해** 조립한다. 조립 규칙을 한 곳에 두고,
두 경우 모두를 픽스처 기반 테스트로 고정한다.

<a id="6"></a>
## 6. 번호 접두어가 내용에 중복 포함된다

**무엇이 문제인가**
`호번호 = '1.'`이면서 `호내용 = '1. "금융회사등"이란 …'`이다. 번호가 두 번 나온다.
항·목도 동일하다.

**관측 사례**
`law_009244_mst252787.xml` 제2조 — `호번호='1.'` / `호내용='1. "금융회사등"이란 다음 각 목의 자를 말한다.'`,
`목번호='가.'` / `목내용='가. 「한국산업은행법」에 따른 한국산업은행'`.

**처리하지 않으면 무엇이 깨지는가**
정규화 기준이 없으면 diff가 흔들린다. 번호가 바뀌었을 뿐인 조문이 "내용 변경"으로 잡히고,
반대로 접두어를 제거하는 쪽과 남기는 쪽이 섞이면 같은 문단의 해시가 달라진다.
검색 인덱스에도 번호가 토큰으로 섞여 들어간다.

**처리 방향**
정규화 기준을 **하나로 정하고 문서화**한다. 후보는 (a) 접두어 제거 후 저장, (b) 원문 보존
+ 비교 시에만 제거.

> **결정됨 — ADR-002 (2026-08-11).** (b)를 택했다. 원문(`text_raw`)과 정규화본
> (`text_norm`)을 **둘 다 저장**하고, 인용과 화면 표시는 항상 원문을 가리킨다.
> 정규화 규칙은 `norm-v1`이며 `norm_rule_version`으로 버전을 남긴다.
> **이 항목의 "미결정" 표기는 2026-08-12까지 갱신되지 않았다** — 아래 §결정 완료 참조.

<a id="7"></a>
## 7. 본문 텍스트 안에 개정 마커가 들어 있다

**무엇이 문제인가**
`<개정 2020.3.24>`, `<신설 2020.3.24>` 같은 마커가 조문·항·호 내용 텍스트 안에 그대로
포함된다. CDATA 안이라 XML 태그로 파싱되지는 않는다.

**관측 사례**
전체 법령 픽스처에서 `<개정 …>` **2,331회**, `<신설 …>` **443회**.
`law_009244_mst252787.xml` 제1조 끝에 `<개정 2020.3.24>`.

**처리하지 않으면 무엇이 깨지는가**
법령이 개정되면 실질 내용이 그대로여도 마커의 날짜가 바뀐다. diff가 **모든 조문을 변경으로
보고**한다. 담당자는 수백 건의 가짜 알림을 받고, 그 다음부터 알림을 보지 않게 된다.

**처리 방향**
비교용 정규화 단계에서 마커를 분리한다. 다만 **마커 자체가 정보**이기도 하다(그 조문이
언제 개정됐는지). 원문에서 제거하지 말고 별도 필드로 추출한다.

> **결정됨 — ADR-002 (2026-08-11).** 마커는 `amendment_markers`(jsonb)로 추출해
> 보관하고 **원문에서는 제거하지 않는다.** `text_norm`에서만 분리한다.
> 이 항목의 "미결정" 표기도 갱신되지 않았다 (§6과 같은 경위).

<a id="8"></a>
## 8. 조문 수준 시행일이 본문 API에서 평탄화된다

**무엇이 문제인가**
`조문시행일자` 태그는 조문마다 있지만, 본문 API(`law`, `eflaw`)에서는 **모든 조문이 문서
`시행일자`와 같은 값**을 갖는다. 조문별 시행일 분기는 본문에서 관측되지 않는다.

**관측 사례**
- 본문/eflaw 픽스처 13개 전부: `조문시행일자` 종류가 1개.
- `eflaw_009256_mst261379_ef20240326.xml` / `..._ef20240627.xml` / `..._ef20240719.xml`:
  같은 MST를 efYd 3개로 조회하면 46개 조문이 각각 그 efYd 하나로 평탄화된다.
- 그런데 실제 분기는 존재한다: `dayjochg_regdt20250401.xml`에서 83개 법령 중 **17개**가
  문서 시행일자 ≠ 조문시행일. 아동복지법은 한 공포에 시행일이 3종(20250401, 20251002,
  20260402)이다.

**처리하지 않으면 무엇이 깨지는가**
본문 API만 쓰면 "이 조문이 언제부터 효력이 있었는가"를 문서 수준으로 뭉갠다.
bitemporal 모델의 `valid_time`이 틀리고, **"그 시점에 담당자가 알 수 있었던 정보"를
재구성하면 잘못된 답이 나온다** — 원칙 6이 무력해진다.

**처리 방향**
`valid_time`은 본문 API가 아니라 **일자별 조문 개정 이력 API(`lsJoHstInf` on
lawSearch.do)의 `조문시행일`**에서 가져온다. 두 소스를 결합하는 수집 절차가 필요하다.

> **정정 (2026-08-17, XML 속성 전수 점검) — "본문에서 관측되지 않는다"가 부정확했다.**
>
> 조문 단위 `<조문시행일자>` 태그가 문서 시행일자로 평탄화된다는 서술은 **맞다.**
> 그러나 분기 정보 자체는 본문 API에 있다 — `<기본정보>`의 **`<조문시행일자문자열>`**에
> 요약 문자열로 담긴다. 본문 픽스처 13개 중 **8개가 이 필드를 가지며 8개 전부 값이 있다.**
>
> ```
> law_010199_mst280277.xml   문서시행일 20261217   "20251216:제42조제3항,제42조의2제1항"
> law_010513_mst283193.xml   문서시행일 20260203   "20260804:제50조제1항 단서 / 20270204:제166조"
> ```
>
> 같은 문서의 조문 단위 태그는 전부 `2026-12-17` 하나로 평탄화되어 있다.
>
> **그럼에도 `valid_from`을 여기서 가져오지 않는다.** 입도가 조문 단위보다 잘고
> (`제42조제3항`, `제10조의12제3항제8호`, `제50조제1항 단서`) 자유 텍스트라, 파싱하면
> ADR-007의 `PARSED` 등급이 된다. 그 등급의 값을 bitemporal의 핵심 축에 넣을 수 없다.
> **원문만 보관한다** (`regulation_document.article_effective_dates_raw`).
>
> 파싱하지 않아도 하나는 얻는다 — **"이 문서에 조문별 시행일 분기가 있는가."**
> 이력 API를 결합할 때 이 플래그가 켜진 문서에서 이력이 분기를 주지 않으면
> 그 자체가 조사 신호다. 상세: spec §2.1, `docs/incidents/silent-undercounting.md`.

## 9. 편/장/절/관 계층이 텍스트로만 표현된다

**무엇이 문제인가**
모든 제목행이 `조문단위`로 평면 나열되고, 계층은 `조문내용` 문자열(`제2편 …`, `제1장 …`,
`제1절 …`, `제1관 …`)을 파싱해야만 알 수 있다. XML 구조에는 중첩이 없다.

**관측 사례**
`law_010513_mst283193.xml`: `'제1편 총칙'`, `'제2편 금융투자업'`, `'제1장 금융투자업의 인가 및 등록'`,
`'제1절 인가요건 및 절차'` — 전부 같은 깊이의 `조문단위`.
`law_001565_mst280405.xml`: `'제1관 세액계산 통칙'`까지 4계층.

**처리하지 않으면 무엇이 깨지는가**
인용에 "제3편 제2장 제1절 제○조" 같은 맥락을 붙일 수 없다. 담당자가 인용을 검증하려면
법령 원문에서 위치를 스스로 찾아야 하고, 검증 비용이 올라가면 승인이 형식화된다(원칙 4의
실효성 문제).

**처리 방향**
제목행 텍스트에서 계층 종류(편/장/절/관)와 번호를 추출해 스택으로 계층을 재구성한다.
추출 실패는 조용히 넘기지 않고 오류로 올린다.

<a id="10"></a>
## 10. 에러가 HTTP 상태코드로 구분되지 않는다

**무엇이 문제인가**
관측된 모든 응답이 **HTTP 200**이다. 실패는 본문 형태로만 구별되며, 형태가 6가지다.

**관측 사례**

| 상황 | 본문 | 픽스처 |
|---|---|---|
| 정상 0건 | `resultCode=00` 포함 XML | `error_search_zero_result.xml` |
| 잘못된 MST | `<Law>일치하는 법령이 없습니다…</Law>`, resultCode 없음 | `error_law_bad_mst.xml` |
| 잘못된 행정규칙 ID | `<Law>일치하는 행정규칙이 없습니다…</Law>` | `error_admrul_wrong_id_param.xml` |
| 파라미터 부족 | `<LawSearch><target/><totalCnt>0</totalCnt></LawSearch>` — **정상 0건과 바이트 단위로 동일하다. 구별 불가능** | `error_dayjochg_id_only_zero.xml` |
| 미신청 target | **HTML 안내 페이지** | `error_target_lsHistory.html` |
| 알 수 없는 target | **본문 0바이트** | `error_unknown_target_empty.xml` |

**처리하지 않으면 무엇이 깨지는가**
`response.raise_for_status()`는 아무것도 잡지 못한다. 파라미터 오류가 "0건"으로 읽히면
**수집 실패가 '개정 없음'으로 위장**한다. 조용한 실패는 규제 도메인에서 오답보다 나쁘다
(CLAUDE.md §4). HTML 응답을 XML 파서에 넣으면 그때서야 엉뚱한 예외가 난다.

**처리 방향** (2026-08-12 정정)

> **정정 이력.** 이전 판은 분류축에 **"`resultCode` 없는 XML"을 실패로** 두었다.
> **그 지시를 그대로 구현하면 모든 이력 응답이 실패로 분류된다** — §2.1에서 확인된
> 대로 이력 계열(`lsHstInf`, `lsJoHstInf` 양쪽)은 **정상 응답에도 `resultCode`가
> 없다.** `resultCode`가 있는 것은 검색 계열뿐이다.
>
> 그리고 더 위험한 것은 그 다음이다 — "전부 실패"에 부딪힌 사람이 검사를 완화하는
> 가장 자연스러운 방법은 **"`resultCode` 없음을 정상으로 취급"**이고, 그러면
> R-11(정상 0건과 실패의 구별 불가)이 그대로 되살아난다.
>
> ADR-005가 이 문제를 부분적으로 잡아 두었으나("edge-case #10의 `resultCode` 기반
> 분류를 이 API에는 적용할 수 없다"), **이 항목 자체는 정정되지 않은 채 남아 있었다.**
> 응답 분류를 구현하려는 사람이 먼저 읽는 문서가 이것이다.
> 경위는 `docs/incidents/silent-undercounting.md`의 "문서도 실패면이다".

수집 경계에서 응답을 **형태로 분류**한다. **분기 기준은 target이 아니라 계열이다**
(§2.1). 순서는 싼 검사부터, 그리고 더 구체적인 진단부터다.

```
1. 빈 본문 (0바이트)          → EMPTY_BODY
2. HTML 표지                  → HTML
3. XML 파싱 실패              → PARSE_ERROR
4. 루트가 <Law>               → LAW_MESSAGE   (루트 대조보다 먼저 — 더 구체적)
5. 루트 태그 ≠ §2.1 기대값     → ROOT_MISMATCH
6. echo된 <target> ≠ 요청 target → ROOT_MISMATCH  (루트 대조만으로는 부족하다)
7. 계열 필수 구조 결여
     검색·이력: totalCnt 없음/비정수 → PARSE_ERROR
     본문: totalCnt 자체가 없는 것이 정상
8. 그 외                      → OK
```

`resultCode`는 **분류에 쓰지 않는다.** 계열에 따라 있고 없으므로 성공/실패의 신호가
될 수 없다.

**정상 외 전부를 실패로 취급하고, 0건과 실패를 절대 같은 값으로 표현하지 않는다**
(`retrieval` 패키지 docstring의 원칙과 같다). 실패를 `None`이나 빈 리스트로 반환하면
호출자가 0건과 섞으므로, **성공과 실패를 다른 타입으로 반환한다.**

**그럼에도 이력 계열의 0건은 이 분류로 가릴 수 없다** — 아래 표의 "파라미터 부족" 행
참조. 그 방어는 카나리아와 0건 재요청이 담당한다 (ADR-005 R-11).

<a id="11"></a>
## 11. `display` 기본값 20으로 조용히 잘린다

**무엇이 문제인가**
목록 조회의 `display` 기본값은 20이고, 잘렸다는 표시가 응답에 없다. `totalCnt`와
실제 반환 건수를 직접 비교해야만 알 수 있다.

**관측 사례**
`jochg_009244_jo000200.xml`: `totalCnt=28`인데 `<law>` 20건.
같은 조회에 `display=100`을 준 `jochg_009244_jo000200_full.xml`은 28건 전부.

**처리하지 않으면 무엇이 깨지는가**
조문 변경 이력의 뒷부분(오래된 이력)이 잘려 나간다. "이 조문이 언제 신설됐는가"를
물으면 잘못된 답이 나온다.

**처리 방향**
목록 조회는 **`totalCnt`와 누적 수신 건수를 비교해 전부 받을 때까지 페이지를 넘긴다.**
불일치 상태로 끝나면 실패로 처리한다. 활용가이드는 `display` 최대 100이라 하지만 실측은
1000도 반환한다 — 문서화되지 않은 동작에 의존하지 않고 페이지네이션을 구현한다.

<a id="12"></a>
## 12. 행정규칙에는 조문 구조가 없다 — 아키텍처 영향

**무엇이 문제인가**
`target=admrul` 본문은 법령과 완전히 다른 스키마다. 조문키·조문번호·항/호/목 태그가
**전부 없고**, `<조문내용>` 문자열이 평면으로 나열된다. 장/절/편 제목과 조문이 같은 태그를
공유한다. `조문형식여부='Y'`인데도 그렇다.

**관측 사례**
`admrul_2100000267264.xml` — 자금세탁방지 및 공중협박자금조달금지에 관한 업무규정,
금융정보분석원 고시. `<조문내용>` 202개, XML 속성 0개.
```
[0]  '제1장 총칙\n'
[7]  '제4조(이사회의 역할 및 책임) ① 금융회사등은 … \n  ② …'   ← 항이 텍스트 안에
[61] '제45조 <삭 제>\n'
```
첨부파일 2건(hwpx, pdf)이 함께 제공된다.

**처리하지 않으면 무엇이 깨지는가**
이 규정은 사내 내부통제 규정과 가장 직접적으로 대응하는 문서다. 법령용 파서를 그대로 쓰면
조문 0건으로 읽히거나, 장 제목을 조문으로 오인해 인용이 엉뚱한 곳을 가리킨다.
**원칙 1(조문 단위 결정론적 diff)의 전제가 이 문서에는 성립하지 않는다.**

**재확인 결과 — 식별자가 아예 없다 (조문번호조차 없다)**
원문 바이트 전수 검사: `<조문내용 …>` 여는 태그의 고유 형태는 `<조문내용>` **한 가지뿐**
이고, **문서 전체의 XML 속성이 0개**다. `조문번호`·`조문키` 태그도 없다. 조문 식별자는
`조문내용` 텍스트의 `제N조(…)` 접두어에서 복원하는 것 외에 방법이 없다.
(법령은 `<조문단위 조문키="0008001">`처럼 속성으로 준다.)

텍스트 패턴으로는 202개 전부 분류된다: 제목 있는 조문 151, 편장절관 제목 48,
제목 없는 삭제 조문 3(`제45조 <삭 제>` — 괄호 제목이 없어 별도 패턴 필요).

**결정 — 1단계 범위에서 제외하되 "연기가 아니라 예약"으로 다룬다**
법령에는 정답이 있고 행정규칙에는 없다. 법령 XML은 `조문키`·`조문가지번호`·
`조문변경여부`를 주므로 파서가 맞는지 기계적으로 채점된다. 행정규칙 텍스트 파서는 채점
기준이 없어, 동시에 만들면 **"틀렸는지 알 수 없는 파서"가 두 개** 생긴다. 또한 법령 파서가
조/항/호/목 트리와 `article_path` 구조를 확정해야 행정규칙 파서의 과제가 "그 구조를
텍스트에서 복원하라"로 명확해진다.

- **착수 조건**: 법령 파서의 `조문변경여부` 기준 일치율 ≥ 0.95. 로드맵에 3주차 착수로
  명시한다. AML의 실질 의무는 법률이 아니라 업무규정에 있고 사내 정책과 직결되므로,
  빠지면 시스템 가치의 상당 부분이 사라진다 — 무기한 연기가 아니다.
- **정답지를 지금 확보한다**: 법령 XML에서 `조문내용`만 뽑아 이어 붙이면 행정규칙과 같은
  평문 형태가 되고, **원래 트리는 이미 알고 있으므로 그것이 정답지가 된다.** 가지번호
  (제5조의2), 장 제목, 부칙 경계 같은 어려운 케이스도 법령 쪽에서 정답을 가져올 수 있다.
  이로써 텍스트 파서가 착수 시점부터 검증 가능한 상태로 시작한다. 평가 체계에 지표가
  하나 더 생긴다 (`evals/README.md` 참조).
- 텍스트 파싱이므로 법령 파서와 달리 **신뢰도가 낮다는 점을 시스템이 인지해야 한다.**
  첨부파일(hwpx/pdf)이 정본인지도 확인이 필요하다 — **미확인**.

<a id="13"></a>
## 13. 행정규칙 `ID` 파라미터가 직관과 반대다

**무엇이 문제인가**
본문 조회의 `ID` 파라미터는 `행정규칙ID`가 아니라 **`행정규칙일련번호`**를 받는다.
잘못 넣으면 "행정규칙명을 확인하여 주십시오"라는, 원인과 무관한 메시지가 온다.

**관측 사례**
AML 업무규정: `행정규칙ID=2037208`, `행정규칙일련번호=2100000267264`.
`ID=2037208` → 실패 (`error_admrul_wrong_id_param.xml`).
`ID=2100000267264` → 성공 (`admrul_2100000267264.xml`).
검색 응답의 `행정규칙상세링크`가 정답을 담고 있다: `target=admrul&ID=2100000267264`.

**처리하지 않으면 무엇이 깨지는가**
행정규칙 수집이 통째로 실패하는데, 메시지가 "규칙명을 확인하라"고 하므로 원인 규명에
시간이 걸린다.

**처리 방향**
식별자를 직접 조립하지 말고 **검색 응답의 `행정규칙상세링크`에서 파라미터를 그대로
가져온다.** 두 식별자를 다른 타입으로 구분해 혼동을 타입 수준에서 막는 것을 검토한다.

<a id="14"></a>
## 14. 별표가 target에 따라 있고 없다

**무엇이 문제인가**
같은 법령이라도 `target=law`에는 별표 트리가 없고 `target=eflaw`에는 있다.
별표 본문의 실질이 첨부파일(HWP/PDF/이미지)인 경우도 있다.

**관측 사례**
특금법: `law_009244_mst252787.xml`에는 `별표편집여부`만 있고 `/법령/별표` 트리가 없다.
같은 법령의 `eflaw_009256_mst261379_ef20240326.xml`에는 `별표단위`, `별표번호`,
`별표시행일자`, `별표HWP파일명`, `별표PDF파일명`, `별표이미지파일명` 등이 있다.
자본시장법(`law_010513_mst283193.xml`)은 `target=law`에도 별표가 있다.

**처리하지 않으면 무엇이 깨지는가**
별표에 규정된 의무(보고 서식, 기준 금액표 등)를 놓친다. target을 바꾼 뒤 별표가
"사라졌다"고 오판해 삭제로 처리할 수 있다.

**처리 방향**
별표는 조문과 다른 종류의 레코드로 다룬다. 첨부파일 기반 별표는 **텍스트 diff 대상이
아님을 명시**하고, 파일 해시 변경 정도만 감지하는 방향을 검토한다. 어느 target에서
수집할지 고정한다.

## 15. XML 인코딩 선언 대소문자가 API마다 다르다

**무엇이 문제인가**
`encoding="UTF-8"`과 `encoding="utf-8"`이 섞여 나온다. 실제 바이트는 모두 UTF-8이다.

**관측 사례**
대문자: `law_009244_mst252787.xml`, `search_law_teukgeum.xml`, `dayjochg_regdt20250401.xml`,
`admrul_2100000267264.xml`.
소문자: `eflaw_009256_mst261379_ef20240326.xml`, `error_law_bad_mst.xml`.

**처리하지 않으면 무엇이 깨지는가**
인코딩 선언 문자열을 그대로 비교하는 코드나, 선언을 기준으로 분기하는 캐시 키가 있으면
같은 내용이 다른 것으로 취급된다. 현재까지 파싱 실패는 없었다.

**처리 방향**
선언을 신뢰하지 말고 UTF-8로 고정 해석한다. 선언 문자열을 로직에 쓰지 않는다.

<a id="16"></a>
## 16. CDATA가 광범위하게 쓰인다

**무엇이 문제인가**
조문내용·항내용·호내용·목내용·법령명이 모두 CDATA로 감싸여 있다.

**관측 사례**
`law_009244_mst252787.xml` 한 파일에 CDATA 블록 **1,126개**.

**처리하지 않으면 무엇이 깨지는가**
CDATA를 벗기지 않는 파서를 쓰면 본문에 `<![CDATA[`가 섞인다. 반대로 CDATA가 없었다면
본문의 `<개정 …>` 마커가 XML 태그로 오인됐을 것이다 — CDATA가 그 사고를 막고 있다.

**처리 방향**
표준 XML 파서(CDATA를 자동으로 텍스트로 처리)를 쓴다. 정규식으로 XML을 파싱하지 않는다.
`type=JSON` 응답에서는 이 보호가 없을 수 있으므로, JSON 전환 시 마커 처리를 재검증한다.

<a id="17"></a>
## 17. 목번호가 `하.` 다음 `거.`로 이어진다

**무엇이 문제인가**
목번호는 `가.`~`하.` 14개를 쓴 뒤 `거.`, `너.`, `더.`로 이어진다. 단순 자모 순서 가정이
깨진다. 그리고 다음 호에서 `가.`로 리셋되므로, **목번호만으로는 호 경계를 판별할 수 없다**
(리셋과 계속이 섞인다).

**관측 사례**
`law_009244_mst252787.xml` 제2조 제1호:
`['가.','나.','다.','라.','마.','바.','사.','아.','자.','차.','카.','타.','파.','하.','거.']`
→ 제2호에서 다시 `가.`

**처리하지 않으면 무엇이 깨지는가**
목 순서 검증이나 정렬 로직이 `거.`를 이상값으로 판단해 파싱을 중단하거나, 목번호 리셋을
호 경계 단서로 쓰면 15개 이상 목을 가진 호에서 경계를 잘못 잡는다.

**처리 방향**
목번호를 순서 판단에 쓰지 않는다. 귀속은 문서 순서로만 결정한다(§4). 한글 순서표가
필요하면 실제 관측 순서를 상수로 고정하고 근거를 남긴다.

## 18. 중복처럼 보이는 것이 세 종류인데, 셋 다 정상 데이터다

> **전면 재작성 (2026-08-12).** 이 항목의 이전 판은 제목·판정·처리 방향이 **전부
> 틀렸다.** "변경이력에 중복 레코드가 있다"로 단정하고 "적재 전 중복 제거 기준을
> 정한다"를 지시했다. **그 지시를 그대로 구현하면 조문 단위 `valid_from`이 소실된다** —
> ADR-005가 존재하는 이유를 파괴하는 지시였다.
> 경위는 `docs/incidents/silent-undercounting.md`의 "미수 2".

**무엇이 문제인가**

변경이력 응답에 같은 식별자가 두 번 이상 나타나는 것처럼 보인다. **한 가지 키로
일괄 제거하는 코드는 반드시 실제 데이터를 지운다.**

### 발견 경위 — 이 항목이 스스로 요구한 검증이 전제를 무너뜨렸다

이전 판은 "제거하기 전에 무엇이 다른지 필드 단위로 확인한다"고 스스로 요구했다.
2026-08-12에 그 확인을 실행하자 전제가 무너졌다.

`jochg_009244_jo000200_full.xml`의 3쌍은 **`조문변경일`이 다르다.**

| MST | 조문변경일 |
|---|---|
| 124054 | 20120321 / **20130322** |
| 143042 | 20131114 / **20140214** |
| 154294 | 20141129 / **20160101** |

**같은 공포(MST)가 그 조문을 두 시점에 나누어 시행한 것이다.** 이것은 ADR-005 근거 2가
"조문별 시행일 분기는 실재한다"고 적은 바로 그 현상이다 — 아동복지법은 한 공포에
시행일이 3종이다.

두 행은 `조문변경일`과 `조문링크`(그 안의 `efYd`)만 다르고 나머지는 같다.

### 세 종류

| 유형 | 키 | 실증 | 성질 |
|---|---|---|---|
| **연혁** | 같은 `법령ID`, 다른 MST | `lschg_regdt20240719.xml` 법령ID 006612 (MST 264383/230047) | **정상** |
| **시행일 버전** | 같은 MST, 다른 `조문변경일`/`시행일자` | `jochg_..._full.xml` 3쌍 / `search_eflaw_teukgeum.xml` MST 261379 × 3 | **정상** |
| 진짜 중복 | 모든 식별 필드가 동일 | **관측 0건 / 35,681행** | **미관측** |

`search_eflaw_teukgeum.xml`의 MST 261379는 3회 나타나는데 **다른 필드 15개가 전부 같고
`시행일자`만** 20240719 / 20240627 / 20240326으로 다르다.

`법령ID`는 법령 자체의 식별자이고 `법령일련번호`(MST)가 버전 식별자다 (§3.1).
특금법의 `법령ID`는 `009244`로 고정이지만 MST는 제정판 59509부터 현행 252787까지 28개다.

**같은 응답 안에 두 종류가 함께 나타날 수 있다.** `lschg_regdt20240719.xml`은 5건짜리
잘린 응답인데도 연혁을 담고 있다.

### 전수 재계산 (2026-08-12)

| 대상 | 행 | 고유 | 진짜 중복 |
|---|---|---|---|
| 조문 행 (캐시 365일) | **35,681** | 35,681 | **0** |
| 조문별 픽스처 3종 | 56 | 56 | **0** |

법령 단위로도 확인했다 — ADR-005가 인용한 "같은 날 같은 법령ID가 중복 `<law>`로 48건"은
정확히 48건으로 재현되지만, **48건 중 같은 MST가 반복된 그룹은 0개다.** 47개 그룹 전부
MST가 다르며, 하루에 같은 법령이 두 번 공포·등록된 것이다.

### 처리 방향 (교체)

**중복 제거를 하지 않는다.**

"중복"으로 보이는 것은 전부 **서로 다른 시점 정보**를 담고 있으며, 제거하면
`valid_from`이 소실된다. ADR-005가 존재하는 이유가 조문 단위 `valid_from`을 정확히
기록하는 것이므로, 이 제거는 시스템의 목적을 파괴한다.

식별키로 적재하고, **키 충돌이 발생하면 조용히 덮어쓰지 않고 실패로 처리한다.**

### 식별키는 계열마다 다르다

하나의 보편 키를 만들려 하면 어느 한쪽에서 필드가 없어 무너진다 — §2.1의 계열별 분기
원칙과 같은 이야기다.

```
일자별 이력 (lawSearch.do, lsJoHstInf)
  키: (법령일련번호, 조문번호, 조문시행일)
  근거: 캐시 365일 35,681행에서 충돌 0건
        (법령일련번호, 조문번호)만으로는 439건 충돌
        법령일련번호 제외 시 249건 충돌
        → 법령ID·조문개정일·변경사유는 식별에 기여하지 않는다
          (조문개정일은 파일 안에서 상수 = 요청한 regDt)

조문별 이력 (lawService.do, lsJoHstInf)
  키: (법령일련번호, 조문번호, 조문변경일)
  근거: 위 3쌍이 조문변경일로 갈린다. 픽스처 3종 56행 충돌 0건
```

**두 계열이 다른 필드를 쓴다.** 일자별은 `조문시행일`, 조문별은 `조문변경일`이다.
§2.1대로 두 계열의 조문 스키마가 애초에 다르다 — 일자별 `<jo>`에는
`조문개정일`·`조문시행일`이 있고, 조문별 `<조문정보>`에는 `조문변경일`이 있다.

### 남은 미확인

**진짜 중복이 존재하는지는 여전히 미확인이다.** 35,681행에서 0건이지만
**큰 표본에 없다는 것이 없다는 뜻이 아니다** — §5.4의 `폐지제정`이 전수 35,681조문에
0건인데 픽스처 4,853조문에는 19건이었다.

→ 그래서 "충돌 0건이므로 안전하다"가 아니라 **"충돌 0건이지만 런타임 단언으로
감시한다"**로 둔다. 충돌 시 두 행의 전체 필드를 로그에 남긴다.
**이 단언이 발화하는 날이 곧 키를 다시 검토할 날이다.**

## 19. 검색이 예상 밖의 법령을 반환한다

**무엇이 문제인가**
법령명 검색이 단순 일치가 아니며, 질의와 무관해 보이는 결과가 섞인다.

**관측 사례**
- `query=특정 금융거래정보` → 법률과 **시행령**이 함께 반환(`search_law_teukgeum.xml`).
- `query=민법` → **난민법**, 난민법 시행령, 난민법 시행규칙 반환.
- `query=상법` → **1980년해직공무원의보상등에관한특별조치법** 반환.
- `query=자금세탁방지`(admrul) → **우체국금융** 자금세탁방지 업무규정이 섞임
  (`search_admrul_aml.xml`). `org=1160100` 필터로 제거된다.

**처리하지 않으면 무엇이 깨지는가**
감시 대상 법령을 이름으로 조회하면 엉뚱한 법령을 수집한다. 그 법령의 개정이 사내 규정
영향으로 보고되어, 담당자가 무관한 알림을 받는다.

**처리 방향**
감시 대상은 **이름이 아니라 `법령ID`로 고정**한다. 이름 검색은 최초 등록 시 사람이 확인하는
용도로만 쓴다. 행정규칙은 `org` 필터를 함께 건다.

## 20. 본문 응답에 MST가 없고, 소관부처코드는 XML 속성이다

> **2026-08-16 적재 구현 중 추가.** 관측이 문서에 없던 사실이며, 이전 판이 틀린 것은
> 아니다 (`silent-undercounting.md` "미수를 세는 기준").

**무엇이 문제인가**

본문(`law`/`eflaw`) 응답을 적재할 때 필요한 두 값이 **기대한 자리에 없다.**

| 값 | 어디에 없는가 | 어디에 있는가 |
|---|---|---|
| `법령일련번호`(MST) | 응답 본문 어디에도 없다 — 픽스처 13개 전부 **0건** | 요청 파라미터 (`LAW_DOCUMENT.required_params = {"MST"}`) |
| 소관부처코드 | `<소관부처>`의 자식 태그가 아니다 | `<소관부처 소관부처코드="1160100">`의 **XML 속성** |

루트 속성 `<법령 법령키="0092442023071819563">`은 MST가 아니다 —
`법령ID(009244) + 공포일자(20230718) + 공포번호(19563)`로 보이며, MST(252787)와 다르다.

**처리하지 않으면 무엇이 깨지는가**

- **MST**: 버전 식별자가 없으면 문서 유니크 키가 무너진다. `(법령ID, 시행일자)`로 대신하면
  같은 날 두 번 공포된 건(#18 "연혁", 12개월 48건)을 구별하지 못한다. 급하게 `법령키`를
  잘라 쓰면 그 구성 규칙이 미확인인 채로 식별자가 된다.
- **소관부처코드**: 태그만 순회하는 파서는 이 값을 통째로 놓치고 `None`이 된다. 그러면
  부처 해결이 **이름**으로 넘어가는데, 이름은 조인 키가 아니다(ADR-009). 값이 비는 것이
  아니라 **다른 키로 조용히 이동한다.**

`<조문단위 조문키="...">`가 속성이라 파서가 놓쳤던 것(#2, ADR-001)과 **같은 함정이 다른
필드에서 반복됐다.** "속성인지 태그인지"를 필드마다 확인해야 한다.

**처리 방향**

- MST는 **스냅샷 매니페스트의 `params`에서** 가져온다. 요청이 유일한 출처이며, 매니페스트가
  그 요청을 이미 기록하고 있다. `법령키`에서 잘라 쓰지 않는다 — 조문키는 재구성해 원본과
  대조한 뒤에야 규칙을 확정했고(1,189조문 불일치 0건), 같은 절차 없이 자르지 않는다.
- 소관부처코드는 `LawDocument.ministry_code`로 파서가 속성에서 읽는다. 본문 픽스처
  13개 전부에서 관측된다.

## 21. 이동 표기는 이 버전의 변경이 아니라 이력 누적이다

> **2026-08-17 작업 4(diff) 측정 중 추가.** 문서에 없던 사실이며, 이전 판이 틀린 것은
> 아니다. 상세는 `docs/api-exploration/diff-measurements.md`.

**무엇이 문제인가**

`조문참고자료`의 이동 표기는 그 조문이 **지금까지 겪은 이동 전부**를 누적한다.
"이번 개정에서 이동했다"가 아니다.

```
이동 표기 128건 중 문서 시행 연도와 같은 해:   0건
                    다른 해(과거 개정 이력):  128건
```

**관측 사례**

| 픽스처 | 문서 시행일 | 표기에 담긴 이동 날짜 |
|---|---|---|
| `law_001586_mst280373_tax.xml` | 2026-01-01 | 2006-12-30 · 2010-01-01 · 2018-12-31 · 2022-12-31 |
| `eflaw_009256_mst261379_ef20240326.xml` | 2024-03-26 | 2008-11-11 · 2015-12-30 · 2021-03-23 |
| `law_009244_mst252787.xml` | 2024-07-19 | 2020-03-24 |

**처리하지 않으면 무엇이 깨지는가**

표기를 그대로 diff 결과로 쓰면 **2008년 이동이 오늘의 이동 후보로 검토 큐에 올라간다.**
소득세법 한 문서만으로 4개 시점이 섞인다. 같은 이동이 버전을 비교할 때마다 반복해서
후보로 나오므로, 검토자는 이미 처리한 이동을 계속 다시 본다 — 이동 축에서의 R-14이며
ADR-003의 "승인이 형식화된다"(신호 2)로 직결된다.

**처리 방향**

`from.공포일자 < 이동날짜 <= to.공포일자` 인 표기만 이번 diff의 이동으로 본다.
경계는 **from 배타 / to 포함**이다. 걸러낸 건수와 날짜를 `change_set`에 남긴다 —
필터가 조용히 버리는 경로가 되면 "몇 건을 왜 제외했나"에 답할 수 없다.

## 결정 사항

0.7단계 종료 시점에 확정된 설계 판단이다. 구현 착수 시 ADR로 옮겨 적는다.

### D-1. 텍스트 정규화 — 원문과 정규화본을 **둘 다 저장한다**

관련 함정: [6](#6), [7](#7)

1번(원문만 저장, 비교 시 정규화)을 택하지 않은 이유는 **검색 인덱스가 정규화본을 요구**하기
때문이다. 임베딩을 원문으로 만들면 번호 접두어와 개정 마커가 토큰으로 섞인다. 임베딩은 행
단위로 저장되므로 정규화본은 쓰기 시점에 물리적으로 존재한다 — 1번을 택해도 정규화본은
만들어지되 **어디에도 기록되지 않은 채 임베딩에만 반영된다. 그것이 가장 나쁘다.**

나머지 두 근거: (a) 감사 재현 — "왜 그때는 변경으로 잡히지 않았나"에 답하려면 그 시점의
판정 기준이 필요하고, 정규화 규칙은 반드시 바뀐다. (b) 성능 — diff는 두 버전 집합을
대조하므로 O(n×m) 비교가 나고, 대형 법령(자본시장법 682조문)에서 매번 재계산은 낭비다.

**컬럼**

| 컬럼 | 용도 |
|---|---|
| `text_raw` | 응답 원문. **인용과 화면 표시는 항상 이것을 가리킨다** |
| `text_norm` | 비교·임베딩 전용 |
| `text_norm_sha256` | diff 판정 기준 |
| `norm_rule_version` | 정규화 규칙 버전 (예: `norm-v1`) |
| `amendment_markers` | 추출된 마커 배열 (jsonb) |

**인용이 `text_raw`를 가리켜야 하는 이유**: 담당자가 검증하러 법령 원문을 열었을 때 우리가
보여준 문장이 그대로 있어야 한다. 정규화본을 인용하면 원문과 미묘하게 달라 검증 비용이
오르고, 검증 비용이 오르면 승인이 형식화된다(원칙 4의 실효성 문제).

**정규화 규칙 `norm-v1`**

1. 번호 접두어 제거: 항/호/목 내용 앞의 `"1. "`, `"가. "`, `"① "` (번호는 별도 필드에 있다)
2. 개정 마커 제거 후 `amendment_markers`로 추출
3. 공백 정규화: 연속 공백 1개, 앞뒤 트림, 개행 정규화
4. 그 외 문자는 손대지 않는다. **특히 한자·괄호·인용부호를 변형하지 않는다**

규칙을 바꾸면 `norm_rule_version`을 올리고 새 버전으로 재계산한 행을 새 `known_from`으로
INSERT한다. 과거 행은 그대로 둔다.

**드리프트가 구조적으로 불가능한 이유**: `regulation_article`은 bitemporal 테이블이며
UPDATE를 하지 않는다(원칙 6). 정정도 `known_until`을 닫고 새 행을 INSERT한다. 원문이
바뀌는데 정규화본이 안 바뀌는 상황 자체가 발생할 수 없다. 추가 장치 셋:

- **단일 쓰기 경로**: `text_raw`와 `text_norm`을 같은 함수에서 한 트랜잭션으로 기록한다.
  `text_norm`만 따로 쓰는 API를 만들지 않는다.
- **불변성 강제**: 두 컬럼에 대한 UPDATE를 트리거로 차단한다.
- **검증 테스트**: 저장된 `(text_raw, norm_rule_version)`에 정규화 함수를 다시 적용해
  `text_norm`과 일치하는지 확인한다. 샘플링으로 CI 상시 실행.

### D-2. 개정 마커 — 제거하되 **별도 필드로 추출한다**

관련 함정: [7](#7)

```json
[{"type": "개정", "date": "2020-03-24", "raw": "<개정 2020.3.24>"},
 {"type": "신설", "date": "2011-05-19", "raw": "<신설 2011.5.19>"}]
```

`raw`를 함께 보관한다. 날짜 파싱이 실패하는 형태를 만났을 때 원본을 잃지 않기 위해서다.
실측에서 `조문제개정일자문자열`이
`"2011.5.19, 2013.8.13, 2014.5.28, 2016.5.29, 2020.3.24, 2020.5.19, 2023.7.18"`처럼
**복수 날짜를 나열**하는 사례가 확인됐으므로(`law_009244_mst252787.xml` 제2조), 파서는
복수 날짜를 전제한다. 파싱 실패는 조용히 넘기지 말고 `raw`만 저장한 뒤 경고를 남긴다.

**확정된 용도 세 가지**

1. **EDITORIAL 자동 분류** — `text_norm_sha256`은 동일한데 `amendment_markers`만 달라진
   경우, 실질 변경이 아니라 이력 갱신이므로 `EDITORIAL`로 분류한다. 이 분류가 없으면 개정
   시마다 모든 조문이 변경으로 보고되어 담당자가 알림을 무시하게 된다.
   **→ 마커를 "제거만 하고 버리면 안 되는" 결정적 이유다. 버리면 EDITORIAL과 실질
   무변경을 구별할 수 없다.**
2. **LLM 호출 억제** — EDITORIAL로 분류된 조문은 분석 계층으로 보내지 않는다.
3. **조문별 개정 연혁 보완** — 조문시행일자가 본문 API에서 평탄화되는 상황에서([8](#8)),
   `조문참고자료`(`[전문개정 2011.5.19]`)와 함께 조문 단위 개정 이력을 구성한다. 변경이력
   API는 "언제 바뀌었는가"를 주지만 조문 텍스트 안의 마커는 "그 조문 자체가 명시하는 개정
   이력"이라 **출처가 다르다. 두 출처가 불일치하면 그것 자체가 조사할 신호다.**

**주의**: 마커는 `text_raw`에서 제거하지 않는다. 제거는 `text_norm` 생성 시에만 일어난다.
따라서 `amendment_markers`는 `text_raw`의 파생 정보이며 원문이 정본이다. 추출 결과가
`text_raw`에서 재현되는지 확인하는 테스트를 D-1의 정규화 검증 테스트와 같은 자리에 둔다.
