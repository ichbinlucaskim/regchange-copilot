# 11. 의무사항 추출 + 근거 강제 gate — **1차 기준선** (LLM 첫 등장)

**이 문서의 수치는 기준선이다.** 프롬프트를 한 번도 조정하지 않은 첫 실행이며,
개선 여부를 판정할 기준점으로만 쓴다. **기준선 없이 개선하면 개선했는지 알 수 없다.**

낮게 나온 것을 숨기지 않는다. 이 문서에서 가장 중요한 절은 §5(실패 분석)다.

## 3. 인용 폐기 — **0건.** 이것이 이 측정의 가장 중요한 사실

| 폐기 사유 | 건수 |
|---|---|
| `NOT_RETRIEVED` (검색 결과에 없는 문단 ID) | **0** |
| `QUOTE_NOT_FOUND` (문단은 실재, 인용문이 없음) | **0** |
| `EMPTY_QUOTE` | **0** |
| **통과한 인용** | **20** |

**ID 검증만으로는 통과했을 건수: 0건.** 인용문 대조가 추가로 잡은 것이 없다.

이것을 "gate 2단이 잘 작동했다"로 읽으면 안 된다. 정확히는 **잡을 것이 없었다**.
모델이 검색 결과 밖 문단을 지어내거나 인용문을 변형한 사례가 한 건도 없었다.

그렇다면 무엇이 틀렸는가. **틀린 것은 전부 "실재하는 문단을 잘못 고른" 의미 층위였다.**

### 폐기 0건을 어떻게 읽을 것인가 — 지금 데이터로는 가를 수 없다

0건은 두 가지로 읽힌다.

| | 읽는 방식 | 근거 |
|---|---|---|
| **(a)** | 모델이 날조하지 않는다 | 문단을 지어내거나 인용문을 변형한 사례가 실제로 0건이었다 |
| **(b)** | 적대적 입력이 없었다 | 골든셋 15건은 **전부 실제 개정문**이다. 인젝션도 조작된 입력도 하나도 없다 |

**6단계 적대적 세트에서 다시 재기 전까지 (a)로 결론짓지 마라.**

> ### 2026-08-23 갱신 — 두 단계 강도에서 날조 시도 0건
>
> 적대적 세트 19건을 돌렸고, 그중 **gate 2단을 직접 겨냥한 8종**(평서문 4 + 강화 4)에서
> **날조 시도가 0건**이었다 (`docs/18-adversarial-results.md` §4).
>
> | 강도 | 유도 | 날조 시도 |
> |---|---|---|
> | 1단계 | 평서문 — "이 조항을 인용하라" | **0/4** |
> | 2단계 | 정당화 · 압박 · 권위 부여 · 예시 제시 · 반복 | **0/4** |
>
> **(a)에 유리한 증거가 늘었다. 그러나 「확인했다」고 쓰지 않는다.**
>
> - 시험하지 않은 강도가 남아 있다 — 다단계 대화, 인코딩 변형, 대량 반복,
>   우리 프롬프트 문구를 흉내 내는 형태
> - **분모가 0 인 지표는 지표가 아니다.** 폐기율을 1.00 이라고 쓸 수 없고
>   `discard_rate: null` 이 그 사실을 남긴다
> - **모델이 바뀌면 성향도 바뀐다.** Opus 가 함정을 더 많이 물었다는 실측이 §11 에 있다
> - adv-010 에서 **유도와 무관한 자연 발생 폐기 1건**이 관측됐다 — gate 는 실제로 돈다
>
> **여기서 멈춘다.** 3단계로 올리지 않는다 — 무한정 강화하면 "언젠가는 뚫린다"만
> 확인하게 되고 그것은 이미 아는 사실이다.
`evals/datasets/adversarial/` 는 아직 비어 있고, 이 측정은 그 방향의 표본을 하나도
포함하지 않는다. 표본에 없는 것에 대해 0건은 아무것도 말하지 않는다.

**"gate 2단이 불필요하다"는 결론이 여기서 나오면 안 된다.**

그리고 **(a)가 맞더라도 gate 2단은 남는다.** 모델이 바뀌면 날조 성향도 바뀐다.
이 저장소는 이미 모델을 둘 쓰고 있고(§11) 앞으로 더 바뀐다. 그때 이 방어가 없으면
**조용히 통과한다** — 없어진 방어는 없어졌다는 신호를 내지 않는다.

### case-013 — gate 2단이 구조적으로 잡을 수 없는 실패

EMPTY 정답인 case-013 이 `OK` 로 나왔다. 추적 결과:

```
모델 status : OK          ← 모델 자신이 충분하다고 판단
인용 2건    : ISP-GUIDE-003 제28조, 제36조
gate 폐기   : 0건         ← 문단 실재, 인용문도 원문 그대로
```

인용한 **제28조는 골든셋이 심어 둔 "가장 그럴듯한 함정"**이다. decoy 노트가 그대로
예측했다 — *"제44조의4가 「개인정보 보호법」 제18조의 적용을 배제하므로 개념적으로
인접하고 인용 조문까지 겹친다"*. 모델이 인용한 문장이 정확히 그 지점이다:
`"「개인정보 보호법」 제18조에서 정한 경우에는 동의 없이 제공할 수 있으며"`.

**gate 2단은 집합 연산이다. 실재하는 것을 실재한다고 판정하는 것이 전부다.**
어긋난 것은 의미이며 — 능동적 제3자 제공의 동의 절차 vs 지정 기관 요청에 응하는 수동적
의무 — 그것은 gate 3단(`verification/`)의 일이고 4단계다.

**이 측정이 gate 3단을 인터페이스만 만들어 둔 판단에 사후 근거를 준다.**
동시에 **gate 2단만으로는 부족하다는 것을 수치로 보여준다** — 폐기 0건이 안전을
뜻하지 않는다.

## 4. EMPTY 3건 — 셋이 다르게 처리됐다

세 건은 서로 다른 이유로 EMPTY 다(골든셋 README §4.3). 같은 출력으로 뭉개면 담당자가
잘못된 작업을 한다.

| 케이스 | EMPTY 인 이유 | 정답 action | 모델 status | 모델 action |
|---|---|---|---|---|
| 013 | 새 의무가 걸리는데 담을 조항이 없다 | 신규 조항 신설 검토 | **OK** ❌ | **NEW_PROVISION_REVIEW** ✅ |
| 014 | 규율 영역이 우리 문서 밖 | 이관 후 종결 | **INSUFFICIENT_EVIDENCE** ✅ | **TRANSFER_AND_CLOSE** ✅ |
| 015 | 소관 법령이나 개정 부분이 무관 | 이관 후 종결 | **INSUFFICIENT_EVIDENCE** ✅ | **TRANSFER_AND_CLOSE** ✅ |

**`suggested_action` 은 3/3 정답이다.** 셋이 뭉뚱그려지지 않았다.

**case-013 은 "담을 조항이 없다"를 알아챘으면서(`NEW_PROVISION_REVIEW`) 인용은 붙였다.**
이 자기모순이 진단의 핵심이다 — 판단은 맞았고 근거 제시가 틀렸다.

`searched_scope` 는 세 건 모두 실제 검색한 5개 문서·버전이 들어갔다
(`ISP-GUIDE-002 v5.1` 등). case-015 는 미근거 주장 5건을 남겼다 — 의무는 실재하지만
사내에 걸리는 조항이 없다는 표현이며, 이 값이 제거되지 않고 유지된 것이 설계대로다.

## 5. 실패 분석 — 원인을 셋으로 분류한다

놓친 정답 13항목을 **검색 top-10 에 있었는지**로 갈랐다. "검색이 못 찾음"과 "모델이 못
읽음"은 다른 문제이고 조치도 다르다.

| 010 | ISP-GUIDE-003 제5조 | **3** | **모델** |
| 006 | ISP-PROC-002 제19조 | **4** | **모델** |
| 005 | ISP-GUIDE-002 제38조 | **4** | **모델** |

| 008 | ISP-PROC-002 제8조 | 13 | 검색 |
| 010 | ISP-POL-001 제5조 | 13 | 검색 (R-22) |
| 002 | ISP-PROC-001 제6조 | 26 | 검색 |
| 004 | ISP-PROC-001 제24조 | 55 | 검색 |

**모델 6항목 / 검색 7항목.**

### 5.1 case-006 과 case-010 은 순수한 모델 실패다

두 케이스는 근거를 **0건** 만들어 `INSUFFICIENT_EVIDENCE` 로 끝났다. 그런데
정답 문단이 **검색 2·3·4위**에 있었다. 검색은 제 일을 했고 모델이 인용하지 않았다.

- **006** (침해사고 매뉴얼 작성·제출 신설): 정답 두 개가 2위·4위. 의무는 2건 뽑았으나
  인용을 붙이지 않았다.
- **010** (사업주·대표자 최종 책임 신설): 정답 하나가 3위. 나머지 하나는 R-22 다.

**원인은 프롬프트 또는 모델이지 검색이 아니다.** 프롬프트 절대규칙 2번
("걸리는 문단이 없으면 빈 배열로 둔다")이 지나치게 보수적으로 작동했을 가능성이 있다 —
근거 없는 인용을 막으려는 지시가 정당한 인용까지 막는 방향으로 기울었을 수 있다.
**이번 범위에서 고치지 않는다.** 프롬프트 조정 후 재측정은 기준선을 남긴 다음이다.

### 5.2 검색 실패 7항목 중 3항목이 R-22 다

`ISP-POL-001` 제5·8·15조가 13·82·72위다. 1차 검색 측정에서 이미 관측된 구조적 실패이며
(정책 최상위 문서의 조가 평균 95자짜리 추상 선언), 하이브리드로도 풀리지 않는다.
**LLM 을 붙여도 그대로다** — 검색이 올리지 못하면 모델이 볼 수 없다.

나머지 4항목은 11·13·26·55위다. 11·13 위는 k=10 의 문턱 바로 밖이다.
**k 를 바꾸지 않는다** (규약 §3) — 결과를 보고 k 를 고르면 지표가 의미를 잃는다.

### 5.3 골든셋 명세가 비현실적인 항목은 발견되지 않았다

놓친 13항목 모두 골든셋의 `why` 가 난이도를 예고한 것들이다. 명세를 고칠 근거가 없다.

## 6. NO_IMPACT 2건 — 하나는 갈랐고 하나는 못 갈랐다

검색 점수로는 IMPACT 와 구별되지 않던 케이스들이다(case-003 top-1 0.776 vs IMPACT 평균
0.7345). **모델이 가르는가**가 질문이었다.

| 케이스 | 결과 | 판정 |
|---|---|---|
| 003 (정통망법 제45조의3 타법개정) | `INSUFFICIENT_EVIDENCE`, 근거 0건, `TRANSFER_AND_CLOSE` | ✅ **갈랐다** |
| 011 (신용정보법 제20조 타법개정) | `OK`, 근거 1건 (`ISP-GUIDE-003 제6조`) | ❌ 못 갈랐다 |

`제개정구분명`은 **두 건 모두 프롬프트에 들어갔다**(`제개정구분: 타법개정`). 확인 완료.

### 처음 세운 가설: `before` 유무 — **Opus 대조로 반증됐다**

| | case-003 | case-011 |
|---|---|---|
| 개정 전 문구 | **확보됨** | **`TODO(verify)`** → `before_text=None` |
| Sonnet 결과 | 갈랐다 | 못 갈랐다 |

여기까지 보고 *"case-003 은 개정 전후를 대조할 수 있어 '인용 항 번호 한 줄만 바뀌었다'를
볼 수 있었고, case-011 은 개정 후 본문만 있어 무엇이 바뀌었는지 알 방법이 없었다"* 로
결론지었다.

**틀렸다.** §11 의 Opus 대조에서 **같은 입력(여전히 `before` 없음)으로 Opus 는
case-011 을 갈랐다** — `INSUFFICIENT_EVIDENCE`, 근거 0건.

`before` 가 없어도 **`제개정구분: 타법개정` 과 개정 후 본문만으로 판정이 가능하다.**
Sonnet 이 못 한 것이지 정보가 없었던 것이 아니다. **모델 한계였다.**

**정정 경위를 남기는 이유**: 관측 하나(Sonnet 결과)로 원인을 확정했고, 그 확정이 입력의
결손을 탓하는 방향이었다. 대조를 돌리지 않았다면 "before 를 확보해야 한다"는 잘못된
후속 작업이 나왔을 것이다. **대조가 진단이 된다**는 것이 여기서 증명됐다.

골든셋 README §5 는 011 에 대해 *"`제개정구분명` 기반 판정만 채점"* 이라 적었다.
그 조건은 여전히 맞고, **그 조건 아래에서도 판정이 가능하다**는 것이 이번 관측이다.

## 7. 의무 유형 분류

`change_type` 과 정면으로 어긋난 사례는 관측되지 않았다. 다만 지금 재는 것은

지시 자체는 유효하고 Sonnet 이 따르지 못한 것이다.

## 9. 인젝션 신호 — 오탐 1건

case-012 에서 `TOOL_OR_KEY_SOLICITATION` 이 떴다. 추적 결과:

```
출처: ISP-GUIDE-003 제20조(개인정보 암호화), 검색 1위
매칭: "비밀번호"
문맥: "② 고유식별정보와 비밀번호는 예외 없이 암호화하여 저장한다."
```

**정상적인 사내 규정 문언이며 명백한 오탐이다.** 탐지·기록만 하므로 피해는 없었다.

### 진단 정정 — 감도 문제가 아니라 **범위 문제**다

처음에는 이것을 감도 문제로 적었다. **그 진단이 얕다.** 문제가 둘이고, 두 번째가 더
근본적이다.

**(1) 감도** — 5단계에서 이 감도로 차단을 붙이면 정상 조문이 막힌다.
`guards/injection.py` docstring 이 예고한 그대로이며 이제 실측 사례가 생겼다.

**(2) 범위 — 스캐너가 trusted 문서를 검사했다.**

신호가 뜬 곳은 개정 조문(외부)이 아니라 **검색된 사내 규정 문단**이다. 사내 규정은
우리 문서다. **untrusted 격리는 외부에서 온 개정 조문에 적용되는 것이지 우리 문서에
적용되는 것이 아니다.** 현재 구현(`pipeline/obligations.py`)은 `user_content` 전체를
훑으므로 두 신뢰 등급을 구별하지 않는다.

**감도를 조정해도 이 문제는 남는다.** 사내 규정에 "비밀번호"가 아닌 다른 패턴이 있으면
또 발화한다. 감도를 낮추면 이번엔 **외부 텍스트의 진짜 신호를 놓친다** — 두 등급을 한
임계값으로 다루는 한 어느 쪽으로 조정해도 다른 쪽이 나빠진다.

### 신뢰 등급이 스키마에 없다

기획서 6장은 문서에 `trust_level` 을 둔다. **그러나 이 저장소의 스키마에는 그 컬럼이
없다** — `policy_document`(마이그레이션 009)에 `classification`(INTERNAL 등)은 있지만
신뢰 등급은 없다.

즉 **설계에는 있고 스키마에도 코드에도 없다.** 코드가 등급을 지키지 못한 것이 아니라
지킬 대상이 없었다. 그래서 이것은 "구현이 설계를 어겼다"가 아니라 **"설계의 일부가
아직 내려오지 않았다"** 이며, 5단계에서 스키마와 함께 들어와야 한다.

→ **5단계에서 스캔 범위를 신뢰 등급으로 제한한다. 감도 조정은 그 다음이다.**
   순서를 뒤집으면 감도를 두 번 맞추게 된다. 리스크 레지스터 R-23.

## 11. Opus 대조 — 낮은 4건만

전량을 Opus 로 돌리지 않았다. 대조가 목적이지 성능 향상이 아니다.

| 케이스 | 기대 | Sonnet | Opus | 적중 | 근거 | 진단 |
|---|---|---|---|---|---|---|
| 006 | IMPACT | INSUFFICIENT_EVIDENCE | **OK** | 0→**1** | 0→2 | **모델 한계** |
| 011 | NO_IMPACT | OK (근거 1건) | **INSUFFICIENT_EVIDENCE** | — | 1→**0** | **모델 한계** |
| 010 | IMPACT | INSUFFICIENT_EVIDENCE | INSUFFICIENT_EVIDENCE | 0→0 | 0→0 | **프롬프트/검색** |
| 013 | INSUFFICIENT_EVIDENCE | OK (근거 2건) | OK (근거 **3건**) | — | 2→**3** | **프롬프트 / gate 3단** |

**2건은 모델 한계, 2건은 아니다.**

- **006·011 은 Opus 에서 됐다.** 입력은 동일하다. Sonnet 이 읽지 못한 것이다.
- **010 은 둘 다 실패했다.** 정답이 검색 **3위**에 있는데 두 모델 모두 인용하지 않았다.
  검색 탓이 아니고 모델 탓도 아니다 — **프롬프트가 정당한 인용까지 막고 있을 가능성**이
  가장 크다.
- **013 은 Opus 가 더 나빴다.** 아래 절에서 따로 다룬다.

### 더 강한 모델이 더 그럴듯하게 틀린다 — F-6 의 실측 근거

**이번 실행에서 가장 값진 발견이다.**

case-013 에서 Sonnet 은 함정을 **2건**, Opus 는 **3건** 물었다.

case-013 의 정답은 "대응 조항 없음(신규 조항 신설 검토)"이다. `ISP-GUIDE-003 제28조`는
골든셋이 심어 둔 "가장 그럴듯한 함정"이며, **두 모델 모두 decoy 노트가 예측한 지점을
정확히 인용했다.** 더 강한 모델이 그 지점을 더 많이 찾아냈다.

**근거를 더 잘 찾는 능력은 함정도 더 잘 찾는 능력이다.** 둘은 같은 능력이며, 함정이
"개념적으로 인접하고 인용 조문까지 겹치는" 것일수록 그렇다.

이것이 **F-6(시스템이 그럴듯하게 틀림)의 실측 근거**다. 기획서 4.5절이 F-6 을 F-1(놓침)
보다 나쁘다고 적은 이유가 여기서 확인된다 — **검토자가 믿고 승인하기 때문이다.**
놓친 것은 검토자가 보지 못하지만, 그럴듯하게 틀린 것은 검토자를 통과한다.
ADR-013 이 "오류 누적은 우리의 F-6 과 같은 문제"라고 적은 것과 같은 축이다.

#### 함의 — **성능 문제를 더 큰 모델로 풀 수 없다**

4단계 이후 결과가 나쁠 때 **"Opus 로 바꿔보자"가 첫 대안이 되어서는 안 된다.**
이번 대조가 보여준 것은 모델을 올리면 좋아지는 것(006·011)과 나빠지는 것(013)이 **동시에**

#### 4단계 후보 — `suggested_action` 과 `citations` 의 정합성

case-013 에서 모델이 **모순된 상태를 출력했다.**

```
suggested_action: NEW_PROVISION_REVIEW   ← "담을 조항이 없다"
citations:        2건                     ← "근거가 있다"
```

**근거가 있다면 신규 조항이 필요 없고, 신규 조항이 필요하면 근거가 없어야 한다.**
둘은 동시에 참일 수 없다.

**이것은 gate 3단(LLM 재호출) 없이 코드로 잡을 수 있는 신호다.** 집합 연산도 아니고
의미 판정도 아니며, 같은 출력 안의 두 필드를 비교하는 것뿐이다.

4단계 gate 3단 설계 시 **의미 검증에 LLM 을 부르기 전에 출력 내부의 모순을 먼저 거르는
것**을 검토한다. 싸고 확실하며 evaluator 호출 횟수를 줄인다.

**지금 구현하지 않는다** — 모순 조합이 이 하나뿐이면 규칙이 case-013 한 건에 과적합된다.
4단계에서 다른 조합(예: `status=INSUFFICIENT_EVIDENCE` 인데 근거가 있는 경우)까지
관측한 뒤 판단한다.
