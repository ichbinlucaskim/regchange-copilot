# 아키텍처 결정 기록 (ADR)

이 디렉터리의 ADR은 모두 `adr-000-template.md`의 **4항목 구조**(목적 / 구현 이유 /
트레이드오프 / 엣지 케이스)를 따르며, 여기에 두 절을 더한다:

- **제품 철학과의 연결** — 이 결정을 뒤집으면 시스템이 어느 지점에서 사용자의 선택을
  대신하게 되는가
- **축 연결** — 축 1(업무) / 축 2(환경) / 축 3(운영) 중 어디에 기여하는가

트레이드오프 절에는 **"틀렸음을 알게 되는 신호"**와 **"되돌리는 비용"**이 반드시 있다.

모든 실측 근거 주장에는 픽스처 파일명 또는 리포트 절 번호가 인용되어 있다.
확인하지 않은 것은 `TODO(verify)` 또는 "미확인"으로 표시했다.

## 읽는 순서 제안

**승인 게이트가 어떻게 강제되는지 알고 싶다면**: 013 → **018**. 013 이 패턴으로 정하고
018 이 그것을 세 겹(그래프 구조 · DB 권한 · FK 제약)으로 만든다.

**이 시스템이 무엇을 하지 않는지 알고 싶다면**: 003 → 004 → 007 → **013**.
앞의 셋이 "근거가 없으면 단정하지 않는다"를 각각 다른 층위에서 구현하고,
013이 "그래서 이 시스템은 워크플로인가 에이전트인가"에 답한다 — 답은 워크플로이고,
그 ADR 의 「용어」 절이 두 낱말을 구별한다.

**왜 이 도메인인지 알고 싶다면**: 008 → 005 → 006.

**은행 환경에서 어떻게 굴러가는지 알고 싶다면**: 010 → 012 → 009.

**설계 근거가 틀린 것을 발견하면 어떻게 하는지 보고 싶다면**: ADR-003의
"근거 정정 이력" → `docs/incidents/silent-undercounting.md`.

**데이터 모델을 알고 싶다면**: 001 → 002 → 009.

## 축별 분포

| 축 | ADR | 개수 |
|---|---|---|
| 축 1 (업무) | 001, 002, 003, 004, 005, 006, 007, 008, 009, **013**, **016** | 11 |
| 축 2 (환경) | **010**, **012**, **015** | **3** |
| 축 3 (운영) | 002, 003, 005, 006, 008, 009, **013**, **014**, **016** | 9 |

**축 2가 2건에서 3건이 됐다 (ADR-015).** 여전히 가장 적다.

ADR-015 를 축 2로 세는 기준을 분명히 해 둔다 — **어댑터 경계 뒤에 두는 것만으로는 축 2가
아니다.** ADR-015 는 전자금융감독규정 제14조의2(클라우드컴퓨팅서비스)의 존재를 원문으로
확인하고, 그 절차를 통과하지 않아도 되는 경로를 **의도적으로** 골랐다. 규제 근거가 붙어야
축 2다. 이 기준을 느슨하게 하면 분포표가 축 2의 공백을 더 이상 보여주지 못한다.

남은 공백은 여전히 **망분리 · 전자결재 · 직무분리**다.

**이 분포 자체가 다음에 무엇을 결정해야 하는지를 가리킨다.** 축 1은 실측이 쌓이면서
자연히 채워졌지만 축 2는 그렇지 않다 — 환경 제약은 코드를 쓰다 보면 드러나는 것이
아니라 **밖에서 들어오는 제약**이라 의식적으로 조사해야 한다. 이 저장소가 증명하려는
3축 중 하나가 비어 있는 상태이며, 분포표를 남기는 이유가 그것을 계속 보이게 하는
것이다.

> **011번은 비어 있다.** 조문 이동의 점수 가중치·임계값을 정할 때 쓰기로 ADR-003이
> 예약해 두었다. 번호는 재사용하지 않는다.
