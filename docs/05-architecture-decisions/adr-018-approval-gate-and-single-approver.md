# ADR-018: 승인 게이트는 그래프의 `interrupt` 이고, 승인자는 **지금 한 명**이다 — 결재선은 행이 늘어나는 형태로 확장한다

## 맥락

원칙 4 는 "인간 승인을 그래프 레벨에 둔다"이고 ADR-013 은 그 이유를 적었다 — UI 검사는 API
를 직접 호출하면 우회되지만, 그래프가 중단되어 있으면 우회 경로 자체가 없다. 4단계에서
그것이 실제 코드가 된다.

동시에 답해야 할 질문이 하나 더 있다. **승인자가 몇 명인가.** 기획서 14.4 는 결재선
(`approval_line`)을 두지만, 지금 운영은 로컬 노트북에서 저자 한 명이 돈다(ADR-014).
결재선을 지금 만들면 **검증할 대상이 없는 구조**가 들어오고, 만들지 않으면 나중에 스키마를
갈아엎게 된다. 어느 쪽인지 정해 두어야 한다.

---

## 결정

**승인은 LangGraph 의 `interrupt` 로 구현한다.** 재개는 `Command(resume=...)` 로만 가능하고,
체크포인터는 Postgres 의 별도 스키마(`graph_checkpoint`)에 둔다. 승인 레코드와 발송 대상은
**승인 이후 노드만** 만들 수 있으며, 그 노드로 들어오는 간선은 `human_review` 하나뿐이다.

**승인자는 한 명이다.** `approval_line` 테이블을 만들지 않는다. 다만 `review_decision` 을
**평가 한 건에 여러 행이 붙을 수 있는 형태**로 두어, 다단계가 필요해지면 순서 컬럼 하나를
더하는 것으로 확장되게 한다.

---

## 목적

승인 없는 실행 경로가 **존재하지 않는** 상태를 만들고, 그 사실을 테스트로 고정한다.
그리고 **승인이 형식화되고 있는지를 잴 수 있게** 한다 (F-7).

---

## 구현 이유

### 승인 게이트를 세 겹으로 만든다 — 무너지는 방식이 다르기 때문이다

| 겹 | 무엇이 막는가 | 어떻게 무너지는가 |
|---|---|---|
| **그래프 구조** | `enqueue_actions` 로 들어오는 간선이 `human_review` 하나뿐 | 코드 수정 |
| **DB 권한** | `app_graph` 는 `review_decision`·`action_outbox` 에 INSERT 불가 | role 설정 변경 |
| **FK 제약** | `action_outbox.review_decision_id` 가 NOT NULL | 마이그레이션 |

**같은 것을 세 번 막는 것이 아니라, 무너지는 방식이 다른 방어를 겹친 것이다.** 코드 수정
하나로 세 겹이 동시에 사라지지 않는다. 셋 다 `tests/security/test_graph_approval_gate.py`
가 검사한다.

### 왜 `status` 를 검토자가 못 고치게 하는가

003 은 `GRANT UPDATE (status) ON impact_assessment TO app_review` 였다. 011 이 그 컬럼을 둘로
갈랐다.

- `status` — gate 가 정한 **기계의 판정**(OK / NEEDS_REVIEW / INSUFFICIENT_EVIDENCE).
  **누구도 UPDATE 할 수 없다.**
- `review_state` — **사람의 처리 상태**(PENDING / ACCEPTED / EDITED / REJECTED). `app_review`
  만 UPDATE 한다.

검토자가 `status` 를 고칠 수 있으면 **"시스템은 근거 부족이라고 했는데 사람이 충분으로
고쳤다"가 기록에서 사라진다.** 그 사실이야말로 6단계 평가가 봐야 할 것이다. 권한을 좁히는
방향의 변경이므로 옛 경계를 검사하던 테스트가 함께 좁아졌다.

### 왜 초안을 고치지 않고 수정 내용을 승인 레코드에 담는가

검토자가 "수정 승인"할 때 초안 자체를 고치면 **원본이 사라진다.** 그러면 6단계에서
"담당자가 무엇을 고쳤는가"를 셀 수 없고, 그것이 모델 품질에 대한 가장 직접적인 데이터다.
초안은 트리거로 불변이고 수정은 `review_decision.edit_json` 에 남는다 (원칙 6).

### 왜 반려 사유를 닫힌 코드로 받는가 — F-7 감시

승인이 형식화되면 **반려율이 0 에 가까워지고 검토 소요가 짧아진다.** 둘을 함께 보지 않으면
"빠르게 잘 처리되고 있다"와 구별할 수 없다. 그래서 둘 다 기록한다.

사유 코드는 **이 시스템이 틀릴 수 있는 방식**에서 도출했다. 조치가 갈리는 단위로 잘랐다.

| 코드 | 무엇이 틀렸나 | 조치 |
|---|---|---|
| `WRONG_PARAGRAPH` | 조항을 잘못 골랐다 (F-6) | 검색·프롬프트 |
| `MISSED_PARAGRAPH` | 걸리는 조항을 놓쳤다 (F-1) | 재현율 |
| `WRONG_DEPARTMENT` | 부서 배정이 틀렸다 | 근거 표현 해석 |
| `WRONG_RISK` | 위험도가 틀렸다 | 위험도 기준 |
| `NOT_APPLICABLE` | 우리 영역이 아니다 | 이관 |
| `INSUFFICIENT_BASIS` | 근거가 주장을 뒷받침하지 않는다 (F-6) | **gate 3단이 놓쳤다** |
| `OTHER` | 위에 없다 | **쌓이면 코드를 늘린다** |

`OTHER` 는 자유 기술을 DB CHECK 로 강제한다. 강제하지 않으면 `OTHER` 가 기본값이 되고,
그러면 코드 집합이 있어도 없는 것과 같다.

### 왜 검토 소요를 브라우저가 재는가

서버에서 큐 진입 시각과의 차이로 계산하면 **"화면을 열어 둔 채 퇴근한 시간"이 검토
시간**이 된다. F-7 이 재려는 값은 그것이 아니다. 화면이 열린 시각부터 제출까지를 재고,
그 값을 행에 저장한다 — 저장해 두면 나중에 큐 진입 시각의 정의가 바뀌어도 과거 측정이
살아남는다.

### 왜 기한을 우리가 정하지 않는가

"검토는 N일 안에"라는 상수를 만들 근거가 이 저장소에 없다. 반면 **실제 기한은 데이터에
이미 있다** — 개정 법령의 시행일까지 사내 규정이 정비되어 있어야 하고, 그 날짜는 법제처가
준다. 우리가 만든 숫자가 아니라 밖에서 온 사실이다.

시행일을 확보하지 못한 건은 `due_at` 을 NULL 로 두고 큐에는 넣는다. **"기한을 모르는 대기"와
"기한이 넉넉한 대기"는 다른 사실**이며 `ops alerts` 가 전자를 따로 센다. 임의의 기본 기한으로
채우면 그 구별이 사라지고, 근거 없는 숫자가 운영 지표가 된다.

### 왜 결재선을 지금 만들지 않는가

로컬 단일 검토자 운영이다(ADR-014). 결재선을 지금 만들면 **검증할 대상이 없는 구조**가
들어오고, 그 구조는 "동작하니까 맞다"로 굳는다. CLAUDE.md §10 의 "검증 없이 쌓지 않는다"가
적용되는 자리다.

**확장 경로는 스키마가 이미 갖고 있다.** `review_decision` 은 `impact_assessment_id` 에
여러 행이 붙을 수 있고, 다단계는 행이 늘어나는 형태가 된다. 필요해지면 `step` 순서 컬럼과
"모든 단계가 ACCEPT 여야 발송 대상을 만든다"는 조건 하나를 더하면 된다 — **테이블을
갈아엎지 않는다.**

지금 구조가 다단계에서 깨지는 지점도 미리 적어 둔다: `review_state` 가 단일 값이므로
"1차 승인, 2차 대기" 상태를 표현할 수 없다. 그때 `review_state` 를 파생이 아니라 계산으로
바꾸거나 값을 늘려야 한다.

### 왜 체크포인트를 별도 스키마에 두는가

체크포인터는 자기 테이블을 만들고 갱신·삭제한다. 그 권한을 `public` 스키마에서 주면 도메인
테이블에 대한 권한과 구별되지 않는다. 스키마를 나누면 "그래프의 작업 상태"와 "도메인
데이터"가 권한 수준에서 갈린다.

**`app_dispatch` 에는 USAGE 조차 주지 않는다.** 체크포인트에는 프롬프트와 모델 출력이 들어
있고, 발송 워커가 그것을 보지 않는다는 것이 원칙 5 다.

### 프레임워크에 대한 가정을 하나 발견했다

ADR-013 은 LangGraph 를 채택하며 *"프레임워크 동작에 대한 잘못된 가정이 문제의 흔한 원인"*
이라는 경고를 함께 적었다. 그 경고가 실제로 맞는 지점이 나왔다.

**체크포인터의 직렬화기가 dataclass 의 `tuple` 필드를 `list` 로 되돌린다.** 타입 힌트는
`tuple` 인데 값은 `list` 인 상태가 되고, 이 어긋남은 아무 오류도 내지 않는다. 같은 직렬화기가
"등록되지 않은 타입은 앞으로 차단된다"는 경고도 낸다.

대응: **그래프 상태에 도메인 객체를 넣지 않는다.** 문자열·숫자·리스트·사전만 넣고 복원은 우리
파서가 한다(`graph/state.py`). 부수 효과로 체크포인트가 **읽을 수 있는 문서**가 되어, 감사에서
"그때 그래프가 무엇을 들고 있었는가"에 JSON 으로 답할 수 있다.

## 제품 철학과의 연결

**"선택의 순간이 아니라 선택에 이르는 과정."** 이 ADR 은 그 문장이 코드가 되는 지점이다.

- 그래프가 멈추는 것은 **선택의 순간을 사람에게 남기는 것**이다.
- 검토 화면이 gate 폐기 기록과 판정 이유를 모두 펴서 보여주는 것은 **결론만 보고 승인하기
  어렵게** 만드는 것이다. 그것이 없으면 게이트는 통과 의식이 된다.
- 반려 사유를 구조화하는 것은 **과정이 학습되게** 하는 것이다.

---

## 축 연결

- **축 1 (업무)** — 주된 기여. 승인 없이는 아무것도 나가지 않는다.
- **축 2 (환경)** — 부분 기여. 승인 레코드와 발송 대상 분리가 전자결재 연동의 접합점이다.
  **다만 지금 인증이 없다** — 실제 배포에는 SSO 와 결재선 연동이 필요하고 그것은 이 단계의
  범위가 아니다. 가짜 인증을 만들면 나중에 진짜와 섞인다.
- **축 3 (운영)** — `ops alerts` 가 검토 기한 초과와 기한 미상을 따로 센다.

## 트레이드오프

**포기한 것**

- **인증.** 로컬 단일 사용자이며 `decided_by` 를 화면에서 받는다. 축 2 를 만족하지 않는다는
  것을 위에 적었다.
- **에스컬레이션·자동 만료.** 보낼 곳이 없다. 미재개 스레드를 조회하고 기한 초과를 판정하는
  것까지만 한다.
- **결재선.** 위 참조.
- **커넥션 하나.** 그래프가 `app_graph` 와 `app_review` 두 커넥션을 연다. 하나로 합치면
  role 도 하나가 되고, 그러면 LLM 노드가 승인 레코드를 쓸 수 있는 상태가 된다.

**얻은 것**

우회 경로가 **존재하지 않는** 상태와, 그것이 유지되는지 확인하는 테스트. 그리고 승인이
형식화되고 있는지 잴 수 있는 값(반려율·사유 분포·검토 소요).

**이 선택이 틀렸음을 알게 되는 신호**

1. **반려율이 0 에 수렴하고 검토 소요가 짧아진다.** → F-7 이 현실이 된 것이다. 화면이 무엇을
   보여주는지부터 다시 본다.
2. **`OTHER` 반려가 쌓인다.** → 사유 코드 집합이 업무를 담지 못한다. 코드를 늘린다.
3. **`INSUFFICIENT_BASIS` 반려가 잦다.** → gate 3단이 놓치고 있다. 검증 프롬프트나 판정
   규칙을 본다.
4. **승인 대기가 기한을 넘긴 채 쌓인다.** → 게이트가 병목이 됐다. 사람의 문제가 아니라
   시스템이 너무 많이 올리는 것일 수 있다 (ADR-003 신호 1번과 같은 축).

**되돌리는 비용**

| 방향 | 비용 |
|---|---|
| `interrupt` → 직접 구현한 승인 대기 | **중간.** checkpointer 와 재개를 다시 만들어야 한다. 승인 레코드와 outbox 구조는 그대로 쓴다 |
| 단일 승인자 → 결재선 | **싸다.** `review_decision` 에 순서 컬럼과 조건 하나. 테이블을 갈아엎지 않는다 |
| 결재선 → 단일 승인자 | 비싸다. 이미 다단계로 남은 이력을 단일 값으로 되돌릴 수 없다 |

## 엣지 케이스

- **체크포인터 없이 컴파일**: 허용하되 `interrupt` 가 실패한다. **"체크포인터가 없으면 승인을
  건너뛴다"는 분기를 두지 않았다** — 그런 분기가 곧 우회 경로다.
- **재개 시 `human_review` 재실행**: `interrupt()` 가 resume 값을 돌려주므로 사람에게 다시
  묻지 않는다. 그래서 이 노드 앞에서 부수효과를 내지 않는다.
- **이미 결정된 건에 다시 재개**: 두 겹으로 막힌다 — 끝난 스레드는 승인 노드를 다시 실행하지
  않고, `record_decision` 은 `PENDING` 이 아니면 거부한다. 두 번째가 중요하다: 프레임워크
  동작이 바뀌어도 발송이 두 번 일어나지 않아야 한다.
- **근거 부족으로 이관된 건**: 큐에 넣지 않되 **행은 남긴다.** 이관 비율(ADR-013 신호 4번)을
  세려면 그 행이 있어야 한다. 상세 화면에서는 볼 수 있다 — "모른다"고 판정한 것도 담당자가
  확인할 대상이다.
- **그래프가 중단 상태가 아닌데 결정이 들어옴**: 승인 레코드가 만들어지지 않으므로 API 가
  409 를 돌려준다. 조용히 200 을 주면 화면은 승인됐다고 표시하고 실제로는 아무 일도 없다.
- **프레임워크 업그레이드로 `interrupt` 동작이 바뀜**: `tests/security/` 가 먼저 깨진다.
  업그레이드는 그 테스트가 통과할 때만 한다 (ADR-013 엣지 케이스).

## 결과 — 전 구간 실행 확인 (2026-08-21)

전문은 `docs/12-impact-assessment-results.md` §11. 그래프를 **실제 모델·실제 role
커넥션·실제 체크포인터**로 두 케이스 돌렸다.

| 케이스 | gate 판정 | 큐 | 재개 결과 |
|---|---|---|---|
| 009 | `INSUFFICIENT_EVIDENCE` | 넣지 않음 (`NOT_QUEUED`) | **아무 일도 일어나지 않았다** — 승인 레코드 0, outbox 0 |
| 008 | `OK` (영향 5건) | 대기 1건, **기한 = 개정 시행일 2026-09-11** | 승인 레코드 1, outbox 1 |

확인된 성질:

- **`interrupt` 가 실제로 멈춘다.** 1차 실행이 `__interrupt__` 를 남기고 종료했다.
- **근거 부족 건은 사람에게 가지 않고, 그 상태에서 재개해도 발송 대상이 만들어지지 않는다.**
- **기한을 우리가 정하지 않았다.** `due_at` 이 개정 조문의 시행일로 채워졌다.
- **발송 대상에 프롬프트도 모델 출력도 없다.** `app_dispatch` role 로 읽어 payload 키를
  확인했다 — `law_name`·`article_path`·`affected_paragraph_ids`·`departments`·`risk_level`·
  `required_evidence`·`decision`·`edit`.
- 프로세스 재시작을 넘어선 재개는 통합 테스트가 별도로 고정한다
  (`tests/integration/test_graph_assessment.py`).

### F-7 감시 지표의 첫 값 — **아직 지표가 아니다**

```
{'decisions': [{'decision': 'ACCEPT', 'n': 1, 'median_ms': 30000}],
 'reasons': [], 'total': 1, 'reject_rate': 0.0}
```

**결정 1건이므로 반려율 0.0 은 아무것도 말하지 않는다.** 지표가 되려면 사람이 실제로
여러 건을 판단해야 한다. 지금 확인한 것은 **값이 나온다는 것**뿐이다 — 그리고 그것이
이 단계의 완료 조건이었다.

> 이 실행의 흔적은 운영 DB 에 남아 있다(`decided_by='smoke-test'`). 세 테이블 모두
> 불변이라 지울 수 없고, 지우려면 소유자 `TRUNCATE` 가 필요한데 그것은 이 저장소가
> 사건으로 기록한 행위다. 남겨 두고 사실대로 적는다.
