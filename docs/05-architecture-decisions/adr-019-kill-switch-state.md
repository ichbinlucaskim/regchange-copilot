# ADR-019: 킬 스위치 상태를 DB 에 두고, 읽지 못하면 멈춘다

| | |
|---|---|
| **상태** | 채택됨 |
| **일자** | 2026-08-21 |
| **결정자** | 프로젝트 저자 (1인 프로젝트) |
| **검토자** | 없음 — 실무자 인터뷰로 사후 검증 예정 |
| **관련 원칙** | 원칙 5 (권한 분리), 원칙 6 (bitemporal) |
| **관련 ADR** | ADR-010 (어댑터 경계), ADR-014 (로컬 운영), ADR-018 (승인 게이트) |

---

## 맥락

CLAUDE.md §6 은 처음부터 킬 스위치 3종(`RETRIEVAL_ENABLED`·`LLM_ENABLED`·
`DISPATCH_ENABLED`)과 그 기본값(꺼짐)을 요구했다. 4단계까지 존재한 것은 `.env.example`
의 세 줄과 그것을 검사하는 테스트 하나뿐이었고, **읽는 코드가 없었다.** 즉 스위치는
선언돼 있고 아무것도 멈추지 않았다.

5단계에서 실동작을 붙이면서 요건 셋이 확정됐다.

1. **재배포 없이 60초 안에 반영된다.**
2. **값 변경이 기록에 남는다** — 누가, 언제, 왜.
3. AWS 이관 시 저장 위치가 `adapters/` 뒤로 갈 수 있다.

세 요건이 저장 위치를 거의 결정한다.

---

## 결정

킬 스위치 상태를 **`kill_switch` 테이블**(bitemporal, 불변 이력)에 두고,
읽기는 `adapters/switches.py` 의 `SwitchStore` Protocol 뒤에서 하며, 판정과 캐시(최대
60초)는 `guards/killswitch.py` 의 `SwitchGate` 가 한다. **상태를 읽지 못하면 멈춘다**
(fail-closed). 쓰기는 소유자 커넥션을 쓰는 CLI(`regchange switch`)만 할 수 있고, 어떤
서비스 role 에도 INSERT/UPDATE 권한을 주지 않는다.

---

## 목적

기능 셋을 **재배포 없이** 멈출 수 있게 하고, 멈춘 사실과 이유가 나중에 답변 가능한
형태로 남게 한다. 그리고 멈춤의 세 가지 이유(껐다 / 켠 적 없다 / 못 읽었다)를 구별한다.

---

## 구현 이유

### 저장 위치

| 대안 | 60초 반영 | 변경 기록 | adapters 경계 | 택하지 않은 이유 |
|---|---|---|---|---|
| **환경변수** | ✗ | ✗ | △ | `api/app.py` 는 장수 프로세스다. 밖에서 프로세스의 환경변수를 바꿀 수 없으므로 "끈다"가 **"재시작한다"**가 된다. 그리고 누가 왜 바꿨는지를 남길 지점이 없다 |
| **파일 + mtime 폴링** | ✓ | ✗ | ✓ | 파일 안에 `changed_by` 를 적을 수는 있지만 **그 값이 진짜인지 확인할 방법이 없다.** 기록을 파일 밖에 따로 두면 그 둘이 어긋난다. 경로가 또 하나의 절대 경로 의존이 되는 것도 이 저장소가 이미 겪은 문제다 |
| **DB 테이블** (채택) | ✓ | ✓ | ✓ | — |

DB 를 고른 결정적 이유는 **기록이 자연스럽다**는 것이다. 이 저장소는 이미 모든 사실을
`known_from`/`known_until` 로 닫고 새로 넣는다. 스위치도 같은 모양이면 "3월 15일에 이
스위치가 켜져 있었나"를 다른 이력과 같은 방식으로 물을 수 있다.

감사 관점에서 이것이 실질이다 — **"왜 그날 분석이 안 돌았나"에 "`LLM_ENABLED` 가
꺼져 있었다"로 답할 수 있어야 한다.** `ops_run` 이 "실패한 날"과 "실행하지 않은 날"을
구별한 것(ADR-014)과 같은 계열의 요구다.

### 읽기와 쓰기를 나눈 이유

`adapters/switches.py` 는 **읽기만** 한다. 쓰기는 `ops/switches.py` 에 있고 소유자
커넥션을 요구한다. 한 클래스에 합치면 **LLM 경로가 들고 다니는 객체에 쓰기 메서드가
생긴다.** DB 권한이 먼저 막지만(013 은 어떤 서비스 role 에도 INSERT 를 주지 않는다),
막힌 것을 부르는 코드를 두지 않는 것이 원칙 5 의 방식이다.

방향이 중요하다 — 인젝션이 성립하더라도 **스위치를 켜는 경로가 없어야** 한다.
`tests/security/test_kill_switches.py` 가 `app_graph` 로 INSERT/UPDATE/DELETE 를 시도해
전부 거부되는지 검사한다.

### 캐시를 게이트에 둔 이유

Protocol 은 "지금 값을 읽어 온다"만 약속한다. SSM Parameter Store 는 자체 캐싱 특성이
다르고, 인터페이스가 캐시를 규정하면 그 특성과 싸우게 된다 (ADR-010 의 논리).

**성공한 조회만 캐시한다.** 실패를 캐시하면 DB 가 돌아온 뒤에도 최대 60초 더 멈춘다 —
장애 시간을 우리가 늘리는 셈이다.

### fail-closed — 모르면 안 한다

상태를 읽지 못하면 멈춘다. 반대 방향(모르면 계속 한다)이 더 편해 보이는 순간이 반드시
오지만, **그 순간이 정확히 스위치가 필요한 순간이다** — 무언가 잘못돼서 멈추려는데 그
무언가 때문에 스위치를 못 읽는 상황. 그때 "모르니까 계속"이면 스위치가 없는 것과 같다.

이 저장소의 다른 fail-closed 와 같은 계열이다: `INSUFFICIENT_EVIDENCE` 를 "없다"가 아니라
"모른다"로 정의한 것, 카나리아 실패 시 수집을 아예 하지 않는 것.

### 「멈춘다」는 예외다

빈 결과나 `None` 을 돌려주지 않는다. 빈 값은 하류에서 **"인용할 문단이 없다" → "영향
없음"** 으로 읽히고, 그러면 스위치가 담당자에게 "괜찮다"로 보인다. 이것이 이 도메인의
대표적 실패 방식이며(F-1), 그래서 멈춤은 반드시 시끄러워야 한다.

멈춘 이유는 셋으로 나뉜다. 조치가 다르기 때문이다.

| 종류 | 무슨 일 | 조치 |
|---|---|---|
| `OFF` | 누가 껐다 (이유가 행에 있다) | 그 사람에게 묻는다 |
| `NEVER_SET` | 켠 적이 없다 (행이 없다) | 켠다 — 기본값이 꺼짐이다 |
| `UNAVAILABLE` | 상태를 못 읽었다 | 장애 대응. 스위치 문제가 아니다 |

## 트레이드오프

- **반영이 즉시가 아니라 최대 60초다.** "60초 내 반영"은 상한이지 보장이 아니다. 즉시
  반영이 필요하면 프로세스를 재시작한다(런북 §1). **캐시 무효화 경로를 지금 만들지
  않는다** — 60초가 실제로 문제가 되는지 아직 모르고, 안 만든 것을 나중에 만드는 것이
  만든 것을 걷어내는 것보다 싸다.
- **스위치 조회가 DB 에 의존한다.** DB 가 죽으면 스위치를 못 읽고, 그러면 전부 멈춘다.
  파일 기반이었다면 DB 장애와 무관하게 읽혔을 것이다. 그 독립성을 포기하고 기록을 얻었다.
  다만 실무적으로는 손실이 작다 — 이 시스템은 DB 없이는 어차피 아무것도 못 한다.
- **검사 지점이 호출 경로마다 있다.** 한 곳에 모으면 새 진입점이 생겼을 때 조용히
  빠진다. 대신 `switches` 를 **기본값 없는 인자**로 두어 mypy 가 누락을 잡는다.
- **`.env` 에서 스위치가 사라졌다.** 익숙한 자리에 없어 처음 보는 사람이 헤맬 수 있다.
  그래서 `.env.example` 에 "여기 없다"와 켜는 명령을 남겼다 — 효과 없는 설정을 남겨 두는
  것보다 낫다. 효과 없는 설정은 **켜진 상태로 읽힌다.**

---

## 엣지 케이스

- **진행 중인 호출**: 중단하지 않는다. 검사는 노드/함수 **진입에서** 한다. 이미 나간 모델
  호출을 끊으면 `llm_invocation` 행이 남지 않는 호출이 생기고, 그것은 이 저장소가 더
  비싸게 치는 실패다 (`docs/incidents/llm-api-schema-drift.md` 미수 1 이 같은 실패였다).
- **승인 대기 중인 그래프**: `LLM_ENABLED` 를 꺼도 **재개된다.** 승인 이후 노드
  (`enqueue_actions`, `record_rejection`)는 모델을 부르지 않기 때문이다. 사람이 이미 본
  것에 대한 결정은 계속 기록될 수 있어야 한다 — 스위치는 **모델을 멈추는 장치이지 사람의
  판단을 멈추는 장치가 아니다.**
- **승인은 됐는데 발송이 꺼져 있음**: `action_outbox` 행은 쌓이고 나가지 않는다. 켜면
  쌓인 것이 나간다. 승인과 발송을 분리한 원칙 5 가 여기서 그대로 작동한다.
- **`RETRIEVAL` 은 켜져 있고 `LLM` 이 꺼짐**: 그래프가 추출 노드에서 멈춘다. 검색까지의
  결과는 체크포인트에 남아 있으므로 켠 뒤 재개하면 검색을 다시 하지 않는다.
- **스위치를 두 번 껐다**: 행이 하나 더 쌓인다. 막지 않는다 — 두 번째 이유가 첫 번째와
  다를 수 있고, 그 문장이 이력의 값이다.

### 실동작 확인 (2026-08-22) — **실제 DB 스위치로 실제 러너를 멈춰 봤다**

단위·보안 테스트는 고정 값(`static_gate`)으로 판정을 검사한다. 그것만으로는
"조립이 실제로 연결됐는가"를 알 수 없으므로, **운영 DB 의 스위치를 껐다.**

| 껐다 | 무엇을 돌렸나 | 결과 |
|---|---|---|
| `RETRIEVAL_ENABLED` | `evals.runners.retrieval_eval --embed kure-v1 --mode hybrid` | `search()` 진입에서 `SwitchOffError`. 질의 0건 |
| `LLM_ENABLED` | `evals.runners.impact_eval --model sonnet --cases case-001` | `extract_obligations()` 진입에서 `SwitchOffError`. **`llm_invocation` 신규 행 0건 — 돈이 나가지 않았다** |

두 예외 메시지 모두 **누가 언제 왜 껐는지**를 담고 있었다(`lucas 가 … 껐다 — 발화 확인`).
켜고 끈 네 번이 전부 `kill_switch` 이력에 남아 있다 — 이 확인 자체가 감사 기록이다.

`DISPATCH_ENABLED` 는 이 확인에서 **한 번도 켜지 않았다.** 켤 이유가 없다(보낼 워커가
없다) — 그리고 그 상태가 `NEVER_SET` 으로 정확히 표시된다.

**아직 검증되지 않은 것**: `DISPATCH_ENABLED` 는 **관문까지만** 검사했다. 발송 워커가
없으므로 "워커가 실제로 안 보내는가"는 검사할 대상이 없다. 워커가 생기는 시점에 그
테스트도 함께 커져야 한다.
