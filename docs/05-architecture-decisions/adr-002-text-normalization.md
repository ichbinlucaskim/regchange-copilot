## 맥락

법제처 응답의 조문 텍스트를 그대로 비교하면 diff가 성립하지 않는다.

**번호 접두어가 내용에 중복된다.** `호번호 = '1.'`이면서
`호내용 = '1. "금융회사등"이란 다음 각 목의 자를 말한다.'`이다. 항·목도 같다 —
`목번호='가.'` / `목내용='가. 「한국산업은행법」에 따른 한국산업은행'`
(`law_009244_mst252787.xml` 제2조, edge-case #6).

**본문 텍스트 안에 개정 마커가 있다.** `<개정 2020.3.24>`, `<신설 2020.3.24>` 형태가
조문·항·호 내용에 그대로 포함된다. 법령 픽스처 전체에서 `<개정 …>` **2,331회**,
`<신설 …>` **443회**다 (edge-case #7). 개정이 있을 때마다 날짜가 바뀌므로, 실질 내용이
같아도 텍스트는 달라진다.

이 마커가 XML 태그로 오인되지 않는 것은 CDATA 덕분이다 — `law_009244_mst252787.xml`
한 파일에 CDATA 블록이 **1,126개**다 (edge-case #16).

문제는 "정규화를 한다"가 아니라 **"정규화본을 저장할 것인가"**였다.

---

## 결정

원문과 정규화본을 **둘 다 저장한다.**

| 컬럼 | 용도 |
|---|---|
| `text_raw` | 응답 원문. **인용과 화면 표시는 항상 이것을 가리킨다** |
| `text_norm` | 비교·임베딩 전용 |
| `text_norm_sha256` | diff 판정 기준 |
| `norm_rule_version` | 정규화 규칙 버전 (`"norm-v1"`) |
| `amendment_markers` | 추출된 개정 마커 배열 (jsonb) |

**정규화 규칙 `norm-v1`**

1. 번호 접두어 제거 — 항/호/목 내용 앞의 `"1. "`, `"가. "`, `"① "`
2. 개정 마커 제거 후 `amendment_markers`로 추출
3. 공백 정규화 — 연속 공백 1개, 앞뒤 트림, 개행 정규화
4. **그 외 문자는 손대지 않는다. 특히 한자·괄호·인용부호를 변형하지 않는다.**

규칙을 바꾸면 `norm_rule_version`을 올리고 새 버전으로 재계산한 행을 새 `known_from`으로
INSERT한다. 과거 행은 그대로 둔다.

`amendment_markers` 형식:

```json
[{"type": "개정", "date": "2020-03-24", "raw": "<개정 2020.3.24>"},
 {"type": "신설", "date": "2011-05-19", "raw": "<신설 2011.5.19>"}]
```

---

## 목적

같은 조문의 두 버전을 비교했을 때 **실질 변경이 있을 때만 변경으로 잡히게** 하고, 동시에
담당자에게 보여주는 문장은 법령 원문과 글자 단위로 같게 유지한다.

---

## 구현 이유

정규화본을 저장하지 않는 대안(비교 시점에만 정규화)을 택하지 않은 이유가 셋이다.

**1. 검색 인덱스가 정규화본을 요구한다.**
임베딩을 `text_raw`로 만들면 번호 접두어와 개정 마커가 토큰으로 섞인다. 임베딩은 행 단위로
저장되므로 **정규화본은 쓰기 시점에 물리적으로 존재할 수밖에 없다.** 즉 저장하지 않기로
해도 정규화본은 만들어지며, 다만 **어디에도 기록되지 않은 채 임베딩에만 반영된다.**
그것이 가장 나쁜 상태다 — 검색 결과가 왜 그렇게 나왔는지 역추적할 수 없다.

**2. 재현성.**
정규화 규칙은 반드시 바뀐다(마커 패턴 추가, 공백 규칙 조정). `norm_rule_version` 없이는
"왜 그때는 변경으로 잡히지 않았나"에 답할 수 없다 — 현재 규칙으로 재계산한 결과만 남아
과거 판정을 재구성할 수 없다. 원칙 6이 요구하는 것과 같은 성질이다.

**3. 성능.**
diff는 두 버전의 조문 집합을 대조하므로 O(n×m) 비교가 난다. 자본시장법은
**682 조문단위**다 (`law_010513_mst283193.xml`). 매 비교마다 재계산하면 그 비용이
개정 감지 지연으로 나타난다.

### 인용이 `text_raw`를 가리켜야 하는 이유

담당자가 검증하러 법령 원문을 열었을 때 **우리가 보여준 문장이 그대로 있어야 한다.**
정규화본을 인용하면 번호 접두어가 빠지고 마커가 사라져 원문과 미묘하게 다르다.
검증 비용이 오르고, 검증 비용이 오르면 승인이 형식화된다.

### `amendment_markers`를 별도 필드로 두는 이유 — 용도 세 가지

**(1) EDITORIAL 자동 분류.**
`text_norm_sha256`은 동일한데 `amendment_markers`만 달라진 경우, 실질 변경이 아니라 이력
갱신이므로 `EDITORIAL`로 분류한다.
**이것이 마커를 "제거만 하고 버리면 안 되는" 결정적 이유다. 버리면 EDITORIAL과 실질
무변경을 구별할 수 없다.**

**(2) LLM 호출 억제.** EDITORIAL 조문은 분석 계층으로 보내지 않는다.

**(3) 조문별 개정 연혁 보완.** `조문시행일자`가 본문 API에서 평탄화되는 상황에서
(edge-case #8), `조문참고자료`(`[전문개정 2011.5.19]`, 특금법 27건)와 함께 조문 단위
개정 이력을 구성한다. 변경이력 API는 "언제 바뀌었는가"를 주지만 텍스트 안의 마커는
**"그 조문 자체가 명시하는 개정 이력"**이라 출처가 다르다.
**두 출처가 불일치하면 그것 자체가 조사할 신호다.**

`raw`를 함께 보관하는 이유: 실측에서 `조문제개정일자문자열`이
`"2011.5.19, 2013.8.13, 2014.5.28, 2016.5.29, 2020.3.24, 2020.5.19, 2023.7.18"`처럼
**복수 날짜를 나열**하는 사례가 확인됐다 (`law_009244_mst252787.xml` 제2조).
파서는 복수 날짜를 전제하고, 파싱 실패는 `raw`만 저장한 뒤 경고한다 (CLAUDE.md §4).

### 정합성 우려에 대한 답

"두 컬럼이 따로 놀 수 있다"는 우려는 이 스키마에서 **구조적으로 성립하지 않는다.**
`regulation_article`은 bitemporal이며 UPDATE를 하지 않는다(원칙 6). 정정도 `known_until`을
닫고 새 행을 INSERT한다. **원문이 바뀌면 그것은 새 행이고, 새 행은 두 컬럼을 함께 쓴다.**

추가 장치 셋:

- **단일 쓰기 경로**: 두 컬럼을 같은 함수에서 한 트랜잭션으로 기록한다. `text_norm`만
  따로 쓰는 API를 만들지 않는다.
- **불변성 강제**: 두 컬럼 UPDATE를 트리거로 차단한다. 애플리케이션 조건문이 아니라 DB
  제약으로 세운다 — 원칙 5가 권한 경계를 DB에 두는 것과 같은 이유다.
- **검증 테스트**: 저장된 `(text_raw, norm_rule_version)`에 정규화 함수를 재적용해
  `text_norm`과 일치하는지 확인한다. `amendment_markers` 재현성도 같은 자리에서 검사한다.
  샘플링으로 CI 상시 실행.

## 제품 철학과의 연결

정규화본만 저장하면 담당자가 보는 문장이 원문과 달라진다. 원문과 다른 문장을 검증하려면
담당자는 법령 사이트에서 해당 조문을 찾아 눈으로 대조해야 하고, 그 비용이 오르면 **검증을
건너뛰고 승인 버튼을 누르게 된다.** 그 순간 승인 게이트는 과정을 지원하는 장치가 아니라
통과 의식이 된다.

`amendment_markers`도 같은 성질이다. 마커를 버리면 EDITORIAL을 구별할 수 없어 개정 때마다
모든 조문이 변경으로 보고되고, 담당자는 알림을 무시하게 된다. **알림을 무시하기 시작한
사용자는 시스템에 선택을 넘긴 것이다.**

## 축 연결

- **축 1 (업무)** — 인용이 원문과 일치해 검증 가능하다. 가짜 알림을 줄인다.
- **축 3 (운영)** — `norm_rule_version`이 있어야 몇 달 뒤 "왜 그때는 안 잡혔나"에 답한다.
  운영 기간이 길어질수록 이 컬럼의 가치가 커진다.

## 트레이드오프

**포기한 것**

- 저장 용량이 늘어난다. 조문당 텍스트를 두 벌 보관하고 bitemporal이라 버전마다 누적된다.
- 정규화 규칙 변경 비용이 "함수 수정"이 아니라 "재적재"다.
- 쓰기 경로가 두 컬럼을 함께 다뤄야 해 적재 코드가 단순하지 않다.

**얻은 것**

인용은 원문을, 비교는 정규화본을, 과거 판정은 `norm_rule_version`을 쓴다. 세 요구가
서로 충돌하지 않게 분리됐다.

**이 선택이 틀렸음을 알게 되는 신호**

1. **검증 테스트가 상시 실패한다.** 단일 쓰기 경로가 지켜지지 않은 것이며, 병행 저장의
   전제가 무너진다.
2. **`norm_rule_version`이 한 번도 올라가지 않는다.** "규칙은 반드시 바뀐다"는 전제가
   틀렸다는 뜻이며, 버전 컬럼과 재적재 비용이 근거 없이 지불된 것이다.
3. **EDITORIAL 분류가 거의 발생하지 않는다.** `amendment_markers` 추출의 주된 근거가
   약해진다. 1단계 첫 개정 사이클에서 바로 측정 가능하다.
4. **반대로 EDITORIAL이 지나치게 많다.** `norm-v1`이 과하게 정규화하는 것이며, 특히
   규칙 4(그 외 문자 불변)가 지켜지지 않는 경우를 의심한다.
5. **담당자가 인용문과 법령 원문이 다르다고 지적한다.** 인용이 `text_norm`을 가리키는
   경로가 생긴 것이다.

**되돌리는 비용**

| 되돌릴 대상 | 비용 |
|---|---|
| 병행 저장 → 원문만 | **중간.** 컬럼 드롭은 쉬우나 임베딩을 다시 만들어야 하고 과거 EDITORIAL 판정 근거가 사라진다. 원칙 6상 과거 행을 지울 수 없어 "컬럼은 남고 신규 행에만 안 쓰는" 형태가 된다 |
| `norm-v1` 규칙 변경 | **설계상 되돌릴 필요가 없다.** 버전을 올려 새 행을 INSERT하면 과거 판정이 보존된다. **이 결정의 핵심 이점이 여기 있다** — 규칙 변경이 파괴적 마이그레이션이 아니라 append가 된다 |
| `amendment_markers` 제거 | **비싸다.** EDITORIAL 분류가 이 필드에 의존하며, 그 구별을 복구할 방법이 없다 |

## 엣지 케이스

- **번호 접두어가 없는 항/호/목**: 원문과 정규화본이 같아진다. 정상이다.
- **항번호 없는 껍데기 항**: 특금법 제2조·제16조처럼 `항번호`가 없고 `항내용`이 빈
  `<항>`이 삽입된다 (4개 법령 합계 51건, spec §4.3). 빈 텍스트의 해시가 모두 같아지므로
  diff 대상 정의에서 제외 여부를 ADR-003이 다룬다.
- **`조문내용`이 제목만 담는 경우**: `<항>`이 있는 조문은 `조문내용`에 제목 줄만 들어간다
  (edge-case #5). 정규화 대상 텍스트를 무엇으로 조립할지는 파서의 책임이며, 이 ADR은
  조립된 텍스트에만 적용된다.
- **복수 날짜 마커**: 파서는 복수를 전제하고, 실패 시 `raw`만 저장 후 경고한다.
- **관측되지 않은 마커 형식**: `<개정 2020.3.24>`가 관측된 형태다. 범위 표기나 다른
  구분자는 **미확인**. 파싱 실패 경로로 흡수하며 조용히 버리지 않는다.
- **행정규칙의 마커 어휘가 다르다**: `admrul_2100000267264.xml`에서는 `<삭 제>` 9건만
  관측되고 `<개정>`·`<신설>`은 0건이다. **`삭`과 `제` 사이에 공백**이 있어 `<삭제>`로
  매칭하면 놓친다 (spec §6.2). `norm-v1`은 법령 기준이며 행정규칙 확장은 ADR-006 범위다.
- **CDATA가 사라지는 경우**: `type=JSON` 응답에서는 마커 보호가 없을 수 있다 —
  **미확인**(spec §8). JSON 전환 시 재검증한다.
- **한자·괄호·인용부호**: 규칙 4가 보호한다. `병과(竝科)`, `「법률명」` 같은 표기를
  정규화하면 서로 다른 조문이 같은 해시를 가질 수 있다 (`law_009244_mst252787.xml` 제18·19조).
