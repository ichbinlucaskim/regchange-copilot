# ADR-014: 로컬 노트북에서 매일 돌리고, 실행 자체를 테이블에 기록한다

| | |
|---|---|
| **상태** | 채택됨 |
| **일자** | 2026-08-20 |
| **결정자** | 프로젝트 저자 (1인 프로젝트) |
| **검토자** | 없음 — 실무자 인터뷰로 사후 검증 예정 |
| **관련 원칙** | 원칙 6 (bitemporal), 원칙 1 (결정론적 diff) |
| **관련 ADR** | ADR-005 (수집 진입점), ADR-007 (출처 추적), ADR-010 (어댑터 경계) |

---

## 맥락

수집 · 파싱 · 적재 · diff 가 완성됐다. 남은 것은 **그것을 계속 돌리는 일**이다.

이 프로젝트가 증명하려는 세 축 중 **축 3(운영)** 은 코드로 만들 수 없다. "혼자서
실제로 몇 달간 운영해 봤는가"는 시간이 지나야 생기는 값이고, 나중에 밤새워 따라잡을
수 없는 유일한 자산이다. 그래서 AWS 배포(7단계)를 기다리지 않고 **지금 노트북에서**
시작한다.

제약이 셋 있다.

1. **노트북은 꺼지고 잠든다.** 예약 시각에 기계가 없으면 그날 실행은 없다.
2. **법제처 등재 시각을 모른다.** `regDt` 는 공포일자이고(ADR-005), 그 공포가
   API 에 언제 등재되는지는 측정한 적이 없다 — `LS_HISTORY` docstring 이 그 지연을
   "우리가 통제할 수 없는 인지 지연의 하한선"이라 부르며 미확인으로 남겼다.
3. **나중에 AWS 로 옮긴다.** 지금 만드는 것이 이관을 막지 않아야 한다.

그리고 R-21 이 남긴 잔여 리스크가 있다 — 탐지 3(MISMATCH)·4(변경 규모)는 실패를
만들지 않고 컬럼에만 기록된다. **아무도 그 값을 보지 않으면 없는 것과 같다.**

---

## 결정

일일 작업을 **CLI 서브커맨드**(`regchange ops daily`)로 만들고, macOS **launchd** 로
매일 07:00 KST 에 건다. 폴링은 어제부터 **최근 7일**을 재확인한다. 실행 하나를
`ops_run` / `ops_law_outcome` 두 테이블에 **성공이든 실패든** 기록하고,
`ops history` / `ops summary` / `ops alerts` 로 조회한다. 알림은 **보내지 않는다** —
조회 명령이 전부이며, 배포 후 CloudWatch 알람으로 승격한다.

---

## 목적

"N개월간 매일 돌았고, M건을 포착했고, K일 실패했다"를 **근거와 함께** 말할 수 있게
한다. 근거란 재현 가능한 질의이며, 로그 grep 이 아니다.

## 구현 이유

### 스케줄러 — launchd

| 대안 | 장점 | 택하지 않은 이유 |
|---|---|---|
| **launchd** | 예약 시각에 자고 있었으면 **깨어난 직후 한 번 돌린다** | (채택) |
| `cron` | 문법이 Linux 와 같아 이관에 유리 | **자고 있으면 건너뛰고 알리지도 않는다.** 노트북 운영에서 이 차이가 곧 실적의 차이다 |
| 수동 실행 | 설비가 없다 | 매일 기억해야 한다. 잊은 날과 실패한 날이 구별되지 않는다 |

cron 의 "이관에 유리하다"는 장점은 실익이 없다. AWS 에서 스케줄러는 EventBridge 이고
어차피 다시 쓴다. **이관되는 것은 스케줄러 설정이 아니라 한 줄 명령**
(`regchange ops daily`)이며, 그 명령이 셸이 아니라 파이썬 안에 있는 것이 이관의 본체다.

`StartCalendarInterval` 에는 타임존 옵션이 없어 값이 언제나 기계의 로컬 시각으로
해석된다. 설치 스크립트가 07:00 KST 를 로컬 시각으로 환산해 채운다 — 이 저장소를
돌리는 기계가 KST 에 있지 않을 수 있고, 실제로 지금 그렇다(America/Los_Angeles).

### 재확인 창 — 7일

**두 가지를 동시에 커버한다.** (1) 노트북이 꺼져 있던 날 따라잡기 — 주말과 연휴가
겹치면 연속 미실행이 3~5일까지 간다. (2) 등재 지연 흡수 — 측정값이 없으므로 하루를
가정하지 않는다.

**비용이 작아서 크게 잡을 수 있다.** 하루 비용은 카나리아 1회 + 폴링 7회 ≈ 8회이고,
이미 처리한 MST 는 DB 조회로 걸러져 본문 수집이 일어나지 않는다.

**더 크게 잡지 않는 이유**는 회수 가능 구간이 흐려지기 때문이다. 7일을 넘겨 빈 구간은
회수 대상이 아니라 **미실행 기록**이어야 하고, `ops summary` 가 그것을 미실행 일수로
보고한다. 장기 부재에는 `--days` 로 명시적으로 늘린다.

### 실행 이력을 `load_run` 에 담지 않는 이유

`load_run` 은 **스냅샷 하나의 적재 완료 표시**다. 행의 존재가 곧 완료를 의미하도록
설계했고(`completed_at NOT NULL`), 그래서 **실패한 실행은 행이 아예 없다.** 실패
행을 허용하면 그 계약이 깨지고 기존 조회(고아 문서 탐지)가 조용히 틀린다. 그리고
하루 실행 하나가 `load_run` 을 여러 개 만든다 — 실행 단위가 아니다.

### 연속 0건 알람의 `N` = 60일 — ADR-005 가 남긴 TODO 의 해소

ADR-005 는 "연속 N일 0건이면 알람"을 방어 4로 정해 놓고 **N 을 비워 두었다**
(`silent-undercounting.md`: "근거 없이 정하지 않았다"). 이제 근거가 있다.

12개월 전수 캐시(`data/frequency-cache`, 2025-08-01~2026-07-31)에서 활성 코퍼스
9개 법령의 개정일은 **14일**이고, 개정일 사이 간격은 다음과 같다.

```
7, 7, 8, 14, 14, 16, 19, 21, 28, 28, 34, 42, 49   (중앙값 19일, 최대 49일)
```

여기에 측정 구간 시작부터 첫 개정일(2025-09-23)까지 **53일**이 있는데, 이 구간은
좌측이 잘려 있어 실제 무개정 구간은 더 길었을 수 있다. 그래서 관측 최장(53일) 위의
첫 라운드 값인 **60일**로 잡는다.

**세는 단위는 달력일이 아니라 실행이다.** 노트북이 꺼져 있던 날은 0건 관측이
아니므로 세지 않는다. 대신 연속 0건 실행이 걸친 달력 구간을 함께 보고해, "3번
실행했는데 그 사이가 70일"인 상태가 숨지 않게 한다.

### 알림을 보내지 않는 이유

이메일·Slack 발송은 **외부 발송**이며 이 시스템에서 그것은 승인 절차와 `dispatch`
경계의 일이다(원칙 5). 운영 가시성을 얻자고 그 경계를 먼저 뚫지 않는다. 지금 필요한
것은 "값을 볼 수 있는가"이고 조회 명령이 그것을 만족한다.

## 트레이드오프

**포기한 것 1 — 0건인 날의 응답 원문.** 폴링 응답 스냅샷은 **새로 처리할 MST 가 있는
날짜에만** 쓴다. 매일 7일치를 저장하면 거의 같은 내용이 7배로 쌓인다(일자별 응답이
하루 180KB~2.7MB이므로 연 수백 MB). 그 대가로 "그날 정말 0건이었나"를 원문으로
증명할 수 없고 `total_count` 기록과 `confirm_zero` 재요청에 의존한다. 0건 판정의
방어를 응답 보관이 아니라 재요청에 둔 ADR-005 의 설계와 같은 방향이다.

**포기한 것 2 — 프로세스가 SIGKILL 로 죽은 날.** 실행 행을 끝에 한 번 쓰므로 그런
날은 행이 없고 "실행하지 않은 날"과 같은 모양이 된다. 시작 시점에 행을 쓰고 끝에
갱신하면 그 창이 닫히지만 **UPDATE 를 허용해야 한다** — 운영 실적을 사후에 고칠 수
있게 만드는 대가가 더 크다. 래퍼 스크립트의 파일 로그가 그 창의 2차 흔적이다.

**포기한 것 3 — 즉시성.** 하루 1회 폴링이므로 공포 후 최대 하루 이상 늦게 안다.
이 도메인에서 규제 대응 리드타임은 주 단위이므로 감수한다.

**얻은 것** — 운영 실적이 질의로 재현된다. 같은 질문에 항상 같은 답이 나온다.

### 이 선택이 틀렸음을 알게 되는 신호

- `ops summary` 의 미실행 일수가 실행일수를 넘는다 → 노트북 운영의 한계이며 배포를
  앞당길 근거다.
- 재확인 창(7일) 밖에서 등재된 개정이 발견된다 → 창을 늘릴 것이 아니라 **등재 지연을
  측정**해야 한다는 신호다.
- 연속 0건 알람이 오탐으로 반복 발화한다 → 60일 근거가 된 분포가 코퍼스 변경으로
  낡았다는 뜻이다. 재산정한다.
- `ops_run` 을 조회하는 사람이 아무도 없다 → 조회 명령이 알림을 대신할 수 있다는
  전제가 틀렸다. 그때 발송을 다시 검토한다.

### 되돌리는 비용

**비대칭이다.**

- **스케줄러 교체(launchd → cron/EventBridge)**: 싸다. plist 하나와 셸 래퍼 하나이며
  실행 로직은 CLI 안에 있다.
- **테이블 폐기**: 비싸다. 원칙 6 상 과거 행을 지우지 않으므로 폐기가 아니라 사용
  중단이며, 그때까지 쌓인 운영 실적의 해석이 두 체계로 갈린다.
- **재확인 창 변경**: 공짜다. `--days` 기본값 하나다.

## 제품 철학과의 연결

이 결정은 "읽고 · 보고 · 결정" 중 **읽고**에 해당한다. 매일 도는 것은 수집과 비교뿐이고,
포착된 변경은 `change_set` 으로 남을 뿐 아무에게도 통지되지 않으며 어떤 정책도 바뀌지
않는다.

**뒤집으면 어떻게 되는가.** 알림을 자동 발송으로 만들면 시스템이 "이것은 담당자가
지금 봐야 하는 변경이다"를 대신 판단하게 된다. 그 판단이 반복되면 담당자는 알림이
오지 않은 개정을 "없었던 것"으로 다루기 시작한다 — 시스템이 검토 여부를 대신 결정한
것이다. 조회 명령은 사람이 물었을 때만 답한다.

## 축 연결

- **축 3 (운영)** — 이 ADR 의 본체다. 운영 실적이 여기서 시작된다.
- **축 2 (환경)** — 부분적. 스케줄러·로그·실행 이력이라는 형태는 은행 환경에서도
  같지만, 노트북 운영 자체는 그 환경의 증명이 아니다.
- **축 1 (업무)** — 기여하지 않는다. 담당자가 보는 것이 아직 없다.

## 엣지 케이스

- **카나리아 실패** → 폴링하지 않고 `SKIPPED_CANARY_FAILED`. fail-closed 다.
  0으로 기록하면 그 0이 "개정 없음"으로 흘러가기 때문이다(ADR-005).
- **한 법령 실패** → 그 법령만 `FAILED` 로 남기고 나머지는 계속 처리한다. 실행 상태는
  `PARTIAL`. 하루치를 통째로 잃지 않기 위해서다.
- **기반 실패(저장소·DB)** → 예외가 CLI 까지 올라가고 **실패 행을 남긴 뒤** 비-0 으로
  끝낸다. "실패한 날"과 "실행하지 않은 날"은 조치가 다르다.
- **같은 날짜 재처리** → 멱등이다. 이미 처리한 MST 는 `SKIPPED_DONE` 으로 끝나고 API
  호출이 일어나지 않는다.
- **실패한 법령의 재시도** → 다음 실행이 자동으로 다시 시도한다. 재시도 상한은 두지
  않았다 — **기록이 우선이고 재시도 강화는 하지 않는다.** 같은 사유가 며칠 연속
  남으면 그것이 사람이 봐야 한다는 신호다.
- **macOS 보호 디렉터리** → 저장소가 `~/Documents` 아래에 있으면 launchd 가 띄운
  프로세스가 스크립트를 **실행**하지 못한다(TCC, exit 126). 읽기는 되는데 실행이
  막혀 원인이 보이지 않는다. 설치 스크립트가 이 조건을 감지해 경고하며, 해소는
  `/bin/bash` 에 전체 디스크 접근 권한을 주거나 저장소를 옮기는 것이다.
  `docs/06-runbook.md` §7 참조.
