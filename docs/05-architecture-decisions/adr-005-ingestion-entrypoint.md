## 맥락

당초 가정은 **문서 수준 `시행일자`를 `valid_from`으로 쓰고 본문 API를 폴링한다**였다.
실측 결과 두 곳에서 틀렸다.

### 근거 1 — `regDt`는 공포일자다 (0.8단계 실측)

`lsJoHstInf`의 `regDt`는 **공포일자**다. 응답 안의 `공포일자`와 `조문개정일`이 전부 요청한
`regDt`와 일치한다 — 2026-01-06 응답의 법령 30건 전원 공포일자 20260106, 조문 206건 전원
조문개정일 20260106 (`amendment-frequency.md` §0).

**공포와 시행은 몇 달 차이가 날 수 있다.** 사용자에게 가치 있는 것은 "공포되었고 앞으로
시행될 것"이다. **시행일에 알림을 받으면 이미 늦다** — 그때는 대응할 시간이 없다.
따라서 D-day 카운트다운이 검토 큐의 핵심 요소가 된다.

### 근거 2 — 조문별 시행일은 본문 API에서 평탄화된다

- 본문 API(`law`, `eflaw`)의 `조문시행일자`는 **모든 조문이 문서 `시행일자`와 같은 값**을
  갖는다. 본문/eflaw 픽스처 13개 전부에서 종류가 1개다 (spec §4.6).
- 같은 MST를 `efYd` 3개로 조회해도 46개 조문이 각각 그 `efYd` 하나로 평탄화된다
  (`eflaw_009256_mst261379_ef20240326.xml` / `_ef20240627.xml` / `_ef20240719.xml`).
- **조문별 시행일 분기는 실재한다.** `dayjochg_regdt20250401.xml`에서 83개 법령 중
  **17개**가 문서 시행일자 ≠ 조문시행일이다. 아동복지법은 한 공포에 시행일이 3종
  (20250401 / 20251002 / 20260402)이다 (spec §5.2).

→ **`valid_from`은 반드시 이력 API에서 가져온다.** 본문 API만 쓰면 원칙 6의 `valid_time`이
문서 수준으로 뭉개져 "그 시점에 알 수 있었던 정보"의 재구성이 틀린다 (edge-case #8).

> **근거 정정 (2026-08-17) — 전제가 부정확했으나 결론은 유지된다.**
>
> 위 서술은 "본문 API는 조문별 시행일을 제공하지 않는다"로 읽혔고, 실제로 작업 3의
> `valid_from` 보류 결정이 그 전제 위에서 내려졌다. **그 전제가 부정확하다.**
>
> XML 속성 전수 점검에서 `<기본정보>`의 **`<조문시행일자문자열>`**이 발견됐다. 본문
> 픽스처 13개 중 8개가 가지며 8개 전부 값이 있고, `20251216:제42조제3항,제42조의2제1항`
> 형태로 **조문별 시행일 분기를 담는다.** 조문 단위 `<조문시행일자>` 태그가 평탄화된다는
> 서술은 그대로 맞다 — 분기가 **다른 필드에** 있었다.
>
> **정확히 고쳐 쓰면**: 본문 API의 조문 단위 태그는 평탄화되며, `<기본정보>`의 요약
> 문자열은 자유 텍스트이고 입도가 조문 단위와 맞지 않는다(항·호·단서까지 내려간다).
> **구조화된 조문별 시행일은 이력 API에만 있다.**
>
> **결론이 유지되는 이유**: 요약 문자열을 파싱해 `valid_from`을 채우는 것은 ADR-007의
> `PARSED` 등급 값을 bitemporal의 핵심 축에 넣는 일이다. 이동 표기 정규식이 조사 하나를
> 놓쳐 53건을 누락한 전례(사건 3)가 있는 종류의 값이며, `valid_from`은 그 위험을 감수할
> 자리가 아니다. 원문만 보관한다(`regulation_document.article_effective_dates_raw`).
>
> **전제가 틀렸는데 결론이 유지되는지를 따진 기록**이라는 점에서 ADR-003의 "근거 정정
> 이력"과 같은 성질이다. 근거가 바뀌면 결론을 다시 검사한다 — 유지되더라도 검사는 한다.
>
> 부수 효과: 이 필드가 **이력 API 결합의 대조 근거**가 된다. 플래그가 켜진 문서에서
> 이력이 분기를 주지 않으면 그 자체가 조사 신호다.

### 근거 3 — `lsHstInf`는 교차검증에 쓸 수 없다

`lsHstInf`의 `regDt`는 공포일자가 **아니다.** `regDt=20260105`로 조회한 34건의 공포일자가
20251230 · 20260106 · 20260102 · 20250224로 제각각이다. 법제처 DB 등록일로 보이나
**확정하지 못했다 — 미확인** (`amendment-frequency.md` §0).

**다만 버리지 않는다.** 공포일과 등록일의 차이는 **우리가 통제할 수 없는 인지 지연의
하한선**이다. "개정을 며칠 만에 포착했는가"를 KPI로 쓸 때 이 지연을 우리 성능에서 분리해야
한다. 이 값을 측정하지 않으면 법제처의 등록 지연이 우리 지표로 잘못 계상된다.

### 변경이력 API 3종 (실측 확정)

| API | endpoint | target | 필수 |
|---|---|---|---|
| 법령 변경이력 목록 | lawSearch.do | `lsHstInf` | `regDt` |
| 일자별 조문 개정 이력 | lawSearch.do | `lsJoHstInf` | `regDt` |
| 조문별 변경 이력 | **lawService.do** | `lsJoHstInf` | `ID` + `JO` |

같은 target이 endpoint로 갈리고 응답 스키마도 다르다 — 일자별은 `조문정보/jo` 반복,
조문별은 `조문정보` 단일이다 (spec §5.2, §5.3).
`lsHistory`(법령 연혁)는 이 OC로 **미신청**이다 (`error_target_lsHistory.html`).

### 본문 플래그와 변경이력 API의 차이

본문의 `조문변경여부`는 "이번 버전에서 바뀐 조문인가"만 알려준다. 변경이력 API는 역대 이력 +
사유 구분 + 조문별 시행일을 준다. **그러나 둘 다 "무엇이 어떻게 바뀌었는지"는 주지 않는다** —
원칙 1(결정론적 diff)이 필요한 이유가 실측으로 확인된 지점이다.

## 결정

```
[트랙 1] 공포 감지 (외부 API)
  lsJoHstInf(regDt=오늘)
    → 감시 대상 필터 (config/corpus.yaml, 법령ID 기준)
    → 본문 fetch (law + eflaw)
    → 결합: 본문 API = 텍스트, 이력 API = 조문별 시행일(valid_from)
    → 영향평가
    → "시행일 D-N, 준비 필요" 큐

[트랙 2] 시행일 도래 감시 (내부 DB, API 아님)
  매일 valid_from == 오늘 인 조문 조회
    → "오늘 시행됨. 조치가 완료되었는가" 확인 큐
```

트랙 2는 **외부 API를 호출하지 않는다.** 트랙 1이 이미 저장해 둔 `valid_from`을 읽을 뿐이다.

## 목적

개정을 놓치지 않고 포착하되, **시행 전에 준비할 시간을 확보**하고, 각 조문이 언제부터
효력을 갖는지를 조문 단위로 정확히 기록한다.

## 구현 이유

| 대안 | 장점 | 택하지 않은 이유 |
|---|---|---|
| 본문 API 전수 폴링 | API 하나만 씀 | 감시 대상 전부의 본문을 매일 받아야 한다(자본시장법 2.1MB/6.1초, spec §7.5). 그리고 **`valid_from`을 조문 단위로 채울 수 없다** |
| `lsHstInf` 진입 | 그날 바뀐 법령 목록을 바로 줌 | **조문 수준 정보가 없다**(spec §5.1). `regDt` 의미도 다르다 |
| `조문별 변경 이력` 진입 | 조문 단위로 정밀 | 조문을 미리 알아야 조회할 수 있어 진입점이 될 수 없다 |
| 시행일만 감시 (트랙 2 단독) | 단순 | **시행일에 알면 늦다.** 준비 기간이 0이 된다 |
| **공포 감지 + 시행일 감시 이원** (채택) | 준비 기간 확보 + 시행 시점 확인 | 두 트랙을 유지해야 한다 |

트랙 2를 따로 두는 이유는, 공포 시점에 만든 큐 항목이 **시행일까지 방치될 수 있기**
때문이다. D-90에 "준비 필요"로 올라온 항목이 D-0에 조치되었는지 확인하는 것은 다른 질문이다.
트랙 1이 "무엇을 준비해야 하는가", 트랙 2가 "준비되었는가"를 묻는다.

## 제품 철학과의 연결

이 결정은 **"보고 → 결정" 사이에 시간을 만든다.** 공포 즉시 알리고 시행일까지 D-day를
세어 주면, 담당자는 판단할 시간을 갖는다. 시행일에 알리면 담당자에게 남는 선택지는
"급히 무언가 하기"뿐이고, 그때 시스템이 제시한 초안을 그대로 쓰게 된다 — 검토 없는 채택은
시스템이 선택을 대신한 것과 같다.

R-11(조용한 실패) 방어도 같은 성질이다. 수집이 실패했는데 "그날 개정 없음"으로 보이면,
담당자는 **확인할 것이 없다고 잘못 안다.** 시스템이 "아무 일도 없었다"는 판단을 대신
내려 버린 것이다. 그래서 아래 카나리아는 **실패 시 0으로 기록하는 대신 수집 자체를 하지
않는다** — 모르는 것을 안다고 말하지 않기 위해서다.

## 트레이드오프

**포기한 것**

- 소스가 둘(이력 + 본문)이라 결합 로직이 필요하고, 한쪽만 성공한 부분 상태를 다뤄야 한다.
- 트랙이 둘이라 스케줄러와 큐가 각각 있어야 한다.
- 매일 폴링이므로 개정 인지가 최대 1일 지연된다. 실시간 알림 수단은 API에 없다.
- 이력 API에 나타나지 않는 변경은 감지하지 못한다. 무엇이 누락되는지는 **미확인**
  (`amendment-frequency.md` §E-2).

**얻은 것**

`valid_from`이 조문 단위로 정확해지고, 시행 전 준비 기간이 확보된다. 감시 대상 전체 본문을
매일 받지 않아도 된다.

**이 선택이 틀렸음을 알게 되는 신호**

1. **이력 API가 잡지 못한 개정을 담당자가 다른 경로로 먼저 안다.** 진입점이 불완전하다는
   결정적 신호다. `lsHstInf`를 보조 진입점으로 추가하거나 본문 전수 대조 주기를 둔다.
2. **이력 API의 `조문시행일`과 본문 API의 `조문시행일자`가 자주 어긋난다.** 결합 규칙의
   전제(이력 쪽이 정확하다)가 틀렸을 수 있다.
3. **연속 N일 0건이 반복된다.** (아래 3-4번 장치)
4. **트랙 2의 큐가 항상 비어 있거나 항상 가득 차 있다.** 전자는 `valid_from`이 잘못 채워진
   것이고, 후자는 트랙 1의 조치가 실제로 이루어지지 않는다는 뜻이다.
5. **본문 fetch 실패율이 높다.** 대형 법령의 응답 시간이 타임아웃에 걸리면 결합이 반쪽으로
   남는다.

**되돌리는 비용**

| 방향 | 비용 |
|---|---|
| 진입점 교체(이력 → 본문 전수) | **중간.** 스케줄러와 결합 로직을 다시 쓰지만 스키마는 그대로다. 다만 **과거에 이력 API로 채운 `valid_from`은 본문 API로 재현되지 않는다**(평탄화되므로). 원칙 6상 과거 행을 고칠 수 없어 경계 시점 전후의 `valid_from` 의미가 달라진다 — 이 불연속이 실질 비용이다 |
| 보조 진입점 추가(`lsHstInf` 병행) | **싸다.** 기존 경로를 건드리지 않고 덧붙인다 |
| 트랙 2 제거 | **싸다.** 내부 DB 조회일 뿐이다. 단 "준비되었는가"를 묻는 주체가 사라진다 |

## 엣지 케이스

### R-11 — 조용한 수집 실패 (최우선)

`lsJoHstInf`는 성공 응답에 **`resultCode`·`page`·`numOfRows`가 없다.** 정상 0건과 요청
실패가 **바이트 단위로 동일하다**:

```xml
<LawSearch><target>lsJoHstInf</target><totalCnt>0</totalCnt></LawSearch>
```

**edge-case #10의 `resultCode` 기반 분류를 이 API에는 적용할 수 없다.**
파라미터 오류가 `totalCnt=0`으로 오면 **수집 실패가 "그날 개정 없음"으로 위장한다.**
규제 준수 시스템에서 조용한 실패는 오답보다 나쁘다 (CLAUDE.md §4).

4중 방어:

1. **응답 형태 분류** — 빈 본문 / HTML / 루트 태그 불일치 / XML 파싱 실패를 각각 실패로
   기록한다. 정상 외 전부를 실패로 취급한다.
2. **0건 재요청 확인** — 0건인 날은 독립적으로 한 번 더 요청해 같은 0인지 확인한다.
3. **카나리아 — 매 수집 실행마다** 알려진 비-0 날짜를 호출한다. 실패하면 **그날 수집을
   아예 하지 않는다.** 0으로 기록하는 것보다 "수집 안 함"이 안전하다.
   (0.8단계에서는 30일 주기로 14회 호출해 전부 통과했다. 운영에서는 매 실행으로 강화한다.)
4. **연속 N일 0건이면 알람** — 형태 분류가 놓친 실패는 결국 "매일 0건"으로 나타난다.
   > **TODO(verify)**: `N`의 값이 정해지지 않았다. CLAUDE.md §4는 매직 넘버를 금지한다.
   > 관측 근거는 있다 — 12개월 중 0건인 날이 **161일**이고
   > (`amendment-frequency.md` §0), 공포가 특정 요일에 몰려 0건이 정상적으로 흔하다.
   > 감시 대상 법령만 놓고 보면 0건인 날이 훨씬 많다. 코퍼스별 개정 빈도 분포를 본 뒤
   > 정한다. 이 ADR에서 임의로 정하지 않았다.

### 페이지네이션

`display` 기본값은 20이고 **잘렸다는 표시가 응답에 없다.** `jochg_009244_jo000200.xml`은
`totalCnt=28`인데 20건만 담고 있다 (edge-case #11).

- `totalCnt`(= 법령 수)와 누적 수신 건수를 대조해 전부 받을 때까지 페이지를 넘긴다.
  불일치 상태로 끝나면 실패로 처리한다.
- 활용가이드는 `display` 최대 100이라 하나 실측은 1000도 반환한다(spec §7.1).
  **문서화되지 않은 동작에 의존하지 않는다.**
- 이 함정은 0.8단계 집계 자체를 오염시킨 적이 있다 — `display=100`으로 `변경사유` 어휘를
  세어 4종으로 결론냈다가, 1000으로 다시 받으니 6종이었다.

### 그 밖

- **감시 대상 지정**: 법령명 검색은 예상 밖 결과를 반환한다 — `query=은행법`이
  상호저축은행법을 먼저 반환한다 (edge-case #19). **`법령ID`로 고정**한다
  (`config/corpus.yaml`). 0.8단계에서 `eflaw` 검색 결과를 법률로 착각해 시행령
  (법령ID 009256) 픽스처에 본법 번호를 붙인 사고가 있었다 — 이 함정은 가설이 아니다.
- **부분 수집**: 이력은 받았는데 본문 fetch가 실패한 경우 부분 상태를 정상으로 커밋하지
  않는다. 부분 상태는 diff를 "대량 삭제"로 오판하게 만든다.
- **조문 0건 수집**: 성공이 아니라 실패로 취급한다.
- **같은 날 같은 법령ID가 `<law>`로 두 번 이상 나타난다 (48건)** — **중복이 아니다.**
  12개월 전수에서 48건이 관측되며(`amendment-frequency.md` §A-1), 2026-08-12 재계산에서
  같은 48건이 재현되었다. 그런데 **48건 중 같은 MST가 반복된 그룹은 0개다.** 47개 그룹
  전부 MST가 다르며, 하루에 같은 법령이 두 번 공포·등록된 것이다. 각자 자기 시행일자를
  가진다.
  → **법령ID로 중복 제거하면 안 된다. 식별키는 MST를 포함해야 한다.**
  조문 단위로도 진짜 중복은 35,681행에서 **0건**이다. 자세한 구분과 계열별 식별키는
  edge-case #18.
- **스파이크 부하**: 하루 최대 법령 1,464건 · 조문 15,528건(2025-10-01)이 관측됐다.
  평균(26.7 / 174.9)의 55~89배다 (`amendment-frequency.md` §A-2). 부하 설계는 ADR-008.
- **OC 마스킹**: 응답의 `조문링크`·`조문변경이력상세링크`에 요청 OC가 echo된다
  (edge-case #1). 저장·로깅 이전에 마스킹하며 실패 시 저장을 거부한다.
  근거는 `docs/security-notes.md`.
- **호출 간격**: 1.2초 간격 540여 회에서 실패 0건. **rate limit의 실제 한계는 미확인.**
- **인코딩 선언**: `UTF-8`/`utf-8`이 API마다 다르다 (edge-case #15). 선언을 로직에 쓰지
  않고 UTF-8로 고정 해석한다.

## 정정 이력

### 2026-08-12 — 이 ADR의 엣지 케이스가 이 ADR의 결정을 파괴하고 있었다

초기 엣지 케이스 목록에 **"적재 전 중복 제거 기준이 필요하다"**가 있었다
(edge-case #18과 같은 지시).

**그 지시를 그대로 구현했다면 조문 단위 `valid_from`이 소실된다.** "중복"으로 보였던
행들이 실제로는 **같은 공포(MST)가 조문을 여러 시점에 나누어 시행한 기록**이었고,
서로 다른 `조문변경일`/`조문시행일`을 담고 있었다.

이는 **이 ADR이 존재하는 이유를 정면으로 파괴한다** — 근거 2가 "본문 API는 조문별
시행일을 문서 시행일로 평탄화하므로 `valid_from`은 반드시 이력 API에서 가져온다"고
결정했는데, 그렇게 가져온 값을 각주가 지우라고 지시하고 있었다.

**ADR의 결정과 그 엣지 케이스가 서로 모순될 수 있다. 엣지 케이스 목록도 검증 대상이다.**

발견 경위는 edge-case #18 자신이 요구한 "제거 전에 필드 단위로 무엇이 다른지 확인한다"를
실행한 것이다. 문서가 자기 검증 조건을 갖고 있었고 그것이 작동했다
(`docs/incidents/silent-undercounting.md` "미수 2", "문서도 실패면이다").

정정 내용은 위 엣지 케이스 절과 edge-case #18에 있다.
