## 맥락

법제처 법령 본문 API는 각 조문에 `조문키`를 준다. 그대로 기본키로 쓰는 것이 가장 단순한
설계이며, 0.7단계 실측 전까지는 그럴 계획이었다.

실측에서 두 가지가 드러났다.

**조문키의 구성 규칙은 확실하다.** 7자리 = `[조문번호 4][가지번호 2][유형 1]`이며,
`scripts/exploration/analyze_articles.py`가 `조문번호`·`조문가지번호`·유형 자리로 키를
재구성해 원본과 대조한 결과 **4개 법령 1,189개 조문에서 불일치 0건**이다
(`law_009244_mst252787.xml` 34, `law_010199_mst280277.xml` 80,
`law_001565_mst280405.xml` 393, `law_010513_mst283193.xml` 682 — spec §4.2).
유형 자리는 `0`=편장절관 제목행(`조문여부="전문"`), `1`=조문 본체다.
최대 조문번호 449(자본시장법), 최대 가지번호 27(소득세법)이 관측됐다.

**그럼에도 조문키는 유일하지 않다.** 편장절관 제목행은 뒤따르는 조문의 키를 공유하므로,
한 조문 앞에 여러 계층 제목이 붙으면 같은 키가 중복된다.
`law_010513_mst283193.xml`에서 `0011000`이 3회 나타난다 — "제2편 금융투자업",
"제1장 금융투자업의 인가 및 등록", "제1절 인가요건 및 절차".
`law_001565_mst280405.xml`에서는 `0012000`·`0014000`이 각각 2회다 (edge-case #2).

또한 조문키는 자식 태그가 아니라 `<조문단위>`의 **XML 속성**이다
(`<조문단위 조문키="0008001">`). 태그만 순회하는 파서는 이 값을 통째로 놓친다.

이 결정을 미룰 수 없는 이유: 조문 식별자는 인용 대상 ID의 출처가 된다. 스키마를 만든 뒤에
바꾸면 이미 발급된 인용이 전부 무효가 되고, 원칙 6에 따라 과거 레코드를 UPDATE할 수 없어
되돌릴 방법이 사실상 없다.

## 결정

```sql
id           uuid PRIMARY KEY,
document_id  uuid NOT NULL,          -- 법령 버전(MST) 단위 문서
article_key  char(7) NOT NULL,       -- 법제처 조문키 (원본 그대로)
seq_in_doc   int NOT NULL,           -- 문서 내 등장 순번 (0부터)
unit_type    text NOT NULL,          -- 'ARTICLE' | 'HEADING'
article_no   int NOT NULL,           -- 조문번호 (정수)
branch_no    int NOT NULL DEFAULT 0, -- 가지번호 (없으면 0)
UNIQUE (document_id, article_key, seq_in_doc)
```

- `unit_type='ARTICLE'`은 유형 자리 `1`, `'HEADING'`은 `0`에 대응한다.
- **인용 대상이 될 수 있는 것은 `unit_type='ARTICLE'` 뿐이다.**
- `"제5조의2"`는 저장 값이 아니라 `article_no`/`branch_no`로부터의 **렌더링 결과**다.

---

## 목적

조문 하나를 시스템 전체에서 하나의 값으로 가리킬 수 있게 하고, 그 값이 법제처의 식별자
체계가 흔들려도 바뀌지 않게 한다. 인용이 가리키는 대상이 모호해지는 경로를 스키마 수준에서
차단한다.

---

## 구현 이유

| 대안 | 장점 | 택하지 않은 이유 |
|---|---|---|
| `조문키` 단독 PK | 가장 단순 | **중복된다.** 자본시장법 `0011000` 3회. 적재가 실패하거나, upsert면 제목행이 서로를 덮어써 계층 정보가 소실된다 |
| `(document_id, 조문키)` 복합 PK | 문서 단위로는 유일해 보임 | 중복이 **같은 문서 안에서** 발생하므로 해결되지 않는다 |
| `(document_id, 조문키, seq_in_doc)` 복합 PK | 유일성 확보 | PK가 3컬럼이라 인용·임베딩·감사 로그가 전부 3컬럼 FK를 들고 다녀야 한다. 자연키 정의가 바뀌면 참조 전체가 깨진다 |
| **uuid 대리키 + 자연키 UNIQUE** (채택) | 참조가 1컬럼. 자연키 규칙이 바뀌어도 참조는 그대로 | 자연키로 조회할 때 조인이 한 번 더 필요 |

`seq_in_doc`을 유니크 제약에 넣는 이유는 중복 조문키를 구분할 수 있는 값이 문서 내 등장
순서뿐이기 때문이다. 편장절관 계층은 XML 구조가 아니라 `조문내용` 텍스트로만 표현되므로
(edge-case #9), 계층으로 구분하려면 **텍스트 파싱 결과에 유니크 제약을 거는 셈**이 된다 —
파서가 흔들리면 제약이 흔들린다. 순번은 파싱 규칙과 무관하게 안정적이다.

`unit_type`을 컬럼으로 승격하는 이유는 조문 본체와 제목행이 **다른 종류**이기 때문이다.
유형 자리를 매번 문자열에서 잘라 쓰면 `article_key[6] == '1'` 같은 조건이 코드 곳곳에
흩어지고, 하나를 빠뜨리면 제목행이 인용 대상 후보에 섞인다.

## 제품 철학과의 연결

인용은 담당자가 **직접 확인하러 가는 좌표**다. 좌표가 모호하면 담당자는 확인을 포기하고
시스템의 말을 믿게 된다 — 그 순간 시스템이 판단을 대신하기 시작한다.

이 결정을 뒤집어 조문키를 단독 PK로 쓰면, 제목행이 서로를 덮어쓰면서 "제2편"과 "제1절"이
같은 레코드가 된다. 인용이 가리키는 위치가 실제와 어긋나도 시스템은 아무 경고를 내지
않는다. 담당자는 확인 불가능한 좌표를 받고, 확인을 포기하고, **선택을 시스템에 넘긴다.**

## 트레이드오프

**포기한 것**

- 자연키만으로 조회할 때 조인이 한 번 더 든다.
- uuid는 정수 PK보다 인덱스가 크고 지역성이 나쁘다.
- `seq_in_doc`은 법제처가 주는 값이 아니라 **우리가 파싱 순서로 부여하는 값**이다.
  파서가 조문 순서를 다르게 읽으면 같은 조문이 다른 순번을 받는다.
  (같은 계열의 문제를 ADR-007이 `article_key_source`로 다룬다.)

**얻은 것**

외부 식별자를 원본 그대로 보존하면서(`article_key`), 참조는 1컬럼으로 유지한다.
감사에서 "법제처 조문키 몇 번인가"를 물으면 그대로 답할 수 있다.

**이 선택이 틀렸음을 알게 되는 신호**

1. `UNIQUE (document_id, article_key, seq_in_doc)` 위반이 적재 중 발생한다.
   → 파서가 순번을 잘못 부여하고 있다.
2. `unit_type='HEADING'` 레코드가 인용 대상으로 조회되는 코드 경로가 발견된다.
   → 인용 후보 필터가 한 곳에 모여 있지 않다.
3. 연속된 두 버전에서 **내용이 같은 조문의 `seq_in_doc`이 크게 흔들린다.**
   → 순번이 안정적 보조 식별값이라는 전제가 깨진 것이며, ADR-003의 위치 신호에도 영향이 간다.
4. `article_no`가 9999를 넘는 법령이 나타난다.

**되돌리는 비용**

| 되돌릴 대상 | 비용 |
|---|---|
| 대리키 → 자연키 복합 PK | **매우 비싸다.** 모든 참조 테이블 FK를 3컬럼으로 넓혀야 하고, 발급된 인용 ID가 전부 무효가 된다. 원칙 6에 따라 UPDATE가 불가하므로 마이그레이션이 아니라 **재적재**다 |
| `unit_type`·`article_no`·`branch_no` 추가/제거 | **싸다.** `article_key`에서 파생 가능하므로 재계산으로 복구된다 |
| `seq_in_doc` 정의 변경 | **중간.** 유니크 제약을 잠시 내리고 재적재하면 복구된다 |

되돌리기 비싼 것은 "대리키를 쓴다" 하나뿐이고, 그 결정은 **중복 조문키라는 실측 사실에
의해 강제된 것**이라 선택지가 넓지 않았다.

## 엣지 케이스

- **조문키 중복**: `seq_in_doc`이 구분한다. 자본시장법 `0011000` 3행은 순번 0·1·2로
  저장되고 셋 다 `unit_type='HEADING'`이다 (`law_010513_mst283193.xml`).
- **조문번호 4자리 초과**: `f"{no:04d}"`가 5자리를 만들어 7자리 가정이 무너지고 유형 자리
  위치가 밀린다. **현재 미관측**(최대 449). 적재 시 `len(article_key)==7`과 재구성 일치를
  검사해 즉시 실패로 드러낸다. 조용히 잘라내지 않는다.
- **가지번호 2자리 초과**: 위와 같은 실패 경로. **현재 미관측**(최대 27).
- **유형 자리에 `0`/`1` 외의 값**: 예외를 던진다. 기본값으로 `'ARTICLE'`을 넣지 않는다 —
  알 수 없는 유형이 인용 후보에 섞이면 원칙 2가 무력해진다. **현재 미관측.**
- **`조문가지번호` 태그가 없는 조문**: 가지번호 0으로 저장한다. 특금법 34개 중 7개만 이
  태그를 갖는다 (`law_009244_mst252787.xml`).
- **조문키가 XML 속성**: 태그만 순회하는 파서는 값을 놓쳐 `article_key`가 빈다.
  NOT NULL 제약으로 적재 시점에 드러낸다.
- **행정규칙**: `조문키`·`조문번호`가 **아예 없다** (spec §6.1 — `<조문내용>` 202개,
  XML 속성 0개). 이 스키마를 그대로 적용할 수 없으며 ADR-006·ADR-007이 다룬다.
