## 맥락

금융권 도입 시 **배포 형태가 규제 심의 결과에 따라 결정된다.** 우리가 고르는 것이 아니다.

전자금융감독규정은 클라우드 이용 시 중요도 평가, CSP(클라우드 서비스 제공자) 평가,
안전성 확보조치를 요구하고, 정보보호위원회 심의·의결과 금융감독원 보고 절차를 둔다.
그 심의 결과에 따라 LLM 호출 경로가 사내 GPU / 전용 리전 / SaaS 중 무엇이 될지가 갈린다.

## 결정

6개 인터페이스를 두고 **AWS 구현체만 만든다. 온프렘 구현체는 만들지 않는다.**

```
adapters/
├─ llm/        LLMGateway         → Bedrock | vLLM | SaaS
├─ storage/    DocumentStore      → S3 | MinIO | EDMS
├─ queue/      TaskQueue          → SQS | RabbitMQ | Kafka
├─ secrets/    SecretProvider     → Secrets Manager | Vault
├─ approval/   ApprovalGateway    → 내부DB | 전자결재 연동
└─ identity/   IdentityProvider   → Cognito | AD/SSO
```

**강제 방법**: `import-linter` 계약으로 도메인 코드가 구체 구현을 import하지 못하게 한다.

---

## 목적

**규제 심의 결과가 도메인 로직에 파급되지 않게 한다.** 배포 형태가 바뀌어도 바뀌는 것이
어댑터 구현체 하나로 끝나야 한다.

---

## 구현 이유

### "확장성을 위해"가 아니다

인터페이스를 두는 흔한 이유는 "나중에 바꿀 수도 있으니까"이고, 그것은 대개 과잉설계다.
**이 결정의 근거는 다르다** — 배포 형태를 우리가 정하지 않는다는 것이 이미 정해진 사실이다.
심의 결과는 조직 밖에서 온다.

| 대안 | 장점 | 택하지 않은 이유 |
|---|---|---|
| 구현체 직접 사용(인터페이스 없음) | 코드가 짧다 | 심의 결과가 바뀌면 도메인 로직 전반을 고쳐야 한다. 그 시점은 우리가 통제할 수 없다 |
| 인터페이스 + 온프렘 구현체까지 미리 작성 | 전환이 즉시 가능 | 검증할 수 없는 구현체를 유지해야 한다. 쓰이지 않는 코드는 썩는다 |
| **인터페이스 + AWS 구현체만** (채택) | 경계는 서되 코드는 최소 | 인터페이스가 실제로 교체 가능한지 두 번째 구현체가 나오기 전까지 검증되지 않는다 |

### `approval/`이 특히 중요하다

**은행에서 "승인"은 우리 화면의 버튼이 아니다.** 전자결재의 기안 → 검토 → 승인 라인이며,
전결 규정과 대결(대리 결재)이 있다. 지금은 내부 DB 구현이지만, 인터페이스가 있으면 실무
도입 시 교체만 하면 된다.

인터페이스가 없으면 승인 로직이 우리 DB 스키마에 녹아들고, 전자결재 연동 시점에 원칙 4
(승인은 그래프 레벨)를 다시 설계해야 한다. **원칙 4는 "승인 지점이 우회 불가능하다"를
보장하지만, 승인의 실체가 무엇인지는 정하지 않는다.** 그 실체를 어댑터로 뺀다.

### `identity/`와 원칙 5

직무분리는 은행 IT의 기본 통제다. LLM 프로세스와 dispatch 워커가 서로 다른 주체로 동작해야
하며(원칙 5), 그 주체를 무엇이 발급하는지는 환경에 따라 다르다(Cognito / AD·SSO).

### 강제가 없으면 무너진다

**인터페이스만 있고 강제가 없으면 6주 뒤 무너진다.** 급할 때 도메인 코드에서 `boto3`를
직접 import하는 것이 가장 빠른 길이고, 리뷰가 매번 그것을 잡아내지 못한다.
`import-linter` 계약을 CI 게이트로 둔다 — CLAUDE.md §8의 의존 방향 규약
(`dispatch`는 `graph`·`prompts`·LLM 어댑터를 import하지 않는다)과 같은 자리에서 검사한다.

---

## 제품 철학과의 연결

직접적인 연결은 `approval/`에 있다. **승인은 "결정" 단계 그 자체다.** 승인의 실체가 우리
화면의 버튼으로 고정되면, 실제 조직의 결재선이 그 버튼으로 대체되거나 우회된다 — 어느 쪽이든
시스템이 조직의 의사결정 절차를 자기 형태로 바꾼 것이다. 어댑터는 **조직의 결정 방식을
시스템이 규정하지 않게** 한다.

이 결정을 뒤집어 승인을 내부 DB에 하드코딩하면, 도입 시 두 갈래가 된다: 조직이 절차를
바꾸거나(시스템이 조직을 대신 결정), 우리 승인이 형식적 절차가 되고 실제 결재는 밖에서
일어나거나(승인 게이트가 무의미해짐). 둘 다 실패다.

## 트레이드오프

**포기한 것**

- 추상화 비용. 호출 경로가 한 겹 늘고, 인터페이스를 유지해야 한다.
- **구현체가 하나뿐인 인터페이스는 과잉설계일 위험이 있다.** 두 번째 구현체가 나오기 전까지
  인터페이스가 실제로 교체 가능한지 검증되지 않는다 — 첫 교체 시점에 인터페이스가 잘못
  잡혔음을 발견할 수 있다.
- `import-linter` 계약 유지 비용.

**얻은 것**

심의 결과가 바뀌어도 도메인 로직을 고치지 않는다. 그리고 경계가 CI로 강제되므로 시간이
지나도 무너지지 않는다.

**이 선택이 틀렸음을 알게 되는 신호**

1. **6개월간 구현체가 하나도 추가되지 않고, 인터페이스 때문에 우회 코드가 생긴다.**
   → 과잉설계다. 어댑터를 줄이거나 인터페이스를 얇게 만든다.
2. **`import-linter` 계약을 예외 처리하는 커밋이 반복된다.** 경계가 실제 코드 구조와 맞지
   않는다는 뜻이다. 예외를 늘리지 말고 경계를 다시 긋는다.
3. **첫 교체 시점에 인터페이스를 크게 고쳐야 한다.** 인터페이스가 AWS 구현에 맞춰 잘못
   잡혔던 것이다 — 추상화가 leaky했다는 증거다.
4. **`approval/` 인터페이스가 전자결재 연동 시 맞지 않는다.** 가장 확인하고 싶은 지점이며,
   실무자 인터뷰로 조기에 검증할 수 있다.

**되돌리는 비용**

| 방향 | 비용 |
|---|---|
| 어댑터 제거(직접 호출로) | **싸다.** 인터페이스를 걷어내고 구현체를 직접 부르면 된다. 구현체가 하나뿐이라 병합이 단순하다 |
| 나중에 어댑터 도입 | **비싸다.** 도메인 로직 전반에 흩어진 구체 호출을 찾아 걷어내야 하고, 그 작업이 **심의 결과가 나온 뒤 촉박한 일정에** 놓인다 |
| 어댑터 개수 조정 | **싸다.** 6개는 상한이 아니라 현재 식별된 경계다 |

**비대칭이 여기서도 결정을 이끈다.** 지금 두는 비용은 인터페이스 6개이고, 나중에 도입하는
비용은 일정 압박 아래의 대규모 리팩터링이다. 그리고 **되돌리기가 싸다는 점이 과잉설계
위험을 감당 가능하게 만든다** — 신호 1이 관측되면 걷어내면 된다.

## 엣지 케이스

- **인터페이스가 특정 구현에 맞춰 새는 경우**: 예를 들어 `DocumentStore`에 S3의
  presigned URL 개념이 들어가면 온프렘 구현이 어색해진다. 인터페이스에 특정 구현의 어휘가
  들어가는지 리뷰에서 검사한다.
- **`approval/`의 비동기성**: 전자결재는 며칠이 걸릴 수 있다. 내부 DB 구현은 즉시 응답할
  수 있어 인터페이스가 동기적으로 설계될 위험이 있다. **승인은 항상 비동기로 모델링한다** —
  원칙 4의 `interrupt`와 정합한다.
- **`identity/`와 감사 로그**: 승인 주체를 감사 레코드에 남겨야 하는데, 주체 식별자 형식이
  구현마다 다르다(Cognito sub vs AD DN). 감사 로그에 **식별자와 함께 발급 주체**를 남긴다
  (ADR-007의 출처 표시와 같은 발상).
- **`llm/` 어댑터와 킬 스위치**: 킬 스위치 검사는 `guards`가 하고 어댑터는 하지 않는다.
  두 곳에서 검사하면 한쪽이 갱신되지 않았을 때 우회 경로가 생긴다.
- **`queue/`의 전달 보장**: at-least-once를 전제하고 멱등성은 소비자가 보장한다.
  구현체마다 보장 수준이 다르므로 인터페이스가 "정확히 한 번"을 약속하지 않는다.
- **온프렘 구현체를 만들지 않는 결정의 부작용**: 인터페이스가 실제로 교체 가능한지 검증되지
  않는다. **완화책으로 테스트용 인메모리 구현체를 둔다** — 두 번째 구현체 역할을 하면서
  단위 테스트에도 쓰인다.
